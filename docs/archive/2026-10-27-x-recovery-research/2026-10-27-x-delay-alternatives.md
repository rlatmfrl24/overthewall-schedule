# X 지연 게시물과 중복 REST 읽기 대안 조사

## 검토 범위

X 공식 문서와 기존 `0391a5e9` 소스 및 2026-10-27 운영 기록 분석을 검토했다. 유료 X 조회, 운영 쓰기, 예산·자동충전 변경은 하지 않았다.

## 완전성의 제약

유한 횟수의 REST 응답과 웹훅만 관찰한 어떤 시점에도 공급자가 나중에 더 오래된 글을 노출할 가능성을 배제할 수 없으면, 아무 글이 없는 세계와 아직 보이지 않는 글이 있는 세계는 구별할 수 없다. 따라서 공급자가 제공하는 가시성 지연 상한, 완전성 watermark, 신뢰할 만한 완전한 이벤트 기록 중 하나 없이 유한 종료 후 누락 0을 증명할 수 없다. 이는 이전 조사에서 검토한 구간 분할뿐 아니라 최신 게시물 ID로 완료 커서를 올리는 기존 전체 범위 조회에도 적용된다. 두 방법 모두 관측 가능한 글의 범위와 완료 시점에 관한 전제가 필요하다. X 사용자 타임라인에는 최근 최대 3,200건 한도가 있다. [타임라인 문서](https://docs.x.com/x-api/posts/timelines/introduction#user-posts-timeline), [기존 REST 커서 코드](../../../worker/features/x-posts/infrastructure/x-api.ts#L2649)

## 비교

| 방법 | 기대 | 조건과 한계 |
| --- | --- | --- |
| 완전 저장 ID로 구간 분할 + 열린 구간 공정 반복 감사 | 웹훅으로 완전하게 저장한 경계 게시물은 반복 응답에서 제외하고, 각 경계 사이의 늦게 노출된 게시물을 이후 순회에서 발견 가능 | 일정한 반복 주기 내에 요청 가능한 예산·처리 용량이 있고 해당 글이 그때까지 API에 계속 노출되며 권한·필터·3,200건 한도 안에 남는다는 조건. 이행 중 기존 토큰은 원래 범위로 끝내야 한다. 구간을 유한 기간 후 닫으면 무제한 지연을 보장하지 못한다. 영구 반복은 요청과 D1 작업 증가, 새로 찾은 글의 당일 이후 반복 조회비, $1 예산 소진·기아를 일으킬 수 있다. |
| 가정한 지연 상한 W만큼 보류 후 구간 감사 | 먼저 유입되는 글이 경계로 추가될 수 있고, 안정된 가상의 범위에서 한 번으로 복구 가능 | W 이내 가시화 및 W 이후 페이지 완료까지 결과의 안정성, 시간/ID 경계의 정확성, 경계 저장 완전성을 모두 가정해야 한다. 공식 문서에 W나 페이지 스냅샷 보장을 찾지 못했다. W 초과 글은 누락 가능하며, 검증되지 않은 가정을 100% 보장으로 표현하면 안 된다. |
| 전체 범위 + 일정 기간 중첩 조회 | 설계가 단순하며 짧은 지연은 다음 회차에서 수습할 수 있다 | 중첩 기간을 초과하면 누락 가능. 이미 받은 게시물을 매 회차 REST에서 반환해 서로 다른 UTC일에 재청구될 수 있다. 보류 및 예산 차단 시 중첩보다 더 뒤로 미완료 원점을 보존해야 한다. |
| 웹훅 replay 보조 | 전달 시도 후 누락된 이벤트의 복구 보조 | 최근 최대 24시간 내 해당 웹훅에 전달 또는 전달 시도한 이벤트만 대상. 구독 누락·전달 시도 자체가 없는 사건, 색인 지연, 24시간보다 오래된 이벤트의 완전한 대체 수단이 아니다. replay 비용이나 권한을 무료라고 가정하면 안 된다. [공식 replay](https://docs.x.com/x-api/webhooks/create-replay-job-for-webhook) |
| 전체 범위 조회를 같은 UTC일로 앞당김 | 같은 리소스를 그날 REST에서 다시 조회할 때 문서상 중복 청구를 줄일 가능성 | 웹훅 event와 REST Post가 같은 과금 리소스로 합쳐지는지 확정되지 않고 이전 운영 표본에서는 각각 계수됐으므로 효과를 가정하지 않는다. UTC일 이후 요청에는 적용되지 않고 X는 중복 제거를 soft guarantee로 설명한다. [요금 및 중복 제거](https://docs.x.com/x-api/getting-started/pricing#deduplication) |

완전 저장 경계는 같은 사이트·사용자·대상 게시물이어야 하고 본문과 필요한 미디어가 실제로 저장돼야 한다. 경계가 불완전하거나 삭제·비공개·수정·전환 등으로 유효성이 의심스러우면 제외하지 않고 기존 읽기로 처리하거나 보류해야 한다. 이 방식은 원래 앱의 갱신·삭제 처리를 별도 유지해야 한다. 현재는 이 모든 것을 입증하는 확정 경계 판정이 없다. [웹훅 저장 코드](../../../worker/features/x-posts/infrastructure/x-activity-site.ts), [기존 조사](2026-10-27-x-recovery-dedup-research.md)

## 운영 표본의 비용 비교 한계

기존 8명 REST 기록 9회에서 반환된 27건의 완전 저장을 모두 가정하고 각 구간을 한 번씩 확인하면 35회, Post Read 단가 기준 최대 가상 $0.135 절감이다. 이 값은 단일 순회에 대한 낙관적 계산이며, 반복 감사의 추가 요청·운영 비용과 날짜 간 재청구를 반영하지 않는다. 매 순회가 항상 35회라는 뜻도 아니다. X 읽기 과금은 반환 리소스 기준이며 당일 중복 제거는 soft guarantee다. 예산은 매 구간에도 실제 공통·사이트 게이트를 적용해야 한다. [운영 표본 보고서](2026-10-27-x-gap-validation.md), [공통 예산 코드](../../../worker/features/x-posts/infrastructure/x-shared-budget.ts), [X 가격](https://docs.x.com/x-api/getting-started/pricing)

가능한 방향은 지속적인 구간 감사와 명시적인 미완료 상태를 결합하되, 실제 공급자의 페이지 경계 및 안정성, 예산 포화 상황에서의 공정 진행과 API 가시성 유지 시간을 검증하는 것이다. 무기한 감사만으로도 공급자가 반환하지 않거나 조회 가능 범위에서 사라진 글은 찾을 수 없다. 현 기록과 공식 문서만으로는 누락 0, 예산 내 확정 완료, 실비 절감을 동시에 보장할 수 없다.


## 로컬 반복 구간 감사 실험

실험 테스트 (`.superpowers/sdd/2026-10-27-x-delay-lab/repeated-gap.integration.test.ts`, 로컬 전용)는 로컬 D1과 기존 `D1SharedXApiGateway`를 쓰되 X 공급자는 가짜 응답이다. 고정된 **하나의 과거 범위** 안에서 저장된 ID를 배타적 경계로 나누고, 각 구간의 마지막 페이지까지 처리한 후 다음 구간으로 넘어간다. 전체 순회가 끝나도 종료하지 않고 처음부터 다시 검사한다. 새로 저장한 글은 해당 순회가 완전히 끝난 뒤 다음 순회의 경계에 반영한다. 페이지와 결과 저장을 로컬 D1 batch로 처리하며 공통 예산은 실제 게이트웨이로 확인한다. 사이트별 예산과 실제 웹훅, 실제 스케줄러, 상한 설정, 상한 밖 신규 영역, 장기간 전체 사이트의 공정 스케줄링은 이 실험에 통합되지 않았다.

6개 시나리오 통과:

1. 이전에 빈 구간으로 지나간 뒤 게시물이 가시화되면 다음 순회에서 찾고, 저장 후 그다음 순회부터 경계로 사용해 재반환을 피했다. 일정 시간 내 회복은 가정된 지연과 조회 성공에 달려 있다.
2. 페이지를 넘기는 중 새 글이 생겨 offset 방식 가상 공급자에서 첫 순회 누락이 생겼고, 이후 순회에서 그 글까지 8건을 저장했다. 실제 X의 페이지 토큰이 offset이라는 뜻은 아니다.
3. $0.875 사용 시 첫 페이지 5건에 장부 $0.025가 추가된 뒤 잔여 $0.100보다 예약액 $0.125가 커서 다음 호출 전에 차단됐다. 인덱스·토큰·미완료 상태는 유지됐고 다음 UTC일 직접 재개해 나머지를 저장했다.
4. 게이트웨이 결과 캐시가 저장되고 페이지 체크포인트가 기록되기 전에 중단되면 동일 요청 ID로 캐시를 재사용했다. 공급자 응답 후 게이트웨이 캐시 이전의 실패는 이 경우에 포함되지 않으며 재전송 비용이 발생할 수 있다.
5. 공통 예산이 계속 소진되면 호출 없이 미완료 상태가 보존됐다. 즉 예산이 없는 경우 복구나 기한을 보장하지 못한다.
6. 저장된 글 8건만 있는 가상 범위에서는 빈 구간 9개를 두 차례 돌며 18회 호출했고 테스트 장부상 반환 Post 비용은 0이었다. 실제 X 청구나 다른 운영 비용이 0이라는 보장은 아니다.

기존 8명·27건 표본을 고정 경계로 단순화하면 한 차례 35회, 두 차례 70회가 필요한 시나리오다. 추가 글이 경계로 추가되거나 추가 페이지가 있으면 달라진다. 웹훅 보강 비용, 공급자당 요금, D1 읽기·쓰기와 실행량, 지연 길이 및 백로그를 포함한 장기 절감액은 근거가 없어 산출하지 않았다. 요청량이 늘어 X 호출 제한 또는 Cloudflare 사용량·예산 경쟁을 악화시킬 수 있다.

실험 명령(로컬 D1과 가상 공급자만 사용, Node 24):

```powershell
node node_modules/vitest/vitest.mjs run --config .superpowers/sdd/2026-10-27-x-delay-lab/vitest.config.ts
```

## 판단과 다음 검증 조건

무한 재검사는 **해당 글이 조회 가능하고, 구간이 빠짐없이 다시 읽히며, 예산과 실행 용량이 장기적으로 충분하고, 큐가 공정하게 실행되는 조건**에서만 언젠가 지연 글을 발견한다. 사용자 타임라인은 최대 최근 3,200건까지라 이 범위를 벗어나거나 공급자가 결과에서 제외한 글은 이 방법으로 찾을 수 없다. 유한 완료 시각, 모든 글의 수집, 총 비용 절감을 동시에 보장할 근거는 없다. 기존 커서 방식도 지연 가시성으로 오래된 게시물을 놓칠 수 있으므로 기존 방식이 그 문제를 해결했다고 표현하지 않는다.

운영 구현 전에 실제 X의 고정 범위 및 페이지 동작, 모든 페이지의 내구성, 기존 진행 중인 페이지의 원래 범위 유지, 새로운 상단 범위의 연속 보장, 경계 게시물의 본문·미디어 완전성, 수정·삭제·비공개 처리, 양 사이트와 공통 예산, 큐의 공정성·D1 한도를 따로 확인해야 한다. W시간까지만 반복하는 방식이나 W시간 성숙 대기는 W보다 지연되는 글의 누락을 허용하는 명시적 제품 결정 없이는 이 문제의 완전한 해결책이 아니다.

운영 코드는 수정·배포하지 않았다. 이번 작업에서 X 유료 조회, 운영 DB 쓰기, 예산·자동충전 설정 변경은 하지 않았다.

# 운영 기록 기반 구간 분할 비용·요청량 분석 — 2026-10-27

## 결론

10월 27일 UTC의 기존 타임라인 복구 기록에서 OTW 5명과 러브다이아 3명의 9개 REST 요청이 총 27개 서로 다른 Post를 반환했다. 27개 모두 **각 계정의 첫 REST 요청 전에 이미 해당 사이트에 저장되었고 웹훅도 수신된 것으로 확인**됐다. 이는 당시 완료 시점이나 필수 미디어의 완전성까지 증명하지는 않는다.

이 27개를 모두 완전한 제외 경계로 사용할 수 있고, 고정 상한 및 배타 경계가 동작하고, 나머지 구간에 페이지가 더 없다는 가정에서 8개 계정의 열린 구간은 총 35개이며 최소 35회 요청이 필요하다. 기존 9회 대비 **26회 증가, 약 3.9배**다. 공개 Post Read 단가 $0.005를 27개에 적용하면 반환을 모두 피했을 때의 **최대 가상 절감액은 $0.135**다. 미디어 및 공급자 실제 청구와 UTC 내 중복 제거 효과는 반영하지 않았고, 개별 Post 청구 내역도 확보되지 않아 실현 예상액이나 확정 청구액으로 볼 수 없다. 나머지 구간에서 새 글이나 다음 페이지가 나오면 요청 수가 더 늘 수 있다.

## 원장 표본과 가상 계산

최초 시각은 KST 2026-10-27, `REST`는 기록된 요청 수, `Post`는 해당 요청들에 반환된 서로 다른 ID 수다. `분할`은 관측된 27개만 제외 경계로 삼고 첫·마지막 빈 구간도 검사하여 `Post + 1`을 적용한 가정이다. 다른 경계가 있거나 페이지가 필요하면 달라진다.

기존 원장상 여덟 계정의 첫 요청에는 모두 `since_id`가 있었고, 모든 반환 ID가 실제 `since_id`보다 크다. 하네는 첫 요청과 기존 이어 페이지가 같은 기준을 사용했다. 9회 모두 `until_id`를 사용하지 않았으므로 **원래 복구 범위에는 기록된 고정 상한이 없다**. 위 분할 시나리오는 가상의 정상 상한을 추가로 가정한 것이며 원래 공급자 결과 전체의 고정 스냅샷을 재현했다고 주장하지 않는다.

해당 계정의 첫 요청 시각과 비교한 결과, OTW 21개와 LuvDia 6개 모두 `x_posts.first_seen_at`이 첫 요청보다 이전이고 공유 `x_activity_dispatch.received_at`도 이전이다. 각 사이트별 dispatch 및 inbox 상태는 현재 모두 `complete`다. 상태 완료 시간은 별도로 기록되지 않으므로 첫 요청 전 완료를 확정하지 않으며, 저장 데이터의 본문·미디어가 그 당시 완전했는지도 확인하지 못했다. 각 사이트 `x_api_resource_daily`에서도 27개가 이 날짜의 해당 사이트 첫 Post 리소스 조회로 기록되었다. 반환 자료가 X 측 모든 청구 항목과 일대일로 같다는 보장은 없다.

앞서 확인한 X 콘솔의 UTC 10월 27일 Post 전체 집계는 33개·표시금액 $0.17이며 개별 Post 청구 명세는 없었다. 27×$0.005 = $0.135는 공개 단가를 적용한 가상 최대치이며 그 콘솔 금액으로부터 특정 리소스의 실제 청구를 분리해 확정한 값이 아니다. X의 일별 중복 제거는 soft guarantee다. [X 가격과 중복 제거](https://docs.x.com/x-api/getting-started/pricing), [X 타임라인 기준 ID 필터](https://docs.x.com/x-api/posts/timelines/introduction#time-based-filtering)

## 재현 방법과 데이터 범위

실행에 사용한 읽기 전용 코드 cost-read.mjs (`.superpowers/sdd/2026-10-27-x-gap-lab/cost-read.mjs`, 로컬 전용)는 먼저 Cloudflare D1 계정 당일 읽기 집계를 조회하고 400만 이상이면 종료한다. 단일 `SELECT`만 허용하며 각 SQL의 `rows_written`이 0이 아니면 종료한다. 공유 DB의 `x_shared_requests`에서 지정 UTC일의 완료된 타임라인 요청을 날짜 인덱스로 고르고, `x_activity_targets`로 사이트·계정을 식별한다. 기록된 `post_ids`만으로 `x_activity_dispatch`를 조회하고, 양 사이트 DB에서는 그 ID만 기본 키로 `x_posts`, `x_api_resource_daily`, `x_activity_inbox`에 대조한다. 사이트별 ID가 다른 DB로 섞이지 않게 나눠 읽는다. ID의 기준 비교는 JavaScript `BigInt`를 사용한다.

각 질의와 비교식은 `cost-read.mjs`에 포함되어 있다. 이 스크립트의 재실행은 **X API 호출이 아니라 제한된 Cloudflare D1 읽기**이지만 운영 D1 읽기량을 추가하므로 필요할 때만 수행한다. 토큰이나 원래 요청 URL·커서 값을 기록하지 않고 집계 결과 (`.superpowers/sdd/2026-10-27-x-gap-lab/cost-aggregate.json`, 로컬 전용)에 수치만 저장한다. 메타데이터가 반환한 읽기량은 공유 요청 41, dispatch 107, OTW 사이트 125, LuvDia 사이트 35행으로 실행당 308행이며 모두 `rows_written=0`이다. 최초 실행과 기준 ID 추가 검증을 위한 재실행은 총 616행이며 각 실행 전 Cloudflare 관측 계정 읽기량은 741,166행이었다. 분석 당시 기록은 2026-10-27 UTC 당일 보존된 요청만이며 미래에도 같은 기간이 보존될 것으로 가정하지 않는다.

이번 분석에는 추가 X 유료 요청이나 운영 쓰기가 없었으며 기존 예산·자동충전 설정은 변경하지 않았다. 분할 알고리즘의 실제 제공자 동작, 고정 상한과 비용은 아직 검증되지 않았다.


## 로컬 구간 분할 실험

기준 소스는 `0391a5e9`다. 운영 기능을 구현하거나 배포한 것이 아니라 로컬 실험 (`.superpowers/sdd/2026-10-27-x-gap-lab/x-gap-research.integration.test.ts`, 로컬 전용)에서 가상 X 응답과 로컬 D1을 사용했다. 실제 공통 게이트웨이 `D1SharedXApiGateway`와 예산 장부를 통과하며, 가상 공급자는 배타적 `since_id`/`until_id`, 고정 상한과 페이지 토큰을 가정한다. 사이트별 예산, 웹훅 처리·전체 운영 스케줄러와 구간 알고리즘을 통합 검증한 것은 아니다. 총 6개 시나리오가 통과했다.

| 시나리오 | 관찰 |
| --- | --- |
| 알려진 세 경계 앞·사이·뒤 | 기존 세 글을 제외하고 네 구간에서 누락 네 글을 수집했다. ID는 `BigInt`로 비교했다. |
| 불완전한 기존 글 | 완전한 두 글만 경계에 포함했을 때 불완전한 글 한 건을 조회했다. 실제 완전성 판정 방법은 아직 없다. |
| 하네와 같은 알려진 글 8건 | 가상으로 9개 구간에 각각 요청해 모두 빈 응답을 받았다. 실제 원장 2회와 비교하면 7회 증가다. |
| 페이지 응답 후 저장 전 중단 | 요청 ID를 미리 보존하고 게이트웨이 결과가 이미 캐시된 조건에서 다시 받아 저장했고, 다음 페이지는 원래 상·하한과 토큰을 유지해 7건을 모았다. 게이트웨이 결과 저장 전의 통신 장애에서는 재발송과 추가 과금 가능성을 배제하지 못한다. |
| 예산 차단·재개 | 기존 사용 $0.875에서 첫 페이지 5건 후 $0.900. 다음 페이지에 필요한 공통 예약 $0.125가 잔여 $0.100을 넘어 실제 fetch 전에 차단됐다. 토큰·구간은 보존됐고 UTC 다음 날 로컬에서 나머지 2건을 수집했다. 이는 로컬의 직접 재개이며 실제 자동 실행 시각을 뜻하지 않는다. |
| 이미 검사한 구간에 지연 게시물 | 첫 구간을 검사한 뒤 해당 구간에서 새로 보이는 글을 공급자 가정에 추가하면 그 회차에서 누락됐다. 실험은 누락 위험을 확인한 것이며 누락 방지가 성공했다는 뜻이 아니다. |

기존 운영 구현을 사용하는 별도 D1 통합 테스트에서도 미완료 페이지의 원래 기준·토큰을 보존하는 복구와 예산에 맞는 계정부터 처리한 뒤 차단된 계정을 다음 정기 실행에서 복구하는 두 사례가 통과했다. 구간 실험의 직접 재개와 기존 구현의 정기 실행은 서로 다른 테스트다.

실험 재현(로컬 D1 및 가상 X만 사용):

```powershell
node node_modules/vitest/vitest.mjs run --config .superpowers/sdd/2026-10-27-x-gap-lab/vitest.config.ts
node node_modules/vitest/vitest.mjs run --config vitest.schema.config.ts worker/features/scheduled-operations/infrastructure/collector-sql-cadence.integration.test.ts -t "recovers only a pending X cursor|recovers affordable X accounts"
```

결론적으로 단순 구간 분할은 지연 노출과 고정 상한 문제로 누락 없는 복구를 보장하지 못한다. 운영 도입 전 지연 노출·페이지 변동에 대한 보완 전략, 기존 미완료 페이지와 경계 스냅샷의 안전한 이행, 실제 미디어 완전성 판정, 사이트·공통 예산 양쪽 연동 및 X의 실제 필터·청구 동작을 검증해야 한다. 특히 추가 조회나 유료 시험은 사용자 승인 범위에 없다.

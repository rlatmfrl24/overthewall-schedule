# X 구간 재검사 운영 적용 판단 — 2026-10-27

## 결론

**운영 적용 보류.** 로컬에서 페이지 복구와 양 사이트 예산 차단의 일부 경로는 검증했으나, 기존 게시물의 전체 미디어·본문 완전성을 신뢰성 있게 판정하는 정보가 없고 구간 재검사 알고리즘도 실제 운영 수집·스케줄러에 통합되지 않았다. 공급자 가시성 지연과 페이지 안정성, 오랫동안 반복할 때의 예산·요청량, 수정·삭제와 상단 범위 관리도 해결되지 않았다. 아래 통과 결과는 제안 모델과 기존 구성요소의 로컬 시험이지 운영 기능의 합격 판정이 아니다.

추가 X 유료 조회, 운영 데이터 쓰기, 배포, 예산·자동충전 설정 변경은 없었다. 코드 기준 `0391a5e9`다.

## 로컬 검증: 페이지 및 예산

연구용 통합 실험 (`.superpowers/sdd/2026-10-27-x-readiness-lab/readiness.integration.test.ts`, 로컬 전용) 16/16 통과. OTW D1과 LuvDia D1의 별도 로컬 인스턴스 및 기존 `requestXApi`의 사이트 예약, 중앙 `D1SharedXApiGateway`의 공통 예약을 사용했다. X fetch는 전부 가짜다. 구간 상태·내구성은 연구용 로컬 D1 테이블로 모델링했으며 실제 스케줄러, 큐, lease, 삭제·전환 오케스트레이션에는 연결되지 않았다.

- **저장 실패·페이지 재개:** 양 사이트 각각 첫 페이지와 두 번째 페이지 저장에 실패하도록 로컬 D1 batch 중간에 오류를 넣었다. 같은 batch의 글과 체크포인트는 함께 롤백됐고 이전 상·하한, 토큰 및 미완료 상태가 유지됐다. 게이트웨이가 이미 응답을 캐시한 조건에서는 동일 요청 ID로 응답을 재사용해 추가 fetch 없이 재개하고, 원래 상·하한과 토큰으로 총 7개를 저장했다.
- **만료 토큰:** 가상 공급자가 두 번째 페이지에 HTTP 400을 반환하면 완료로 표시하지 않고 5건과 원래 커서를 보존했다. 실험에서는 오류를 별도로 식별했다는 가정으로 로컬 상태를 수동 리셋해 동일 구간을 처음부터 다시 조회하고 6개를 저장했다. 재조회가 늘었고 실제 X의 토큰 만료 오류 분류, 자동 리셋과 재시도 정책은 검증하지 않았다. 공급자 응답 후 게이트웨이 캐시 기록 전의 장애는 재전송 비용이 발생할 수 있다.
- **사이트별 차단:** OTW와 LuvDia 각각 사이트 사용액 $0.960일 때 사이트 예약 $0.050이 $1을 초과해 공통 게이트웨이 및 fetch 전에 차단됐다. 다른 사이트 요청은 별도 사이트 장부로 처리됐다.
- **공통 차단:** 두 사이트 각각 공통 사용액 $0.900에서 공통 예약 $0.125가 잔여 $0.100보다 크면 외부 fetch 전에 차단됐고 사이트 예약도 해제됐다. 각 사이트에서 첫 페이지 후 사이트 또는 공통 예산이 차단되는 4가지 조합 모두 범위·토큰을 보존하고 다음 UTC일 로컬 직접 실행으로 나머지 페이지를 저장했다.
- **동시성:** 공통 사용액 $0.875에서 OTW가 $0.125를 예약한 상태에서 LuvDia 요청은 차단됐다. 첫 응답 정산 후 공통 장부는 사용 $0.880, 예약 0이었다.
- **범위 반복:** 앞선 반복 구간 실험 (`.superpowers/sdd/2026-10-27-x-delay-lab/repeated-gap.integration.test.ts`, 로컬 전용)도 6/6 재실행 통과했다. 이미 지난 구간에 지연 노출되는 글과 페이지 순서 변동을 다음 순회에서 찾는 가상 사례다. 공급자의 가시성 및 페이지 보장은 검증하지 못했다.

공통 $1은 신규 REST 요청을 예약할 때의 목표다. 이미 전달·과금된 웹훅 이벤트가 나중에 장부에 기록되면 목표를 넘을 수 있으며, 기존 로컬 통합 테스트는 $1.005 기록 후 구독을 예산 일시중지하는 동작을 확인했다(1/1). 따라서 전체 X 실제 청구를 절대 $1 이하로 보장한다고 말할 수 없다. 외부 충전 설정도 바꾸지 않았다.

## 로컬 검증: 미디어

기존 `xActivityMediaReady`와 정규화 로직을 이용해 사진 URL, 영상 포스터, 누락된 항목, 허용되지 않은 URL, 빈 첨부 목록을 시험했다. 양 사이트 각각 실제 로컬 `writeStoredPosts`를 통해 사진·영상 메타데이터를 저장하고, **원본 첨부 키가 남아 있고 모든 항목이 일치하며 사이트에서 유효한 상태**라는 가정의 연구용 판정을 시험했다. 원본 소실, 미디어 일부 유실, 미완료, 숨김은 보수적으로 제외했다. 이 시험은 영상 파일 다운로드나 재생을 확인한 것이 아니다.

또한 첨부 키가 있으나 미디어 expansion이 없는 자료와 원래 미디어가 없는 자료가 정규화 후 똑같이 빈 `media` 배열이 되는 사례를 확인했다. 따라서 저장된 `x_posts`만으로 이전 미디어의 누락 여부를 판정할 수 없다. 아래 기존 소스 검토에 따라 원본과 보강 payload도 완료 시 제거되므로 이 임시 판정을 현재 운영 데이터 전체에 적용할 수 없다. `mediaReady=true`는 앱의 미디어 **표시 준비**일 뿐 본문·참조·게시물 전체의 완전성은 아니다.

## 판정과 필요한 작업

1. 사이트별 게시물·작성자 일치, 접근/삭제 상태, 본문·장문 및 모든 예상 첨부 키·유형·URL, 부분 오류, 참조 품질의 근거를 내구성 있게 보존하고, 불명확한 기존 글은 경계에서 제외하는 계약이 필요하다. X가 필드 생략을 어떻게 보장하는지 증명되지 않은 경우도 불명으로 남겨야 한다.
2. 오래된 미완료 REST 토큰은 원래 범위로 우선 완료하고, 구간별 상·하한·토큰·요청 ID·저장 상태와 공정 재검사 큐를 안전하게 유지해야 한다. 만료·실패 유형 분류 및 복구와 새로운 상단 범위, lease·동시성·삭제는 실제 수집 경로에서 검증해야 한다.
3. 예산 포화·D1 상한에서 두 사이트의 기아를 방지하고 복구 지연과 미완료 상태를 표시해야 한다. 사용자 타임라인 3,200건 한도 및 임의로 긴 공급자 노출 지연에서는 유한 시간 누락 0을 약속할 수 없다.
4. 이전 8명·27건 고정 가정에서 한 순회 35회이며 반복할수록 요청이 늘어난다. 실제 예산·보강·D1 비용과 공정 진행이 허용 가능한지 검증하기 전 장기 비용 절감을 주장할 수 없다.

## 미디어 완전성 조사 근거

## 결론

현재 `xActivityMediaReady`나 `x_activity_inbox.status=complete`, `x_posts` 존재만으로는 구간 재검사에서 조회를 생략해도 되는 **게시물 전체의 완전성**을 증명할 수 없다. 운영 적용을 위해서는 사이트별 본문·첨부·접근·참조의 수집 계약과 출처/확인 이력을 명시적으로 보존하고, 불명·미완료 상태는 경계에서 제외해야 한다. 제한된 이미지 표시 준비 여부와 본문/미디어 원본 완전성은 서로 다른 조건이다.

## 현재 코드와 공식 문서

- 이벤트 파서는 `post.create`, 이벤트/작성자/시각을 검증하지만 `text`가 아예 없어도 허용한다. `note_tweet`가 있으면 문자열 형식만 검증한다. X 공식 설명에서 장문 전체 텍스트는 `note_tweet`에 들어가며, Activity `includes`는 선택 사항이고 전달 시점의 상태에 따라 필드가 달라질 수 있다. 필드가 빠진 이벤트를 단순히 본문·첨부가 없는 확정 자료로 볼 근거는 없다. [이벤트 파서](../../../worker/features/x-posts/domain/x-activity.ts), [X post 데이터 사전](https://docs.x.com/x-api/fundamentals/data-dictionary), [Activity payload](https://docs.x.com/x-api/activity/event-payloads)
- `xActivityMediaReady`는 첨부 키 배열이 없으면 false, 명시적으로 빈 배열이면 true다. 키가 있으면 모든 키가 해당 `includes.media`에 매칭되고 사진은 HTTPS twimg URL, 영상/GIF는 HTTPS twimg `preview_image_url`이 있어야 true다. 전체 텍스트·참조·최종 DB 저장·다른 사이트 상태는 판단하지 않는다. [미디어 판정](../../../worker/features/x-posts/domain/x-activity.ts)
- X에서 `preview_image_url`은 정적 대표 이미지이고 `variants`가 재생용 형식/URL을 표현한다. 현재 모델에는 `variants`가 없고, UI는 비디오 포스터를 보여주고 X 원문을 열도록 되어 있다. 따라서 ‘앱이 요구하는 포스터 표시 가능’과 ‘영상 재생 파일을 저장함’은 다르다. URLs는 실제 이미지 파일 본문을 영구 저장했다는 증거도 아니다. [X 미디어 사전](https://docs.x.com/x-api/fundamentals/data-dictionary), [정규화](../../../worker/features/x-posts/infrastructure/x-api.ts#L1959), [카드](../../../src/features/x-posts/ui/x-post-card.tsx#L76)
- 웹훅 이벤트에서 미디어 준비가 불명확한 경우 Post lookup을 공통/사이트 예산을 거쳐 시도한다. 다만 `write`가 완료 판정 전에 수행될 수 있고, 보강 응답의 첨부 키가 없을 때 완료로 취급하는 경로도 있다. 원본이 없다는 사실과 응답 필드 누락의 차이 및 기존 저장물의 품질은 별도 보장되지 않는다. 종료 시 원본과 보강 payload는 지워지고, inbox는 30일 경과 후 삭제된다. `media_source/count/types`와 `status`는 영속적 원본 증거도 게시물 전체 완전성 인증도 아니다. [웹훅 처리](../../../worker/features/x-posts/infrastructure/x-activity-site.ts#L118)
- 정규화는 매칭되지 않은 media key를 버리고 저장 객체의 `media` 배열만 남긴다. 기존 `x_posts.value`와 `media_count`만으로 원래 몇 개의 media key가 있었는지, 장문 원문이 누락됐는지 확실히 복원할 수 없다. 사진 한 건이라도 유효할 경우 나머지도 다 있다는 증명은 안 된다. [정규화](../../../worker/features/x-posts/infrastructure/x-api.ts#L1959), [스키마](../../../db/schema/index.ts#L765)
- 인용·답글의 ID가 있어도 정규화 직후 연결 대상 본문은 `null`이며 별도 참조 보강 상태가 있다. 경계 판정에서 참조 본문을 필수로 할지는 사용자에게 보장하는 카드 동작 및 관련 참조 정책에 따라 결정해야 한다. 멤버 계정·사이트 소속과 각 사이트의 접근/삭제/차단 상태는 독립적으로 판정한다. 현재 구독·파서는 `post.create` 전용이므로 X 측 수정·삭제가 자동으로 완전 동기화된다고 가정할 수 없다. 관리자 삭제된 정보는 보강이나 구간 경계 처리로 복원해선 안 된다. [정규화](../../../worker/features/x-posts/infrastructure/x-api.ts#L2008), [참조 이력](../../../worker/features/x-posts/infrastructure/x-history.ts#L406), [구독](../../../worker/features/x-posts/infrastructure/x-activity-coordinator.ts#L192)

## 권고하는 보수적 계약

동일 사이트의 대상 계정·ID이고 해당 사이트에서 공개 허용·미삭제 상태이며, 요청한 필드와 응답의 부분 오류, 모든 예상 첨부 키·유형 및 URL 매칭, 본문이 필요한 품질로 저장됐음을 별도의 내구성 있는 출처 증거와 함께 확인한 경우에만 해당 게시물을 **그 사이트의** 제외 경계 후보로 삼는다. 누락/불명/보강 대기/접근 변경/관련 데이터 보존 근거 부족은 경계로 삼지 않는다. 레거시 자료는 역추정하지 않는다. 삭제·숨김은 접근 정책대로 별도 처리하며 경계화나 조회·복원 여부를 보안 계약에 맞게 재검토한다.

이 규칙도 새 원본에서 필드 생략이 ‘없음’을 뜻하는지, X가 장문/첨부/수정 상태를 언제 확정하는지, 링크 유효성, 외부 서비스 접근과 수정 이력, quote/reply 미리보기의 요구 품질을 입증하지 못하면 **확정 경계**를 만들지 못한다. 특히 경계로 제외하면 일반 REST 업데이트로 얻던 변경 정보도 받지 못하므로 관련 수명주기 동기화를 따로 설계해야 한다.

# 웹훅·REST 복구 중복 조회 조사 — 2026-10-27

## 결론

REST가 이미 저장된 글을 다시 읽는 이유는 웹훅과 REST의 완료 위치가 의도적으로 분리되어 있기 때문이다. 웹훅 한 건의 도착은 그보다 오래된 다른 글의 전달·저장까지 증명하지 않는다. 최신 웹훅 ID로 REST의 완료 위치를 곧바로 올리거나 웹훅이 정상이라는 이유만으로 REST 복구를 생략하면 누락이 생길 수 있다. 이번에는 운영 코드·수집·예산·자동충전 설정을 변경하거나 X 유료 요청을 보내지 않았다.

검토할 만한 절감안은 **저장이 확실한 웹훅 Post ID를 제외 경계로 삼고 그 사이의 모든 열린 구간을 REST로 검사하는 방식**이다. 이는 단순히 최신 ID를 완료 위치로 쓰는 것과 다르다. X가 제공하는 `since_id`/`until_id`는 각각 해당 ID 뒤/앞을 반환하므로, 누락 후보가 있는 사이 구간을 계속 살펴볼 수 있다. 다만 이 방식의 경계·상한·변경 중 페이지 동작과 X 실제 청구 효과는 아직 검증되지 않았다. 공식 문서나 이번 관측만으로 누락 0 또는 비용 절감을 보장할 수 없으므로, 구현·운영 전 검증과 실패 시 기존 전체 범위 방식으로 복귀하는 설계가 필요하다. [X 타임라인 필터](https://docs.x.com/x-api/posts/timelines/introduction#time-based-filtering), [요청 매개변수](https://docs.x.com/x-api/users/get-posts)

## 현재 흐름과 하네 표본

- 웹훅은 수신을 inbox에 기록하고 처리 후 `writeStoredPosts`로 게시물을 저장하지만 REST 완료 위치를 전진시키지 않는다. 미디어가 부족하면 별도의 보강 조회를 할 수 있다. [웹훅 수신·저장 코드](../../../worker/features/x-posts/infrastructure/x-activity-site.ts)
- REST는 마지막으로 **전체 페이지를 저장 완료한** `last_seen_post_id`를 기준으로 조회한다. 미완료 페이지가 있으면 최초 기준 `sync_base_post_id`와 원래 `pagination_token`을 유지하며, 새로 받은 페이지의 저장이 성공한 후에만 커서를 기록한다. 그래서 그 범위에 웹훅으로 이미 저장된 글이 있으면 X 응답에 다시 포함된다. [REST 조회 및 커서 코드](../../../worker/features/x-posts/infrastructure/x-api.ts#L2649), [커서 영속 코드](../../../worker/features/x-posts/infrastructure/x-api.ts#L1585)
- 10월 27일 KST 09:38 하네 REST 첫 페이지 5건과 10:44 이어 페이지 3건은 모두 해당 REST 요청 전에 저장된 게시물이며, 8건 각각의 이전 웹훅 dispatch 완료를 운영 원장의 읽기 전용 대조로 확인했다. 첫 요청은 `since_id`를 사용했고 이어 요청은 같은 `since_id`와 `pagination_token`을 함께 사용했다. 8개 Post는 각각 그 UTC일 최초 타임라인 조회로 기록됐다. 8건 모두 이전 웹훅 수신은 UTC 10월 26일, REST 재조회는 UTC 10월 27일이었다. 대조 SQL은 0 쓰기였다. 페이지·웹훅 대조 (`.superpowers/sdd/2026-10-27-x-followup/hane-event-days.json`, 로컬 전용), 요청 형태 (`.superpowers/sdd/2026-10-27-x-followup/hane-request-shape.json`, 로컬 전용), [앞선 실제 실행·청구 대조 기록](../../current-work.md)

## ID 경계별 누락 탐색: 조건부 설계안

예를 들어 REST 완료 위치 `A`와 검증된 기존 글 ID `B`, `C`, `D` 사이를 `(A,B)`, `(B,C)`, `(C,D)`, `(D,고정 상한)`으로 나눈다. 각 구간의 빠진 글이 있다면 그 범위를 조회·저장하고, 이미 온전하게 저장된 경계 글 B/C/D는 반환 대상에서 제외하는 구상이다. X 문서는 ID 범위 필터와 페이지 토큰을 제공하며 두 ID를 함께 사용하면 `since_id < until_id`를 요구한다. [공식 타임라인 필터](https://docs.x.com/x-api/posts/timelines/introduction#time-based-filtering), [공식 엔드포인트](https://docs.x.com/x-api/users/get-posts), [페이지 토큰](https://docs.x.com/xdks/python/pagination)

성공 전제와 미확정 사항:

1. 경계는 **동일 사이트·허용 계정·동일 게시물**이고 작성자·본문·필수 미디어가 안전하게 저장된 ID만 사용한다. 처리 대기/실패·미디어 미확보·삭제/비공개/전환 중인 자료는 유효한 제외 근거가 아니다. 편집·삭제·내용 갱신과 다른 수집 기능에 필요한 갱신을 놓치지 않도록 별도 계약을 확인한다.
2. 시작 전에 전체 조사 범위의 상한과 경계 집합을 고정하고, 처리 중 신규 게시물과 지연된 웹훅은 후속 범위에서 놓치지 않아야 한다. `end_time`과 ID를 함께 쓰는 경우 우선순위, 경계 포함 여부, 페이지 중 새 글/삭제가 있는 경우의 공급자 snapshot 동작은 문서만으로 완전히 확인되지 않았다. 이를 검증하지 못하면 기존 범위 조회를 유지한다.
3. 모든 구간을 빠짐없이 검사하고 구간마다 `next_token`이 끝날 때까지 저장·진행 상태를 영속화한다. 예산 차단·장애·재시도 시 미완료 구간을 보존하고 전체 REST 완료 위치를 먼저 전진시키지 않는다. 기존에 발급된 이어 페이지 토큰은 원래 범위·매개변수로 끝까지 처리하며 구간 분할로 섞거나 강제로 버리지 않는다.
4. X ID는 전역 64비트 Snowflake로 대체로 시간순이며 JS `Number`는 정밀도를 잃을 수 있다. 문자열 또는 `BigInt`로 숫자 순서를 정확히 비교하고, ID 간 빈 숫자에서 해당 멤버의 글이 없다고 추정하지 않는다. [X ID 공식 설명](https://docs.x.com/fundamentals/x-ids)
5. 조회 구간의 스냅샷, 경계 저장, 페이지 커서 및 완료 표시가 동시 웹훅·관리자 보관/삭제와 충돌하지 않도록 트랜잭션과 lease를 설계한다. 인증·사이트 격리·공통 예약과 각 사이트 예산 방어도 기존 경로 그대로 통과해야 한다.
6. X 사용자 타임라인은 최근 최대 3,200건으로 문서화되어 있다. 기간이 너무 길거나 권한 변경·삭제·API의 색인 지연 등으로 공급자가 돌려주지 않는 글까지 수집할 수 있다는 보장은 없다. 한도 초과, 불명확한 상한/경계, 페이지 오류, 검증 불일치 또는 예산 부족은 완료 대신 보류·경고하고 기존 방식/별도 복구 경로로 이어야 한다. [X 사용자 타임라인 한도](https://docs.x.com/x-api/posts/timelines/introduction#user-posts-timeline)

### 비용과 운영 상의 교환

- 저장된 경계 ID 3개면 빈 구간을 포함해 최대 4개 구간, 즉 최소 4회 요청이 필요하며 각 구간에서 추가 페이지가 생길 수 있다. 기존 단일 페이지보다 HTTP 요청·rate limit·큐/D1 읽기와 쓰기가 늘어난다. 추가 요청이 항상 이득인 것은 아니다.
- X는 공개 문서상 읽기 응답의 리소스 단위로 청구한다. 빈 응답이라도 공급자·앱별 계약과 예외를 확인해야 하며 무료라고 확정할 수 없다. 현재 앱은 요청 전 공유·사이트 예산을 예약하므로, 결과가 비어도 각 요청의 보수적인 예약 여유와 D1 작업량이 필요하다. 예산이 부족하면 미완료 상태를 유지한다. [X 가격](https://docs.x.com/x-api/getting-started/pricing), [공통 예약 코드](../../../worker/features/x-posts/infrastructure/x-shared-budget.ts#L105)
- 최소값이 최적이 아닐 수 있다. 예컨대 기존 글 8건의 양 끝을 포함한 전체 범위를 나누면 9개 구간을 살펴야 하고, 기존 실행은 2회 요청이었다. 빠진 글이 없으면 중복 Post 반환을 피할 잠재력이 있지만 각 구간이 비었다는 근거를 요청 없이 추정할 수는 없다. 누락 글이 많거나 알려진 ID가 많으면 추가 호출이 크게 늘 수 있어, 해당 계정의 예상 절감액·요청 수·시간·예약·실제 응답 분포를 기준으로 기존 스캔과 선택 비교해야 한다. 편의상 인위적 구간 수 상한에 걸렸다면 기존 전체 구간 복구로 안전하게 전환해야 한다.
- 합성 데이터/로컬 통합 테스트는 경계·동시성·재개 정확성을 검증하는 데 필요하다. 하지만 X 실제 필터/페이지 동작, 빈 응답 실제 과금, 웹훅과 REST 간 과금 결합, 금액 절감은 대체하지 못한다. X 실계정 유료 검증은 별도 승인 없이 하지 않는다.

## 추가 검증 제안

1. 기존 운영 기록을 읽기 전용으로 분석해 계정별 저장 완료 ID 수, 커서 미완료 범위, 예상 분할 구간·요청 수와 공개 단가 기준 중복 반환 금액을 추산한다. SQL은 기존 D1 예산 가드와 인덱스 조건을 지키고 쓰지 않는다.
2. 상한·배타 경계·빈 구간·멀티 페이지·동시 신규/지연 이벤트·이전 커서·삭제/미디어·사이트 전환·예산 차단·재시도·3,200건 초과를 로컬에서 검증한다. 서버가 동일 결과 snapshot을 보장하지 않는 조건은 명시한다.
3. 아직 불확실한 X endpoint의 경계와 실제 청구는 공식 문서 또는 향후 승인된 실제 관측으로 확인한다. 데이터 손실이나 비용 악화의 위험이 해소되기 전에는 현재 REST 복구를 변경하지 않는다.

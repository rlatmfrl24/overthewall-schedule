# 구조 검토 후보 02 — 카탈로그 조회 점검

카탈로그 목록·페이지 밖 선택 항목·검색·전체 게시가 각자 조회 결과의 범위와 최신 여부를 판단하는 경로를 점검했다. **기능 문제 2건, 읽기 비용 문제 1건**을 확인했다. 이번에는 제품 코드·정식 테스트·배포 설정을 수정하지 않았다.

- 검토 기준: `codex/play-catalog-retry`, HEAD `b2be7c7e1f976a8702eb9fa386186ada0f28ed82` + 직전 후보01의 미커밋 수정. 운영 소스와 동일하다는 주장은 아니다.
- 부하 가정: 소수 관리자, 25곡 단위 페이지, 기존 비용 회귀 테스트와 같은 5,000곡 규모.
- Graphify: `graphify-out/graph.json`, 9,352 nodes, `built_at_commit=d27f26a4628dff34b9eb06628b957b26c3b3aa11`. `catalog lookup selected revision` 조회는 211개 node 중 39개만 budget 안에 표시됐다. 관계 탐색에만 사용하고 현행 소스·호출자·실행으로 재확인했다. 폐기된 이관 경로는 현행 근거에 포함하지 않았다.

## 먼저 수정할 문제

### 1. [P2] 오래된 선택 조회가 최신 페이지의 행을 덮는다

위치: `src/features/otw-play/ui/admin/catalog-manager.tsx:192–194`.

- 역할: 첫 페이지 밖에 있는 선택 곡을 별도로 조회하고 목록에 합친다.
- 문제: 선택 결과를 마지막에 붙이고 Map의 마지막 행을 채택해 version을 무시한다. 현재 페이지 revision9의 인물 version3과 캐시된 선택 결과 revision7의 같은 인물 version1을 주고 선택 결과의 재조회만 실패시키면, 실제 `곡 정보 수정 → 원곡 가수 검색`에 `Current artist` 대신 `Old artist`가 표시됐다.
- 최소 수정: 기존 `queries/use-admin-catalog.ts:60`의 `mergeAdminCatalogRows`를 재사용해 최신 version을 유지한다. 이 병합과 선택 보완·revision/준비 상태를 기존 query 모듈에서 소유하도록 모아 같은 규칙이 화면마다 달라지지 않게 한다.
- 미수정 영향: 최신 정보가 이미 도착했어도 과거 인물·채널 상태를 제시할 수 있다. 수정 요청은 서버의 version/CAS 검사에 막힐 수 있으며, 이번에 데이터 손상은 관측하지 않았다. 발생 조건은 서로 다른 시점의 캐시와 한 조회의 실패/지연이 겹치는 경우다.

### 2. [P2] 페이지 밖 선택 곡의 조회 실패를 표시하지 않는다

위치: `src/features/otw-play/ui/admin/catalog-manager.tsx:189,196`, 목록 오류 표시는 `:477–489`.

- 역할: URL의 `selected`가 현재 페이지에 없을 때 해당 곡을 보완한다.
- 문제: 별도 `selectedCatalog`의 loading/error/refetch는 소비하지 않고 목록의 상태만 반환한다. 실제 관리자 컴포넌트에 첫 페이지 성공 + 선택 조회503을 주면 선택 조회는 error 상태인데 오류 안내는 0개였다. 선택 곡 상세가 열리지 않아도 별도 재시도를 제공하지 않는다.
- 최소 수정: query 모듈에서 선택 조회의 준비/실패/재시도를 반환하고 해당 상세 부분에 안내와 재시도를 연결한다. 성공한 목록은 계속 사용할 수 있어야 한다. 새로고침이나 다른 작업의 무효화에 복구를 의존하지 않는다.
- 미수정 영향: 페이지 밖 항목의 북마크·뒤로 가기에서 일시적인 오류가 빈 결과처럼 보인다. 데이터 삭제 문제는 아니지만 사용자가 선택한 작업에 자연스럽게 복귀하지 못한다.

## 함께 개선할 문제

### 3. [P2] 검색을 넣으면 페이지 크기와 무관하게 전체 후보를 읽는다

위치: `worker/features/otw-play/infrastructure/d1-admin-catalog-repository.ts:359–374`.

- 역할: 목록과 선택기의 검색 결과를 25개씩 반환한다.
- 문제: `q`가 있으면 SQL의 LIMIT을 제거하고 `.all()`로 후보를 전부 읽은 뒤 JavaScript에서 필터·slice한다. 실제 저장소 코드를 workerd/D1에 연결한 5,000곡 로컬 실험에서 모두 25곡을 반환했지만 읽기 수가 아래처럼 달랐다.

| 요청 | 반환 곡 | SQL 수 | D1 rowsRead | rowsWritten |
| --- | ---: | ---: | ---: | ---: |
| 일반 목록 `limit=25&scope=all` | 25 | 13 | 659 | 0 |
| 검색 목록 `limit=25&scope=all&q=Cost` | 25 | 13 | 10,607 | 0 |
| 곡 선택기 `limit=25&lookup=songs&q=Cost` | 25 | 7 | 5,254 | 0 |

- 최소 수정: 기존 저장소의 검색에서 정렬 키 기준으로 후보를 제한해 읽고 Unicode 최종 검증 후 필요한 26개를 채우면 멈춘다. 곡의 정확 일치 여부는 별도의 좁은 존재 조회로 보존한다. SQL에 단순 LIMIT만 먼저 추가하면 기존 구두점/Unicode·페이지 밖 정확 일치 계약이 깨지므로 그 방식은 피해야 한다.
- 미수정 영향: 많은 곡에 일치하는 검색어를 입력할 때 응답 크기는 작아도 읽기 비용과 후보 메모리가 카탈로그 크기에 비례한다. 이 실험의 검색 목록 읽기는 일반 목록의 약16.1배다. 운영 빈도·지연·실제 과금 초과는 측정하지 않았다.

## 실행한 검증

- 기존 `catalog-pickers.test.tsx` 7개 + `review-catalog-changes.test.ts` 5개, 총12개 PASS. 이 통과가 위 관리자 선택 보완의 실패/버전 조합을 검증하는 것은 아니다.
- 실제 `OtwPlayCatalogManager`와 실제 TanStack Query를 렌더링한 임시 진단2개에서 위 1·2번을 관측했다. 화면과 query 상태를 함께 확인했다. API만 통제한 UI 재현이며 운영 브라우저 검증은 아니다. 진단 테스트의 PASS는 문제를 재현했다는 뜻이며 결함 해결 판정이 아니다.
- Worker Vitest 진단은 cloudflare-pool runner 시작 시간 초과로2회 중단, 실행 테스트0. 이 시도들을 PASS로 계산하지 않았다.
- 대안으로 설치된 Wrangler가 사용하는 Miniflare/workerd와 직전 작업의 격리된 전체148 migration 로컬 DB를 사용해 **현행 D1AdminCatalogRepository**와 `meterD1`를 직접 호출했다. 5,000곡·5,000가창은 검증 DB에만 fixture로 추가했다. 해당 세 조회는 모두 실제 D1이며 추가 쓰기0을 확인했다. HTTP 인증·네트워크 비용까지 측정한 것은 아니다.
- 임시 진단·로그·실행 설정은 작업 트리의 ignored `.tmp/review2/`에만 있다. `ui-focused.log`, `existing.log`, `d1-direct-measured.log`가 실제 근거다. 제품·정식 테스트·정식 Vitest 설정의 변경은 없다.

## 개선 방향과 판정

기존 `use-admin-catalog.ts`에 선택 보완, version 병합, 준비·오류 상태의 소유권을 모으는 것이 우선이다. 새 통과 계층을 추가하거나 항상 전체 카탈로그를 읽도록 되돌릴 필요는 없다. 서버 검색의 후보 읽기 제한은 같은 API/저장소 안에서 별도로 보강할 수 있다. 전체 게시 준비는 기존의 명시적 fresh 전체 조회·오류 표시·확인 후 실행을 유지한다. DTO의 선택 필드 자체만으로 별도 결함을 주장하지 않는다.

**판정: 1·2번 우선 수정. 3번의 검색 비용도 보강 필요.** 수정과 영구 회귀 테스트 추가는 이번 요청 범위에 포함하지 않았다.

운영 브라우저·운영 D1 사용량·동시 관리자 실부하·전체 preflight는 미검증이다. 운영 요청/쓰기·배포·중지된 자동화 재개·유료 AI 실행은 없었다. 기존 로컬 개발 DB와 이전 미커밋 변경을 보존했다.


## 후속 수정 — 2026-10-20

사용자의 세 문제 수정 승인에 따라 기존 조회 hook·저장소를 수정하고 영구 회귀 테스트를 추가했다. 높은 version/최신 revision의 내용과 기존 페이지 순서를 함께 유지하고, 선택 조회 실패의 명시적 재시도를 제공한다. 5,000곡에서 검색 읽기10,607→659행, 곡 선택5,254→283행·쓰기0행이다. 화면 핵심3개와 실제 네이티브 D1 검색6개가 통과했다. 독립 검토에서 확인한 새 페이지 순서 회귀도 수정했다. 최종 검사·실행 제한은 작업 트리의 `docs/reports/sul-36/2026-10-20-play-catalog-query.md`가 소유한다. 위 내용은 수정 전 검토 기록이다.

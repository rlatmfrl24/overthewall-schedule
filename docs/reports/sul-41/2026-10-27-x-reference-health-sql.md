# X 관리자 참조 상태 SQL 읽기 최적화

## 원인과 변경

UTC10/26의 별도 query 집계에서 관리자 답글·인용 상태 SQL 한 개가 읽기1,531,355행/268호출을 기록했다. 이는 webhook 수신이나 정규 REST 수집의 직접 비용이 아니다. `useXReferenceHealth` → 관리자 `GET /api/x/history/health` → `readXHistoryHealth` → `readXReferenceHealthCounts`의 누적 집계다.

기존 SQL은 전체 참조·게시물의 연결 결과를 세 분기에서 다시 읽었다. 먼저 상태·오류·답글 표시별 COUNT/MIN을 materialize하고, 원문/작성자/답글 분기는 압축된 집계를 재사용하도록 바꿨다. 마지막 SUM/MIN과 정렬, DTO reducer는 유지한다. 날짜·source LIMIT로 총계를 줄이지 않는다.

변경은 읽기 SQL과 회귀 테스트에 한정한다. API/관리자 권한·숨김/삭제 제외·공개/보관/공유 소유자·빙하유 정책, 60초 상태 조회·24시간 REST 및 다른 주기 설정을 변경하지 않는다. 캐시·인덱스·마이그레이션·계측 쓰기를 추가하지 않는다. 계정 전체 UTC일5M행/배경4M 및 더 엄격한 제한, Play/AI 중지를 유지한다.

## 로컬 비용과 검증

Node24.20.0/pnpm11.7.0, `vitest.all.config.ts`의 실제 workerd 로컬 D1에서 같은2,000개 quote(원문/작성자 동시 대기) fixture로 비교했다. fixture 쓰기와 EXPLAIN은 조회 계측에서 제외했다.

| 지표 | 변경 전 | 변경 후 |
|---|---:|---:|
| 조회 수 | 1 | 1 |
| 실제 rows_read | 14,003 | 6,005 |
| 실제 rows_written | 0 | 0 |

해당 fixture 읽기57.12% 감소다. 무관한 게시물 이력10,000개를 추가해도 비용과 결과가 같다. 운영 하루 절감률이나 UTC10/26의1.53M행 감소량으로 환산하지 않는다. 정확한 누적 총계를 위해 참조 이력 읽기는 남으며, 상태·오류 조합 수와 데이터 분포에 따라 비용이 달라진다.

- 회귀 테스트를 먼저 실행해 기존14,003행이 읽기 예산10,000행 미만 조건에서 실패함을 확인했다.
- 독립 리뷰에서 완료된 quote2,000개 경로가2,004→8,003행으로 늘어나는 중간 구현의 성능 회귀를 발견했다. 실패하는 회귀 테스트를 추가하고, 분기 대상 참조만 먼저 거른 뒤 parent PK를 읽도록 보완했다. 최종2,005행으로 기존대비추가1행이며 쓰기는0이다.
- 비용·원문/작성자 중복 대기·NULL시각·terminal/오류·답글 미리보기·잘못된JSON·숨김/삭제 제외를 검증했다. 기존49개 보강통합검증과 신규3개 회귀가 대상이며 최종 결과는 PR evidence에 남긴다.
- 최종 독립 리뷰·preflight·현재 PR HEAD의 CI 근거는 PR evidence 댓글에 기록한다. 본 문서만으로 미실행 검증의 PASS를 주장하지 않는다.

다음 완전한 UTC10/28 하루의 자연 webhook/24시간 REST 관측은 별도 읽기 전용 예약이다. 이 SQL PR이 운영에 반영되기 전에는 기존 SQL의 비용이 계속 포함된다. 운영 D1/업무 API·강제 수집·설정 변경·병합·배포는 이번 SQL 구현에서 실행하지 않는다.

# REST 예산 이월 확인·구독 목록 사이트 범위 수정

사용자는 유료 테스트 없이 정기 REST의 부분 처리/이월을 확인하고, LuvDia의 과거 실패 표시를 설명하며 구독 설정의 OTW 멤버 혼입을 수정하도록 요청했다. 기존 예산·자동충전·과거 원장·커서는 유지한다.

## 확인한 동작

정기 planner가 활성 멤버를4명 이하 shard로 계획하고 실행기는 계정별 요청을 공통 게이트에 보낸다. 각 요청의 원자적 예약을 통과한 계정은 처리하며, 전체 첫 요청 예상 합계를 일괄 예약하거나 합계 부족으로 실행 전체를 차단하지 않는다. 처리 순서는 저비용 계정 우선순위를 보장하지 않는다. 콜드 사용자 캐시의 선행 조회·사이트 한도·다른 보호 조건도 영향을 준다.

성공한 페이지는 저장 후 확인하고, 예산 차단은 마지막 완료 위치와 기존 pagination token을 보존한다. 미처리 계정은 기존 위치부터, 이월 페이지는 기존 token/base부터 이어진다. 공통 예산은 UTC 일자(한국09:00)가 바뀌면 갱신되지만 정기 REST는 기존24시간 cadence의 다음 실행을 기다린다. 웹훅 등 동시 비용 때문에 다음 날 모두 완료된다는 보장은 없다.

현재 운영의 다음 자격은10월27일13:53 KST 이후 첫 정기 실행이며 당일09:00 예산 갱신 이후다. 현재 UTC26일 잔여$0.640 경고를 그 시각의 예산으로 고정 해석하면 안 된다.

08:32 KST readback에서 LuvDia 최신 REST291은10월26일13:53 `shared_budget_unavailable`, API0·비용0·저장0이다.14:26 공통 장부 준비 전의 실패이며 이후 REST 실행이 없어 현재 ‘실패 포함’으로 남는다. 현재 웹훅 처리 장애나 새 차감이 아니다. 성공으로 덮어쓰지 않는다. OTW2852/2853과 설정24시간·100센트·최적화 허용·완료 위치도 보존되어 있다. 공통 장부$0.360/예약0/목표$1, 계정 D1 읽기2,940,659(<배경4M), 관측SQL쓰기0이다.

## 원인과 최소 수정

실제 LuvDia 관리자→X 수집→X 신규 피드 구독의 멤버별 table에 Luv3·OTW5가 모두 표시됐다. 공통 coordinator의 `status(site)`가 멤버 목록을 사이트 필터 없이 반환하는 것이 원인이다.

`subscriptions` 배열을 요청 사이트로 제한하고 계약 주석과 표 제목에 그 범위를 명시한다. 공통 고유 활성 수·사이트별 집계는 유지한다. 구독 등록/삭제·수집·예산 예약·정산·정기 주기 코드는 변경하지 않는다.

## 검증

동일 D1의 양 사이트 활성화 후 각 응답의 멤버 목록이1명이어야 하는 회귀가 기존 코드에서 실패(1 FAIL/27 PASS)했다. 수정 후28건 PASS다. 기존 UI9건과 타입·변경 린트·구조 검사도 통과했다.

전체 schema를 쓰는 기존 cadence 통합 파일에 실제 planner→repository→executor→finalizer 경로의 회귀를 추가했다. 한 요청분만 남은 예산에서1계정 저장·다른 계정 차단과 원래 위치 보존, 다음 UTC 자정 직후 cadence 미도래,24시간 후 미처리 범위 저장·중복 없는2건·당일 정산을 확인했다. 해당 파일27건 PASS이며 관련 총64건이다. 기존 pagination 중단/다음 날 재개 회귀도 함께 통과했다. 이 검증은 로컬 D1과 차단된 외부 응답을 사용하며 추가 유료 호출은 없다.

## 운영 반영 완료

[PR198](https://github.com/rlatmfrl24/overthewall-schedule/pull/198)의 최종 HEAD `0de86e0d25c89dd34ad862b00f3a952a1f8b2a12`의 CI/보안 검사와 정적 검토를 통과하고 `74b47386005c32941d5b7d1b46ec02365a8f77c9`로 병합했다. 같은 병합 소스의 LuvDia 정상 빌드·배포는 소스/Clerk/계측 보호·원격 D1 doctor를 통과했다.

첫 OTW 병합 CI `19cacf63-b59d-4230-a2e9-1b7d03d7f952`는 기존 동시 미디어 재사용 회귀1건의5초 시간초과로 FAIL이었다(3330 PASS·3 SKIP). 데이터 단언 실패는 없으며 같은 커밋·동일5초 제한의 해당 케이스 선별 재검증은510ms PASS였다. 정확한 CI 지연 원인은 미확정이다. 제품·테스트·시간 제한을 바꾸지 않고 정상 빌드를1회 재시도한 `ff6462a9-5f90-40d6-880e-ecc6013ddeeb`는400파일3331 PASS/기존3 SKIP과 정상 배포를 완료했다. 이전 FAIL과 후속 PASS는 PR 댓글에 함께 보존했다. OTW 수동 중복 배포를 하지 않았다.

실제 배포 로그의 commit은 양 사이트 모두 `74b47386`이며 활성 버전은 OTW `536d8fce-a13a-4477-9b5e-2cfbb7257693`, LuvDia `a6fdd12b-48c7-4256-a8ce-3a4fa9b25dfa`다. 양 사이트의 정상 관리자 수집→X→X 신규 피드 구독에서 새 표 제목과 OTW5명·LuvDia3명만의 멤버 목록을 확인했다. 공통8집계와 각 웹훅 정상 표시는 유지됐다. REST는 여전히10월26일13:53의 과거 실패와10월27일13:53 이후 자격을 정확히 표시한다.

배포 후 authoritative readback에서 양 사이트의 설정·REST 완료 위치/커서 유무·최근 실행 원장이08:32 baseline과 동일했다. UTC26 사용360,000/예약0 원장과 UTC27 사용0/예약0/목표1,000,000을 함께 읽어 일자 갱신과 이력 보존을 확인했다. 관측SQL쓰기0이며 새 UTC일의 계정 D1 읽기4,099는 배경4M 아래다. 추가 유료 X 조회·강제 REST·구독 제어·자동충전 변경은 없었다.

멤버 목록 수정은 실제 운영 주 화면으로 확인했다. 예산 차단 후 다음 날 재개는 코드·로컬 D1의 정상 스케줄러 실행으로 확인했고 운영의 유료 재개 시나리오는 실행하지 않았다. 저비용 계정 우선이나 다음 날 전체 완료를 보장하지 않으며, 당시 잔여액과 기존 보호 조건에 따라 요청별로 처리한다.

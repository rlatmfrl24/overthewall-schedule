# SUL-31 구현 및 검증 결과

2026-09-23 · 기준 commit `4e8daa61492a6ea42e82da3d7ca7885038314e1d` · Node 24.20.0

## 결과와 범위

관리자 가져오기 → 검수 → Ready 저장 → 임시 등록 → 게시 경로를 유지했다.
동일한 500개 워크로드에서 로컬 workerd D1 `rows_read`가 **6,927,563 → 583,049행 (91.58% 감소)**으로 줄었다.
이는 운영 측정값이 아니다. 운영 배포와 동일 작업의 Insights 재측정은 아직 수행하지 않았다.

- 단일 곡·주체·채널·가창의 검증 및 저장 결과를 필요한 ID와 연결 데이터로 한정했다.
- 변경 곡의 gram 키만 통계에서 감소시키고, 신규 곡의 감소와 게시·철회의 projection 재생성을 제거했다.
- Queue 내부 작업 조회에서 관리자 통계를 분리했다. 관리자 통계는 선택한 작업의 후보를 한 번 분류해 집계한다.
- 검수 목록은 출처·이력·종류·상태와 커서를 적용한 51개 ID에만 상세 정보를 붙인다.
- 자동 수집 출처 `candidate_id`, 플레이리스트 출처 `(job_id, candidate_id)` 인덱스를 추가했다.
- AI 시작은 멤버 정보, 결과 해석은 곡·주체 정보만 읽는다. 모델 입력과 검수 정책은 유지했다.
- 숨긴 화면·완료 작업의 주기 조회, 편집 중 목록 갱신, 전체 Play 캐시 무효화를 줄였다.
- Ready 응답의 `catalogChanges`를 캐시에 병합한다. 동시 revision이 누락된 캐시를 최신 전체 스냅샷으로 인증하지 않는다.
- 무한 목록을 갱신할 때 첫 페이지부터 커서를 다시 계산한다. 방문한 미저장 검수 폼은 유지한다.

5,000개 사례는 수집 5,000개와 검수·등록·게시 1개를 측정했다. 5,000개 전체 게시 수치가 아니다.
별도 단일 곡 수정은 50/500/5,000 배경 곡에서 각각 **661/704/704행**, Ready 저장은 **218/256/264행**을 읽었다.
무관한 카탈로그 크기에 비례하는 단일 저장 비용 증가는 관찰하지 못했다.

측정은 실제 SQL을 실행하는 임시 workerd D1에서 `meta.rows_read`, `rows_written`를 수집했다.
쓰기 SQL이 유발한 읽기도 포함했다. seed와 EXPLAIN 비용은 제외했다.
YouTube 응답은 재현 가능한 합성 관측값을 사용했으며 실제 외부 API 호출·관리자 UI 검증은 아래 별도 증거로 구분한다.
50 → 500 → 5,000 배경 곡을 순차 확장하면서 앞 단계 생성 데이터는 보존했다.
각 후보는 승인 채널·동일 가창자와 새로운 곡을 사용한다. 운영 데이터의 모든 분포를 대표한다고 보장하지 않는다.
양쪽 비교에 동일한 0097 인덱스를 적용했으므로 새 인덱스 자체의 이득은 비교 수치에 포함시키지 않았다.

기준 commit의 두 서비스와 두 repository, projection 구현을 임시 파일로 복원해 동일 워크로드를 실행했다.
`DELETE/UPDATE music_search_gram_stats` 실행계획이 전체 `SCAN`에서 `(gram_size, normalized_gram)` 인덱스 `SEARCH`로 바뀌었다.

재현: Node 24.20.0 환경에서 `node scripts/benchmark-otw-play-reads.mjs`.
결과는 `.tmp/sul31-read-benchmark`에 기록한다. 기존 로컬·운영 DB를 변경하지 않으며, 임시 기준 구현은 종료 시 제거한다.

## 예산 계약

- `GET /api/play/admin/imports/budget`: 관리자 인증, `no-store`, 상태·행 수·기준·관측 시각·UTC 초기화 시각·사유.
- `POST /api/play/admin/imports/:jobId/resume`: 실행 가능한 해당 작업 pending 메시지만 재전송한다. 차단 시 `429`, `Retry-After`, `data.budget.resetAt`을 반환한다.
- 기존 `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_D1_TOKEN`으로 Analytics GraphQL에서 계정 전체 UTC 당일 `rowsRead`를 읽는다. DB별 필터를 사용하지 않는다.
- `OTW_PLAY_D1_READ_DAILY_TARGET` 기본값은 4,000,000이다. 계정·UTC 날짜·설정값별 60초 캐시이며 오래된 관측을 재사용하지 않는다. 측정 장애는 사용량 0이 아닌 `unavailable`과 경고 후 진행으로 처리한다.
- 새 작업은 사전 검증과 DB 저장 성공 후에만 접수한다. 차단 중에는 job과 pending 메시지를 보존하고 Queue로 보내지 않는다.
- 전달된 Queue 메시지는 차단 중 성공 반환하여 ACK한다. pending·재개 위치·attempts·오류·partial 상태를 변경하지 않는다.
- 수동 Ready·카탈로그·일괄 등록·AI 검수에는 수집 예산을 적용하지 않는다.
- 기존 매시 03분 `ingestion_recovery`, 자동화 pause·예약 설정·쓰기 guard를 유지한다. 별도 D1 예산 원장·대기 테이블·상태를 추가하지 않았다.
- 숨긴 화면에서는 예산 polling을 멈추고, 보이는 예산 대기 화면에서는 빠른 작업 polling 대신 예산을 60초 간격으로 확인한다.

Analytics 지연, 장애 시 진행 정책, 다른 기능의 사용량 때문에 계정 Free 한도 미초과를 절대 보장하지 않는다.

## 검증과 남은 적용

- 변경 범위 서비스·HTTP·Queue·관리자 UI·Query 캐시 회귀 테스트 통과.
- D1 catalog/ingestion/AI 통합 테스트 52개 통과: 동일 ID 재사용, CAS 충돌, 중복 수집, 부분 실패, rollback, 곡 이동, 검색 통계 무결성 포함.
- 예산 경계·UTC 날짜 교체·오래된 값·측정 오류·보류 저장 실패·중복 전달·수동/자동 재개·보류 중 Ready 허용 테스트 통과.
- 50/500/5,000 비용 비교와 단일 Ready/곡 수정 비용 증가 상한 테스트 통과.
- test/Worker/Node 타입 검사, TypeScript 프로젝트 빌드, Vite 빌드, SEO 생성, 변경 파일 lint, architecture, agent mirror 검사 통과.
- 임시 D1에서 migration 97개 전체 적용 검증 통과. 기존 로컬 DB에는 0097 인덱스 migration만 증분 적용했다.
- 테스트 기대값은 지연 로딩과 완료 작업 조회 중단에 맞춰 갱신했다. CAS·게시 검증·인증·트랜잭션을 약화시키지 않았다.

운영에는 아직 반영하지 않았다. 운영 적용 시 인덱스 0097 → 호환 코드 배포 순서를 지키고,
계정 Analytics 조회 권한과 budget API 응답을 확인한 뒤 동일 500개 작업의 Insights를 비교해야 한다.
이번 결과는 UTC 당일 운영 사용량이나 계정 한도 보장의 증거가 아니다. 최근 24시간 약 589만 읽기라는 사전 관측과도 다른 지표다.

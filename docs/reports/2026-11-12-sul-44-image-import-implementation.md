# SUL-44 이미지 일정 입력 개발 기록

브랜치: `codex/sul-44-schedule-image-import` · 기준: `b51d99e5` · 환경: Node24.20.0 / pnpm11.7.0.

최신 후속 결과는 [상태 통합·점선 영역·전송 안내의 약관 이동](#2026-11-16-상태-통합점선-영역전송-안내의-약관-이동)을 따른다. 아래는 시점별 구현·검증 이력이며 초기 Luna·참조 정답·예산 누적을 현재 상태로 해석하지 않는다.

사용자가 D1~D7 확정 뒤 실행 계획에 따른 개발을 재개했다. 원래 작업 공간과 별도 Play 커밋은 보존하고 관리 작업 공간에서 개발한다. 이 기록은 실제 모델 품질이나 운영 적용 완료 보고가 아니다.

## 구현한 경로

- 일간·주간 스케쥴 추가 메뉴에서 직접 입력과 이미지 입력을 선택한다. 로그인 사용자는 파일 선택·끌어 놓기·붙여넣기, 원본 미리보기와 확대를 사용할 수 있다.
- 이미지 인식은 서버의 Luna Responses API와 입력 토큰 계산 API를 사용한다. Standard·추론 none, 입력50,000/출력12,000토큰, 업로드 후20초·재시도0회다. 형식·크기·로그인·사이트 예산·계정별 횟수/동시성을 검증한다. 별도 Play AI나 자동 수집을 활성화하지 않는다.
- 원본 대조 편집, 기준 주 확인·요일/자정 보정, 동일 인식 이름의 멤버 일괄 연결, 시간 미정, 빠진 일정 추가, 중복/미확인 제외, 기존 유지/수정 대상/새 추가 선택과 삭제 영향 추가 확인을 연결했다.
- 적용은 기존 일정 저장 SQL과 감사 기록을 공유하며 멤버·날짜별 원자 batch에 snapshot·현재 권한·삭제 확인·결과 receipt를 포함한다. 다른 묶음의 성공을 보존하고, 결과 유실은 확인 중으로 남긴다. 저장 후 조회만 재시도하며 모델을 재호출하지 않는다.
- 최소 결과는 사용자·사이트별로24시간 보관한다. 시각을 포함한 요청 ID의 만료를 검사해 오래된 재전송이 새 저장으로 바뀌지 않게 했다. 비용 예약 기록과 감사 이력의 수명은 구분한다.

## 확인한 증거

- 수정 범위60파일441건이 통과했다. 실제 D1의 예산 경합, 묶음 rollback, 중복 요청·24시간 만료·actor/site 격리, LuvDia 멤버 정책, 실제 JWT를 검증하는 정확 API 경로와 기존 비로그인 직접 입력을 포함한다. 합성/격리 검증이며 실제 모델 품질 증거가 아니다.
- 변경 소스44파일 ESLint가 통과했다. OTW·LuvDia 모두 정상 빌드와 산출물 manifest 검사를 통과했다. 앱/테스트/Worker/Node 타입 및 구조 검사도 통과했다. 독립 검토의 중요 지적3건을 아래와 같이 보완했다. 수정 후 전체 pnpm test에서428파일4,014건과 보조10건이 통과했다. 보완 후 OTW·LuvDia 빌드와 각 산출물 manifest도 다시 통과했다.
- 전체171건의 migration을 임시 D1에서 검증했다. 새 migration0171은 비용 예약·적용 결과2테이블과 인덱스만 생성하며 파괴적 SQL이 없다. 원격 적용은 하지 않았다.
- 실제 Chrome의 정상 일간·주간 진입점에서 메뉴·키보드 진입/ESC·초점 복귀, 로그인된 업로드 화면과 로컬 파일 미리보기, 닫은 뒤 원본 폐기/재진입 초기화,390×844와1280×900에서 수평 넘침 없음·새 콘솔 오류0건을 확인했다. 선택 파일은 저장소의 공개 이미지이며 인식 버튼은 누르지 않았다. 실제 모델→편집→저장 전체 흐름의 증거로 사용하지 않는다.
- 편집 검증에는 모델 경계 mock을 사용했다. 이미 읽은 초안의 한도 오류 후 사용, 부분 적용 뒤 성공 행 보존·다른 행 편집, 멤버 일괄 연결의 성공 행 보호, 삭제 확인과 제외 행 미전송을 검증했다.

## 독립 검토와 보완

검토 기준은 `b9aa9b4c`이며 새 검토자1명이 전체 브랜치를 읽었다. 중요 지적3건, 별도 경미 지적0건이었다. 재검토를 반복하지 않고 작성자가 한 번의 수정 단계에서 회귀를 먼저 실패시킨 뒤 보완했다.

1. **묶음의 수정 대상 삭제/누락:** 명시적으로 수정하는 모든 기존 ID를 같은 묶음의 부수 삭제에서 보존하도록 공통 저장 계획과 삭제 예상 계산을 맞췄다. 추가→수정과 수정→추가 양 순서에서 실제 D1의2건과 기존 ID 유지·삭제 이력0건을 확인했다. 각 선택 내용이 실제로 존재하는지도 영수증 생성 전 같은 트랜잭션에서 검사하며 조용한0행 UPDATE는 전체 취소한다. 수정으로 이전 값이 사라지는 대상은 최종 상태에 따라 중복을 다시 판단한다.
2. **실패 행의 멤버·날짜 변경 후 재시도 막힘:** 확정 실패 상태의 행이 다른 묶음으로 이동하면 이전 실패 요청을 해제하고 현재 멤버·날짜의 비교를 사용한다. 적용 완료/결과 불명 요청은 해제하지 않는다.409 후 날짜 변경과403 후 멤버 변경이 재인식 없이 적용되는 UI 회귀를 확인했다.
3. **응답 유실 재시도와 커밋 경합:** 사전 snapshot/권한 거절 경로에서도 같은 요청의 커밋 영수증을 다시 확인하고 본문 hash를 검증한다. 실제 D1에서 첫 영수증 조회와 context 조회 사이에 원래 요청을 커밋시켜 실제 결과 재사용·일정/감사 각1건을 확인했다. 권한 변경과 영수증 생성 경합도 검증했다.

초기 회귀10건이 실패했고 보완 후4파일32건이 통과했다. 수정 후 타입·구조·변경9파일 lint와 전체 pnpm test(428파일4,014건·보조10건)도 통과했다. 이는 실제 모델 품질 검증을 대신하지 않는다.

검토자가 판단을 보류한 실제 모델 품질/계정 호환성/외부 보관 설정/원격 적용은 계속 미검증으로 남긴다. 링크 입력·자동 수집·백필·자체 OCR은 확정 이미지 범위에 추가하지 않는다.

## 아직 확인하지 않은 것

- 실제 일정표 표본은0/30장이다. 사용자는 자료를 준비할 예정이라고 답했다. 유료 모델 호출0회이며 D7 인식95%, 속도5/10/20초, 작업 시간50% 단축, 실제 모델 기반 저장 일치 판정은 모두 미검증이다. Haiku 비교도 실행하지 않았다.
- 초기 검증에는 이미지 인식 전용 서버 키 `SCHEDULE_IMAGE_OPENAI_API_KEY`를 설정하지 않았다. 후속 지시로 사용자가 OTW 로컬 키를 입력했고 서버 전용 실행 설정 일치와 OpenAI의 `gpt-6-luna` 모델 조회 HTTP200을 확인했다. 이미지 인식 요청은0회이며 실제 인식·정형 출력·저장 흐름을 확인한 것은 아니다. LuvDia 키와 운영 설정은 변경하지 않았다. 키가 없으면 비용 예약 전에503으로 안내한다. 운영자는 각 사이트의 서버 비밀값으로 키를 준비하고, 로컬은 해당 사이트의 무시되는 환경 파일에 둔다. `VITE_*`나 브라우저 코드에 넣지 않는다.
- 새 로컬 DB의 일반 증분 migration은 기존0030의 멤버 bootstrap 의존성 때문에 실패했다. 이 작업에서 만든 부분 상태만 백업하고 canonical reset으로 전체 검증 DB를 생성했다. fixture seed는 그 새 DB의 migration 기본값5건 때문에 비강제로 거절되어 새 로컬 fixture에만 강제 seed를 사용했다. 기존 사용자 DB는 변경하지 않았다.
- 초기 로컬 doctor는 기존 fixture의 `youtube_api_daily_quota_units` 누락으로 실패했다. 이후 사용자의 복원 지시로 로컬 초기 데이터에 `'1000'`을 추가하고 현재 작업 공간의 OTW 로컬 DB에도 누락된 설정 한 건만 복원했다. DB에서 값1000과 기존 설정11건의 동일성을 확인했으며 `pnpm d1:doctor`는 차단 실패 없이 통과했다. 관련 기존 검사2파일23건도 통과했다. 초기 데이터를 다시 덮어쓰거나 운영 DB를 변경하지 않았고 YouTube 수집을 실행하지 않았다.
- 원격 DB·유료 실험·Git 게시·PR·병합·배포·운영 preflight는 실행하지 않았다.

## 진행 중 정한 사항

1. 개발 재개는 로컬 코드·검증·계획 커밋으로 해석하고 유료 실험/원격 보류를 유지했다. 잘못 해석했다면 품질 실측 시작이 늦어지는 비용이 있다.
2. 기존 D1ScheduleWriteRepository의 저장 문장 생성부를 공유하는 원자 적용을 택했다. 동일 정책 권위를 보존하며, 잘못된 비교는 덮어쓰기 대신 묶음 거절과 사용자 재확인으로 이어진다.
3. 비용은 정수 nano-USD와 캐시 쓰기1.25배를 포함한 보수적 예약/사용 토큰 정산을 사용한다. 불명 비용을 보존하며 실제 청구액보다 일찍 한도에 도달할 수 있다.
4. 적용 ID는 시각+UUID로 정하고 actor/site에 한정했다. 만료 후 새 쓰기 우회를 막으며 기기 시각이 크게 틀리면 새 요청이 필요하다.
5. 편집 UI가 빈 저장 경로에 의존하지 않도록 Task3을 Task2보다 먼저 구현했다. 정책은 같고 연결 순서만 바뀐다.
6. 모르는 멤버 이름은 초안 전체 거부 대신 UID 미지정으로 보존한다. 임의 ID는 수용하지 않으며 사용자의 추가 확인이 필요하다.
7. 새 로컬 DB의 기존 migration 의존성은 canonical 초기화 절차로 처리했다. 이 작업의 부분 로컬 상태는 복원 가능하게 백업했고 원본 작업 공간은 보존했다.

8. 편집창의 예시 onApply 콜백 대신 schedules 기능 내부의 실제 API/use-case를 사용하고 메뉴가 mount/폐기를 소유하게 했다. 입력과 적용의 권위가 한 기능에 남으며, 부모 화면의 별도 적용 사용자화가 필요해지면 연결 변경 비용이 있다.

9. 실제 모델 품질·계정 호환성·외부 보관 설정·원격 운영은 검토 범위에서 판단하지 못한 것으로 남긴다. 사용자 보류를 품질 보장으로 바꾸지 않으며 실제 실험에서 추가 문제가 발견될 수 있다.
10. 링크 입력·자동 수집·백필·자체 OCR은 이미지 기능에 편입하지 않는다. 필요한 경우 별도 설계가 남는다.

## 실제 이미지 1장 검증과 Luna low 비교 (후속 지시)

사용자가 현재 업로드한 이미지의 실제 인식·편집·로컬 적용을 요청하고 운영 DB 변경을 금지했다. 이후 문자 인식 품질 문제를 제기했으며 Luna low로 같은 이미지 1회 비교를 명시적으로 승인했다. 이 승인은 이 이미지의 개발 확인 범위이며 30장 D7 실험이나 기본 설정의 영구 변경 승인이 아니다.

- 실제 화면에서 서버 오류를 재현했다. 입력 토큰 요청 전에 native fetch를 클래스 메서드처럼 호출해 Worker가 Illegal invocation 오류를 냈다. fetch를 globalThis에 바인딩하는 한 줄 수정으로 정상 연결했고, 같은 호출 규칙을 재현한 회귀가 실패한 뒤 통과했다. [Cloudflare의 해당 오류 설명](https://developers.cloudflare.com/workers/observability/errors/#illegal-invocation-errors)과 실제 실행 오류가 일치했다. 일시 진단 코드는 모두 제거했으며 키·이미지·원시 모델 응답은 로그에 남기지 않았다.
- 모델 입력은 사용자가 화면에 올린 850×478 이미지다. 처음 화면 갱신으로 메모리 이미지가 해제됐지만 사용자가 다시 올린 동일 일정표로 실제 결과를 확인했다. 원본 크게 보기의 blob 탐색은 자동화 브라우저 정책으로 제한되어 우회하지 않고 기존 화면의 원본 미리보기에서 대조했다.
- 원본에 없는 Local Sora를 원문 이름으로 생성하고 시간 있는 5행의 상태를 비운 결과를 확인했다. 모델에 로컬 멤버 이름을 제시하는 부분을 제거하고 원문에 보이는 이름만 추출하도록 보완했다. 명시적 시간은 방송, OFF는 휴방으로 읽고 원문 제목을 임의 완성하지 않도록 지시했다. 보완 후 7행의 방송/휴방이 채워졌고 이름은 미확인으로 남겨 사용자가 실제 로컬 멤버와 연결할 수 있었다.
- 같은 지시의 none과 low를 각 1회 비교했다. low는 일부 글자를 개선했지만 작은 제목의 오독·부제 누락이 남았다. 예를 들어 none의 ‘퍼리 쉬는 룸!’은 low에서 ‘테리 쉬는 중!’으로 달라졌고, 15일 제목은 두 결과에서 서로 다른 오독을 보였다. 제목 정확도 합격이나 95% 달성을 선언하지 않는다. 기본 설정은 none으로 복원했으며 자동 전환·재시도와 추가 비교 호출은 없다.

## Flash-Lite minimal 기본 전환과 실제 로컬 검증 (후속 승인)

## 작은 글자 원본 해상도 읽기와 동일 이미지 재검증

사용자가 작은 글자 오독을 더 줄이도록 인식 방식을 개선하고 같은 이미지로 재검증하되 기존 비용 한도와 운영 DB 변경 금지를 유지하도록 요청했다. 기본 모델·minimal 추론·추출 프롬프트·JSON 필드·사용자 편집/명시적 적용 경계는 유지했다. 이미지 전송의 해상도 요청과 사전 계산만 변경했다.

### 근거와 변경

현재 구현이 원본1장을 `detail:high`로 보내고 있고, 실제 화면에서 작은 제목의 ‘룬/문’, ‘오버더월/오버더웰’ 오독이 반복된 것을 확인했다. Google 문서는 Gemini3 이미지 high에 약1,120토큰, 이미지별 ultra_high에 약2,240토큰을 배분한다고 설명한다. 따라서 시각 입력의 정보량을 늘려 글자 획을 보존하는 접근을 먼저 비교했다. 원본의 픽셀 자체가 늘거나 복원된다는 주장은 아니다. [Google 해상도·토큰](https://aistudio.google.com/docs/media-resolution?generate-content=true)

- OpenRouter 공개 OpenAPI의 `ChatContentImage.image_url.detail`은 `original`을 지원하며, 원본 해상도를 지원하지 않는 공급자는 high로 낮출 수 있다고 명시한다. 생성 요청을 **`detail:original`**로 바꾸고 기존 Google AI Studio pin·단가 상한·자동 전환 없음은 유지했다. [공개 OpenAPI](https://openrouter.ai/openapi.json)
- Google native `countTokens`에는 해당 이미지 part의 **`mediaResolution:{level:"MEDIA_RESOLUTION_ULTRA_HIGH"}`**를 넣었다. global high보다 이미지별 설정이 우선하며 ultra_high는 이미지별 설정으로만 지원된다. 생성 경로와 사전 계산의 토큰 수가 정확히 같다는 보장은 여전히 없으므로 전체50K 입력 예약·반환 사용량 검사도 유지한다. [이미지별 설정과 우선순위](https://aistudio.google.com/docs/media-resolution?generate-content=true#per-part-media-resolution)

### 실제 인식 경로와 최소 변경

정상 **주간표 → 스케쥴 추가 → 이미지로 스케쥴 추가하기 → 파일 선택 → 일정표 읽기** 흐름을 그대로 사용한다. 기본은 전체 이미지이며, 이미지에 그림이나 여백이 크면 **확대할 일정 영역**에서 왼쪽·오른쪽·위쪽·아래쪽을 선택할 수 있다. 영역 선택만으로 인식하거나 기존 초안을 지우지 않는다. 바꾸고 다시 읽으면 새 인식으로 계산된다는 안내를 유지한다.

- 브라우저에서 선택 영역을 겹치는4영역으로 나눠 실제 원본 픽셀을 최대2배 확대한다. 영역 간 중복은20%이며, 좌/우/상/하는 해당 방향60%를 잡아 경계를 일부 겹친다. 확대는 글자 관찰을 돕는 전처리이며 없는 픽셀을 복원한다는 의미가 아니다. 긴 변2048px, 무손실 PNG 한 장500KB 이내로 제한하고 초과하면 원본에서 축소해 다시 만든다. 취소·실패 시 canvas와 임시 URL을 해제한다. 새 의존성·AI 이미지 생성은 없다.

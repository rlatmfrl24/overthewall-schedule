# SUL-43 전체 리뷰 및 후속 교정

검토일: 2026-10-29 KST. 고정 기준: 36625f9265a8f6e097eddd4d0a67fc553000e49a. 사용자 승인에 따라 미커밋 작업 트리와 신규 파일까지 포함해 검토한 후 커밋·PR을 준비했다. 원격 master도 같은 기준임을 fetch로 확인했다. 병합·배포·추가 운영 데이터 정리는 범위 밖이다.

원본 [SUL-43](https://linear.app/sulfurbottom/issue/SUL-43/otw-play-문제-수정)은 재조회 시 Todo이며 설명은 가수 중복과 새곡 제안/승인 수정 두 항목, 댓글·연결 자료는 없었다. 이 채팅에서 승인된 구체적인 요구와 후속 수정 지시를 우선 적용했다. 규칙 준수와 요구사항 두 축은 별도의 새 컨텍스트 에이전트가 병렬로 정적 검토했다.

## Standards

문서화된 표준 위반0건, 수정이 필요한 중대한 코드 냄새0건이다.

- 외부 가수 이름/별칭 조회는 infrastructure에 모으고 기존 정규화·바인딩을 재사용한다. 복수 일치·보관 상태에서 실패하며 기존 revision batch·오류 변환·감사 경계를 유지한다.
- 회원 선택 레코드·삭제·역할 키에 ID를 보존한다. 관리자 자동 조회는 요청 세대·선택 제안·active/status/archive 조건을 유지한다.
- 두 인라인 수정 루프의 작은 조회 형태 반복은 생성·감사 처리가 서로 달라 별도 추상화를 추가할 정도의 Duplicated Code로 보지 않았다.
- 순서 교정 후에도 새 배열만 정렬하며 기존 identity 키·subject/역할 변환을 재사용한다. 별도 도메인 타입이나 resolver를 추가할 필요가 없다.

Standards 에이전트는 diff/규칙/호출부와 회귀 로그를 읽었으며 테스트·브라우저·운영 조회를 독립 재실행하지 않았다.

## Spec

최초 요구사항 미충족1건(P2)을 발견했고 수정 후 재리뷰에서 해소를 확인했다. 미해결 중대 지적은0건이다.

**P2 — 메모만 수정해도 참가자 저장 순서 변경.** 요구는 ‘생성·수정·초기화에서 ID·순서·역할을 보존’하는 것이다. 기존 선택 상태가 멤버/외부로 분리된 뒤 멤버→외부 순서로 재조립되어, 저장된 [외부A, 멤버, 외부B]가 메모 저장 때 [멤버, 외부A, 외부B]로 바뀌었다. baseline까지 재그룹화돼 미저장 판정에 드러나지 않았다.

수정 전 실제 API 요청 배열이 달라지는 실패 회귀를 관찰했다. 저장된 identity의 원래 순서를 별도 UI 상태로 보관하고 선택 배열을 그 순서로 구성했다. baseline과 최종 확인 화면도 동일한 순서를 사용한다. 새 identity는 기존 참가자 뒤에 배치하며 초기화에서 저장 순서를 지운다. 새 순서 편집 기능·API/서버 변경은 추가하지 않았다. 회원29건이 통과했고 Spec/Standards 두 축이 변경 부분을 재검토해 추가 중대 문제 없이 해소됐다고 판단했다.

직접 등록·이름 변경·곡/가창자 인라인·카탈로그/제안 승인·Ready의 중복 검증과 사전 revision/동일 batch CAS, 회원 ID 보존 및 관리자 조회/승인 경계에서 추가 요구 미충족이나 명백한 범위 확장은 발견하지 않았다.

Spec 에이전트의 최초 결론은 정적 분석이었으며, 아래 실패 회귀·실기·저장 검증은 주 에이전트가 별도로 수행했다.

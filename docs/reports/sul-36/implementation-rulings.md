# SUL-36 구현 중 기술 판단 기록

**2026-10-15 현행 우선 정책:** [실제 초기 서비스 개통 목표와 실행 기록](initial-service-launch.md)이 아래와 충돌하는 이전 조건을 대체한다. 10월 17일 KST 이내 개통을 우선하고 필수 원격 자원·초기 복사·Clerk/도메인·최초 수동 배포가 허용됐다. OTW 중단은 가능하며 Task 4.4 전체·실시간 인계·모든 자동화는 개통 선행 조건에서 제외한다.

상태: 코드·로컬 검증 진행 중. 이 기록은 운영 이관·배포·공개 승인이나 전체 구현 완료를 뜻하지 않는다.

사용자가 확정한 공통 코드, 사이트별 자원·회원 분리, 전체 기능·현재 보유 콘텐츠 승계, 무중단 전환 정책을 구현하면서 내린 판단을 시간순으로 기록한다. 각 항목에는 이유와 판단이 틀렸을 때의 재작업을 함께 적었다. 최신 코드 검증 상태는 [로컬 구현·검증 기록](./local-implementation-verification.md)을 따른다.

1. **현재 기능 브랜치와 작업 공간을 재사용한다.** 현재 작업 공간에서 진행하라는 실행 범위를 따른다. 초기에는 기존 변경을 모두 작업 문서로 보았으나, 이후 별도 AI 검수 문서·계획은 무관한 변경으로 확인하여 보존하고 모든 SUL 커밋에서 제외했다. 공간 분리가 필요했다면 미커밋 작업을 옮겨야 한다.

2. **LuvDia의 운영 `publicOrigin`은 도메인 입력 전까지 `null`이다.** 로컬 origin은 선택한 포트에서 공급한다. 임의 도메인을 넣지 않는다. origin 의존 소비자가 이 상태를 처리하지 못하면 해당 소비자를 수정해야 한다.

3. **Task1에서 LuvDia의 최소 로컬 설정을 함께 만든다.** 처음부터 두 번째 사이트의 지원 진입점이 필요하다. 전체 runtime 격리는 Task3에서 완성한다. 설정 형태가 맞지 않으면 후속 연결 전에 수정해야 한다.

4. **작업별 검사는 영향 범위에 맞추고, 전체 공통 검사는 마지막에 한 번 수행한다.** 저장소의 검증 규칙을 따른다. 놓친 공통 영향은 최종 검사에서 해결해야 하며, 부분 검사만으로 전체 완료를 선언하지 않는다.

5. **LuvDia의 기본 로컬 포트는 `5174`이며 Clerk 앱 identity를 명시한다.** 사이트별 `CLERK_ISSUER`는 publishable key가 가리키는 frontend API origin과 일치해야 한다. 일반 fallback은 없다. 입력이 잘못되면 실행이 거부되므로 운영자가 올바른 설정을 공급해야 한다.

6. **환경 파일은 `config/sites/<siteId>`에 둔다.** 기존 OTW 입력은 사이트 identity가 일치하는 명시적 OTW alias에서만 사용한다. 잘못된 파일 배치는 운영자가 수정해야 하며 상대 사이트 설정으로 대신 실행하지 않는다.

7. **SEO 생성 CLI에도 사이트 선택을 처음부터 전달한다.** 임시 wrapper 없이 최종 빌드 parameterization으로 연결한다. 인터페이스가 맞지 않으면 후속 작업의 의존 관계를 수정해야 한다.

8. **기존 LuvDia 로고와 `397love@gmail.com`을 사용하고 커뮤니티 링크는 비워 둔다.** 사용자 확정 입력을 그대로 반영한다. 변경이 필요하면 화면 자산·설정을 수정하며 데이터 변경은 필요하지 않다.

9. **Worker의 `configPath`를 위장하지 않는다.** 지원되는 사이트별 환경 또는 실제 생성된 로컬 설정으로 identity와 상대 경로 해석을 유지한다. 맞지 않으면 환경 준비를 추가로 수정해야 한다.

10. **reset·location·doctor·seed의 최소 사이트 선택 연결을 Task1에서 수행한다.** 두 사이트 모두 정상 지원 명령으로 새 로컬 상태에 접근할 수 있어야 한다. 후속 도구가 이 계약을 따르지 못하면 수정해야 하며 기존 로컬·원격 데이터는 건드리지 않는다.

11. **Task2에서 `getWorkerSiteDefinition(env)`의 최종 경계를 먼저 도입한다.** Worker SEO도 명시적 설정 identity가 필요하다. 자원 격리는 Task3에서 추가한다. 합성이 맞지 않으면 인터페이스를 수정해야 하며 host 기반 임시 선택을 넣지 않는다.

12. **두 사이트의 persistence root는 겹치지 않아야 한다.** 내부 `v3`·자원 alias와 실제 promotion·삭제·rollback 대상을 확인한다. 중첩 배치를 의도한 경우에도 별도 디렉터리로 바꿔야 한다.

13. **PNG 내보내기의 이미지 누락 문제는 정상 공통 흐름에서 최소 수정한다.** fixture에서만 우회하면 요청한 내보내기 기능의 증거가 되지 않는다. 기존 결함 수정이 포함되는 만큼 해당 회귀 검사가 필요하다.

14. **Task4를 다섯 개의 순차 구현·리뷰 범위로 나눈다.** schema·포착 기반, 전체 읽기 경계, 보존·파일, 저장·수집 인계, 도구·통합 검증 순서다. 원래 전체 범위는 유지한다. 분할이 비효율적이면 조정·리뷰 비용이 늘어난다.

15. **source 쓰기 차단 전에 target의 접수·인계 준비를 영속적으로 확인한다.** 인계 ACK와 provider 작업의 최종 결과를 구분하고, 완료 조건은 차단 이전의 유한한 접수 집합만 대상으로 한다. 잘못된 연결은 수집 공백·무기한 대기·늦은 저장 덮어쓰기를 만들 수 있어 수정해야 한다.

16. **세 사람의 식별자는 `bing_hayu`, `u_lili`, `yang_mei`라는 code이며 숫자 UID가 아니다.** 각 code는 source에서 정확히 하나의 `members.uid`로 해석하고 승인된 target UID mapping을 사용한다. 없거나 중복이면 conflict다. 잘못된 원본은 명시적으로 분류해야 하며 roster를 추가하거나 identity를 바꾸지 않는다.

17. **새로 생성하고 아직 적용하지 않은 migration만 안전하게 다시 생성한다.** 자동 rebuild가 기존 FK 관계를 지울 수 있으므로 additive expansion과 constraint·nullable 변환을 나눠 실제 보존·rollback을 확인한다. 안전성 증거가 부족하면 새 산출물을 다시 만들어야 한다. 기존 번호 SQL·applied 기록은 수정하지 않는다.

18. **최종 canonical schema 생성은 유지하되 새 미적용 SQL의 생성기 결함만 교정한다.** FK-safe backup·rebuild·restore, 없는 새 열의 복사, 잘못된 DESC quoting을 교정하고 실제 populated D1과 no-diff snapshot을 확인한다. 불일치가 남으면 새 산출물을 거부하고 다시 생성해야 한다.

19. **`content_access`는 사이트 내부 정책으로 이관 business image에서 제외한다.** 새 LuvDia 자료는 기존 공개·회원·관리자 제한을 유지한 정상 접근 상태로 생성하고 OTW 원본만 `admin_archive`로 바꾼다. 기존 target·재개 자료의 정책을 임의 초기화하지 않는다. mapping이 틀리면 import 전에 고쳐야 한다. 차단 뒤 source의 접근 정책 변경 권한도 business 수정 우회가 될 수 없다.

20. **D1의 실제 compound SELECT 한도에 맞춰 고정 SQL branch를 나눈다.** business 변경·포착·receipt의 단일 transaction은 유지한다. 생성 크기와 canonical closure·cascade·rollback을 검증한다. runtime 한도나 비용이 맞지 않으면 후속 작업 전에 mechanism을 수정해야 한다.

21. **baseline은 승인된 source boundary·digest에 묶인 비활성 staging과 제한된 페이지 설치로 처리한다.** 전체 row·hash·checkpoint의 실제 확인 뒤 영속 receipt를 만든다. 일반 business delta replay는 원자적으로 유지한다. 불완전 staging이나 불일치가 있으면 활성화를 거부하고 복구해야 한다.

22. **45행 같은 임의의 일반 변경 제한을 제품 계약으로 넣지 않는다.** 최종 replay persistence에서 최소 statement grouping을 구현하고 45행을 넘는 실제 committed delta를 확인한다. 지원 runtime·producer 규모가 맞지 않으면 그 한계와 필요한 조치를 밝혀야 한다. 실제 계정 요금제·한도·운영 부하는 별도 확인 대상이다.

23. **차단 전 새 분류 ambiguity는 인계만 막고 source 운영은 계속한다.** 수집·접수·business commit을 일괄 중지하지 않는다. 두 guard가 잘못 결합됐다면 무중단 계약을 지키도록 수정해야 한다.

24. **차단 전 분류 수정은 정확한 parent digest·CAS·target 승인에 묶인 append-only revision으로 허용한다.** 기존 결정·UID·자원·schema·generation과 원래 baseline header·hash는 유지한다. 새 closure 포착·stale readiness 무효화도 원자적이다. lineage가 틀리면 인계를 거부하고 복구해야 하며 차단 뒤 revision이나 일반 manifest 수정은 허용하지 않는다.

25. **파일 관측·최종 disposition·참조 proof의 영속 계약은 Task4.1에서 확정한다.** 실제 R2 byte·hash adapter는 Task4.3, 인증된 전달은 Task4.4에서 연결한다. 계약이 틀리면 누락·stale·mismatch receipt를 거부해야 한다. 파일 포함 활성화의 거부 검사는 성공한 파일 이관의 증거가 아니다.

26. **유효한 원본 행의 증가를 2MB adjacency aggregate로 제한하지 않는다.** relational edge row와 분할 SQL로 aggregate-string 병목을 제거하고 실제 D1에서 확인한다. 영향을 받은 root만 읽고 변경분만 쓰는 원자적 포착을 유지한다. 플랫폼 비용·한도가 맞지 않으면 추가 증거와 수정이 필요하다.

27. **버전이 있는 source shape·reference 선언에서 인계 전용 SQL 검증을 생성한다.** protect·fence와 같은 원자적 boundary에서 검증하며 정책을 따로 중복 작성하지 않는다. 검증과 projector가 다르면 수정해야 한다. target이 항상 source 최신 tail과 같아야 한다는 조건은 추가하지 않는다.

28. **다른 사람의 역사적 identity는 승인된 baseline·이전 committed image의 실제 사실에서 만든다.** 기존 canonical entity를 우선 사용하고 없으면 추적 가능한 비관리 external persona를 같은 projector에서 만든다. 첫 binding은 유지하고 이후 canonical 출현·삭제를 참조와 함께 반영한다. 누락·ambiguity는 인계 conflict이며 이름만으로 merge하거나 네 번째 roster를 만들지 않는다.

29. **전달 command는 명시적 codec ID·version과 owning validator로 검증한다.** source sanitize·projection 뒤 target에서도 positive reparse한다. raw `Record`·type brand·cast를 전달 권한으로 삼지 않는다. 맞지 않으면 receiver가 거부하며 남은 실제 producer 연결은 Task4.4에서 완성한다.

30. **entity·alias unique conflict를 차단 전에 확인한다.** canonical JS Unicode normalization을 SQL로 그대로 재현할 수 없는 값만 내부 source fact receipt를 사용하며 정확한 sealed 입력·protocol·revision·generation·mapping·현재 fact set에 묶는다. stale·위조·누락 proof는 인계를 거부한다. 이름 기반 merge나 business 변경마다의 관측용 쓰기를 추가하지 않는다.

31. **현재 상태뿐 아니라 원래 승인된 baseline과 replay에 필요한 모든 image가 표현 가능해야 한다.** 나중의 이름 수정·필드 삭제로 과거 승인 image를 바꾸지 않는다. 본질적으로 충돌하는 baseline은 정확한 boundary·table·PK·이유를 표시하고 source를 계속 운영한다. 일반 reset·rebaseline·merge API는 넣지 않는다. 해당 경우에는 후속으로 검토된 baseline·identity 처분 결정이 필요하다.

32. **최종 인계 proof는 실제 저장된 source fence와 sequence seal에서 만든다.** 초기에 받은 envelope나 caller flag로 최종 인계를 완료 처리하지 않는다. target의 이미 진행된 operation·file 상태는 단조롭게 보존한다. seal이 틀리면 활성화 전 거부·수정해야 한다. provider·R2의 미확정 결과는 terminal 완료로 꾸미지 않는다.

33. **보관 상태의 cache revision은 기존 원자적 archive receipt를 읽어 사용한다.** 현재 검증된 viewer 권한과 함께 cache 반환 전에 검사하고 stale provider allowlist와 알려진 archived ID의 우회를 차단한다. 추가 관측용 D1 쓰기는 넣지 않는다. 빠진 경계가 있으면 과거 cache가 노출될 수 있어 수용 전에 수정해야 한다. 실제 bytes·static·R2 경계는 Task4.3에서 연결한다.

34. **공지·프로필 파일의 owning codec과 일반 업로드의 최소 영속 intent·version·reference 상태를 보완한다.** 기존 파일 port는 승인된 operation이 필요한데 해당 producer codec과 일반 업로드의 복구 기록이 없다. 이관 중에는 확정된 기존 port에 연결하고 admission status는 불변으로 유지한다. 가짜 transition·actor나 별도 권한 엔진을 만들지 않는다. 새 migration과 분류·포착·참조 소비자의 일치가 틀리면 수용 전에 다시 수정해야 한다.

35. **미확정·미수신·참조 중인 파일은 시간만으로 보호를 해제하지 않는다.** 실제 미참조·미보호이면서 기존 정리 자격이 확인된 파일에만 기존 15분 유예를 적용하고, ACK·최종 해제·업로드 중 가장 늦은 시각에서 계산한다. 원래 정리 대상이 아니던 보관·legacy·프로필 파일을 새로 자동 삭제하지 않는다. 의도한 redaction도 owning codec·최종 commit으로 연결하며 owner guard를 우회하지 않는다. 보호가 오래 남으면 저장량·한도·비용 확인이 필요하므로 실제 활성화 전 점검 대상에 둔다.

36. **순환을 만드는 전체 기능 index 대신 필요한 순수 command-parser의 좁은 공개 entry를 선언한다.** 검증·broadcast·검색 도메인 행동은 원래 기능에 두고 기존 index export도 유지한다. 실제 경로만 canonical 규칙과 검사기에 명시하고 일반 deep import를 계속 거부하며, application port·app 합성 경계는 유지한다. 규칙 mirror는 정상 sync로 생성한다. module graph나 공개 범위가 잘못되면 구조·허용/거부 검사를 수정해야 한다.

37. **파일 receipt의 DB·bucket 이름은 실제 선택된 Wrangler 선언에서 명시적으로 공급한다.** `SITE_D1_DATABASE_NAME`·`SITE_ASSET_BUCKET_NAME`을 기존 site/resource·local 생성기 검사와 함께 소비하고, 누락·상대 사이트·선언 불일치를 거부한다. 이름 metadata가 운영 DB ID·실제 binding 관측을 대신하지 않는다. config·Env·타입·producer가 어긋나면 수용 전에 수정해야 한다.

39. **정적 자산은 R2 upload-version 증거와 구분하여 실제 body로 검증한다.** 기존 `FileObservation`은 단일 bucket과 업로드 version을 요구하므로 static ETag나 존재 여부를 그 증거로 넣지 않는다. 최소 static availability 증거를 기존 최종 port에 연결하고 선택된 source·target artifact, site·resource·경로·hash·size와 승인 manifest·현재 포착 참조·transition·generation·fence를 확인한다. 가짜 upload intent·operation·actor는 만들지 않는다. 증거나 참조 조건이 틀리면 수용 전에 수정해야 하며 누락·stale·다른 자원·bytes 불일치는 활성화를 거부한다.

40. **전환 전에 정상 저장된 R2 파일도 가짜 접수 작업 없이 baseline 참조로 검증한다.** 기존 파일에는 transition operation이 없으므로 활성 전환의 `FileIntent`를 억지로 만들지 않는다. 기존 body verifier를 사용한 최소 committed-file receipt를 최종 availability port에 연결하고 승인된 baseline·manifest·포착 참조, exact transition·generation·fence, 각 bucket의 실제 업로드 version·hash·size를 확인한다. source·target 업로드 version의 동일성 대신 실제 bytes의 동일성을 확인한다. 승인된 과거 참조를 현재 행으로 바꾸거나 존재·metadata만으로 복사 완료 처리하지 않는다. receipt·참조 조건이 틀리면 수용 전에 수정해야 하며 기존 데이터·운영을 초기화하지 않는다.

41. **업로드 CLI의 import가 운영 작업을 실행한 사고는 즉시 중단·공개하고 안전한 entry 경계를 먼저 검증한다.** 테스트가 기존 최상위 원격 업로드를 실행했고 완료 6개·완료 여부 미확인 1개를 로컬 로그에서 확인했다. 추가 원격 조회·복구·삭제는 하지 않고 사용자에게 읽기 전용 영향 확인을 별도로 요청했다. 실제 subprocess를 실행하지 않는 import·잘못된 대상 회귀를 먼저 확인하며, 로컬 PASS로 운영 영향이나 원본 동일성을 판정하지 않는다. guard·caller·검증이 틀리면 추가 외부 변경을 막도록 수정해야 하고, 이미 발생한 운영 영향은 별도 확인·필요 조치가 남는다. 상세 범위는 [사고 기록](./operational-upload-incident.md)에 보존한다.

43. **사용자가 허용한 사고 7개 경로의 현재 읽기는 사고 전 동일성·복구 권한으로 확대하지 않는다.** 정확히 7개 GET의 현재 크기·hash는 입력과 일치했고 마지막 파일의18:55:28 수정 기록도 확인했다. 44. **공유 music metadata·source-health를 membership만으로 중지하지 않는다.** 실제 caller 조사에서는 source-health의 만료·삭제가 없었고 공유 metadata는 source의 비독점 dependency였다. 불필요한 두 selector를 제거하고 실제 expiry의 보호·최종 조건과 독점 이동 source의 재활성화 차단을 확인한다. 실행행은 source에, target에는 비실행 역사 자료로 남기는 기존 계약을 유지한다. 조사나 판정이 틀리면 누락된 보호 경계를 수정해야 하며 반대로 범위를 넓히면 무관한 정상 공유 작업이 멈출 수 있다.

45. **절대 자산 URL의 origin·bucket 권한은 승인 plan에 명시한다.** 기존 plan에는 bucket 이름만 있어 host를 제거한 path만으로 소유권을 판정할 수 없다. 최소 positive-parsed mapping으로 실제 제공된 site/static·bucket 또는 명시 external-only 처분을 구분하고 relative 참조는 origin 없이 지원한다. own source URL은 target의 승인 상대 경로로 투영하며 원본 봉인 image·expected state는 유지한다. 새 분류는 기존 parent-CAS·append-only 계보로 처리하고 누락은 인계 진행만 막으며 source 저장·수집은 유지한다. 도메인·별칭을 추측하거나 다른 host를 자동 own으로 만들지 않는다. 판정이 틀리면 manifest·parser·SQL·projector를 수용 전에 고쳐야 한다.

46. **정규화 참조 index는 원문·manifest 권한을 대신하지 않는 최소 파생 상태로 둔다.** inline·view 방식이 실제 D1 byte/depth 한도에서 실패해 `asset_file_reference_paths`를 재구축 가능한 검색 보조로 허용했다. 모든 producer의 같은 transaction에서 index→capture 순서를 명시하고 final 참조·claim·access·fence는 현재 원문과 같은 권한을 확인한다. origin·resource 의미를 잃거나 별도 trigger 순서를 가정하지 않는다. target에는 index를 business로 복사하지 않고 실제 재구축·stale/missing·race·scale·읽기/쓰기 비용을 검증한다. 새 미공유111 초안만 재생성하며 기존 applied 기록·봉인 image·private 원문을 유지한다. 잘못된 구조는 권한·정합성·비용을 수용 전에 수정해야 한다.

47. **기존 legacy cleanup 자격에도 실제 마지막 해제 시각을 영속 보존한다.** legacy notice thumbnail에는 관리 version의 `released_at`이 없어 오래된 upload 시각만으로 방금 해제한 파일을 정리할 수 있었다. 최소 `asset_file_retention_releases`를 파생 index와 분리하고 실제 owning reference·hold 해제 transaction에서 단조롭게 기록한다. 참조·보관·미확정 보호 중에는 시간만으로 해제하지 않으며 실제 미참조·미보호·기존 자격 뒤 가장 늦은 upload·최종 ACK·실제 해제에서15분을 계산한다. 동일값 retry·관측 heartbeat는 release 쓰기나 유예 초기화를 만들지 않는다. 기록 없는 과거 객체를 곧바로 적격으로 추정하거나 새 삭제 대상을 만들지 않는다. 판정이 틀리면 timestamp·자격·소비자를 수용 전에 고쳐야 하며 운영 보관량·한도·비용 확인도 남는다.

49. **기존 파일은 baseline 전에 명시적으로 보호하고 승인된 inventory를 봉인한다.** 실제 `protect()`는 baseline 생성·scope·capture·seal을 한 D1 batch로 실행하며 이전 R2 목록·본문을 받는 지점이 없었다. 최소 prepared 단계의 별도 명시 arm/hold와 실제 owning raw 참조·정확한3명 prefix 목록·본문/hash/size/source version 관찰 port를 허용했다. 같은 protect transaction이 site/resource/UID/승인 revision·digest·현재 참조와 coverage를 검증해 baseline과 inventory를 함께 봉인하며 prepare/import는 암묵 arm하지 않는다. source 일반 작업과 무관한 멤버는 계속 동작한다. target은 원래 봉인 목록을 자기 실제 body/version으로 검증한다. 가짜 업로드·사후 목록 교체나 R2/D1 분산 원자성을 주장하지 않는다. 틀리면 hold·목록·race·계보를 수용 전에 고쳐야 하며 잘못된 광범위 hold의 정리 지연·비용도 평가해야 한다.

51. **파일 history 검증은 같은 D1 batch의 읽기 guard와 기존 exact CAS로 분리한다.** 실제7116byte history SELECT는 통과했지만 fence UPDATE와 합치거나 별도 NOT NULL assignment로 나눠도 SQLITE_NOMEM이었다. 최소 read-only guard SELECT 뒤 기존 UPDATE를 같은 batch에 두는 후보를 허용했다. 정확한 transition/site/generation/manifest·봉인 history를 검증하며 missing·NULL·0행이 성공으로 처리되면 안 된다. 기존 CAS·rowcount·readback과 conflict 진단을 유지하고 실패 때 fence·frozen sets·control 변경 전체 rollback을 실제 D1에서 확인해야 한다. 별도 선행 조회나 caller bool·관측 쓰기·조건 완화는 허용하지 않는다. 틀리면 transaction·guard·race·진단을 수용 전에 복구해야 하며 통과 전 해결됐다고 표시하지 않는다.

Bearer는 자기 resolver·검증된 상대 Blob 경로에만 보내고 raw·봉인 값은 유지한다. 틀리면 일반 관리자 표시 회귀 또는 이동 파일의 권한 우회를 막도록 경계·호출자를 수용 전에 고쳐야 한다.

54. **기존 doctor의 미확정 실행 실패는 schema 증거와 구분하고 Task5에 연결한다.** 최종 doctor는 exit1이었으며 성공 줄만 읽은 최초 요약을 정정한다. 동일한 선택 config·persist의 실제5개 PRAGMA를 한 CLI로 실행해 exit0·필수 열 누락0을 확인했고, 양 사이트의 전체117개 적용과 실제 화면·D1/R2 검증도 별도 통과했다. 기존 doctor가 child 실패의 exit·signal·stderr 대신 stdout 배너만 보여 준 문제와 최초 child 실패의 원인은 별개다. 현재 수정에서 무관한 진단 개선을 추가하지 않고 예정된 Task5 도구 정비에 전달하며 전체 doctor gate는 미완료로 유지한다. 틀리면 실제 schema·도구 실패를 다음 작업 전에 바로잡아야 하며 진단 보완만으로 실행 성공을 주장할 수 없다.

55. **사이트 간 인계는 명시적 Service Binding의 named RPC로 제한한다.** 두 Worker가 같은 계정에 있으므로 `CONTENT_TRANSITION_PEER`가 반대편 `ContentTransitionRelay` entrypoint를 가리키는 최소 내부 경로를 선택했다. 공개 fetch·Clerk·사용자 header·Host를 relay 인증으로 쓰거나 새 secret·공개 fallback을 추가하지 않는다. binding 구성 권한을 가진 계정 운영자가 이 capability의 신뢰 경계이며, RPC가 caller site를 자동 증명한다고 주장하지 않는다. 실제 상대 runtime과 저장 승인 plan·site/resource/role/schema/protocol/generation/digest·원래 receipt/hash를 확인하고 좁은 receiving/control port만 제공한다. 누락·자기 자신·다른 상대는 인계 전에 거부하지만 무관한 OTW 작업은 계속한다. 임시 source 의존은 이전 작업의 유한 drain 뒤 제거하며 운영 연결은 실행하지 않는다. 틀리면 권한·상대 검증·배포 연결을 수용 전에 수정해야 한다. 근거는 [Service bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/), [named RPC entrypoints](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/), [RPC security model](https://developers.cloudflare.com/workers/runtime-apis/rpc/visibility/)이며 이 구체 구성은 프로젝트 조건에 따른 구현 판단이다.

56. **일정 저장은 원래 전체 영향행을 보호하고 새 LuvDia 편집에는 자체 로그인을 요구한다.** 실제 저장은 ID 없는 생성과 member/day·미정 충돌 삭제를 같은 batch로 수행한다. 단일 기존 행만 다루던 codec·expected-state를 실제 영향행과 충돌 predicate의 source-local·projected 조건으로 확장하며 새 충돌행도 검출한다. 임의 ID 예약이나 기존 저장 뜻을 바꾸지 않는다. source 및 무관한 OTW의 기존 권한은 유지하고 target의 새 native 편집은 검증된 별도 Clerk 로그인과 기존 권한 규칙을 함께 적용한다. 이전 source 접수 건에 새 사용자 매핑·재로그인 승인을 요구하지 않는다. 틀리면 부분 삭제·동시 저장 덮어쓰기·인증 회귀를 실제 저장 경로에서 바로잡아야 한다.

57. **순수 D1 일정의 범위 이탈은 source의 원자적 접수·저장으로 처리한다.** source save의 admission·원래 충돌 삭제/생성/수정·감사/capture·terminal 결과를 같은 D1 batch에 둔다. save가 먼저면 selected→unselected의 동일 ID 의미와 전체 변경을 저장하고 target의 선택 자료 삭제를 committed journal로 재생한다. fence가 먼저면 접수·business 변경 모두 rollback되어 명시적 이동/충돌 결과를 주며 이미 접수한 성공으로 위장하지 않는다. 성공 receipt 재시도는 원래 source 사용자 권한으로 읽는다. target 삭제와 source 새 행을 분산 쓰거나 ID를 나누고 source 권한을 우회하지 않는다. 이 local shape는 deferred pending transport로 접수하지 않는다. 실제 이전 held 범위 이탈 producer가 발견되면 별도로 확인하며 selected→selected·provider·due의 기존 접수 인계는 유지한다. 틀리면 누락·원자성·ID·이미 접수한 결과의 보존을 바로잡아야 한다.

58. **정상 일정 editor의 요청 키와 원래 결과를 source에만 보존한다.** 기존 save API에는 원래 결과를 재조회할 요청 identity가 없어 길이를 제한한 선택적 `Idempotency-Key`와 원래 actor·request·result의 같은 D1 batch 저장을 허용했다. 실제 editor는 논리적 저장마다 키를 만들고 불확정·network retry에는 유지한다. 다른 actor나 다른 내용의 같은 키는 거부하며 header 없는 기존 호출자의 저장 의미도 보존한다. 재시도는 같은 site/resource·원래 권한 뒤 기존 응답만 읽고 새 접수·business 변경이나 추가 보관 raw·private 정보를 반환하지 않는다. 원래 source 결과를 새 target 로그인으로 재승인하거나 사용자 매핑하지 않으며 이 키·source private 상태는 transport에서 제외한다. 틀리면 중복 생성·다른 사용자의 결과 접근·재시도 응답 손실을 실제 editor와 저장 경로에서 바로잡아야 한다.

59. **과거 감사의 일정 ID가 무관한 현재 일정을 이관하지 않도록 소유 관계를 바로잡는다.** 실제 `readUpdateLogs`는 감사 행을 직접 읽고 현재 일정과 JOIN하지 않으며, `UpdateLogDto.schedule_id`는 역사 ID이고 registry에도 FK가 없다. 선택 멤버의 과거 감사 필드는 보존하되 그 ID가 지금 존재한다는 이유만으로 무관한 현재 일정을 필수 의존 자료로 가져오지 않는다. 공통 capture 관계에서 수정하고 선택 일정의 root·실제 필수 참조 검증은 유지한다. 누락된 member context를 무조건 제외하거나 과거 봉인·원본 감사를 삭제해 해결하지 않는다. 선택 과거 감사가 현재 무관한 일정 ID를 참조하는 실제 가능한 baseline과 범위 이탈 journal을 검증하며, 생성 guard 변경은 다음 정규 migration으로 적용한다. 틀리면 이관 누락·무관한 자료 노출·현재 일정과 역사 정보의 혼동을 수용 전에 고쳐야 한다.

60. **추천 공지의 변경 범위는 해당 사이트가 현재 편집할 수 있는 일반 공지로 제한한다.** 기존 gateway는 모든 공지의 `is_featured`를 지운 뒤 선택 공지를 추천했지만 공개 화면은 이미 열람 가능한 공지 중에서 추천·기존 fallback을 고른다. 공개 기간·활성 상태·fallback과 일반 공지의 한 개 추천 의미는 유지한다. 보관되거나 이동한 source 자료의 raw 추천 값은 역사 정보로 보존하고 일반 추천 선택에서 제외한다. fence 이후 아직 archive 표기가 되지 않은 선택 자료도 source 소유가 아니므로 `content_access='normal'` 조건만으로 편집할 수 없다. 선택 ID의 실제 권한과 변경 가능한 전체 행·새 충돌행 조건을 같은 owning transaction에서 검증하고, 보관·이동 자료를 직접 추천하려는 요청은 변경 전에 명시적으로 거부한다. target은 자기 일반 공지만 변경한다. 틀리면 다른 OTW 공지 추천이 실패하거나 원본 역사·사이트 격리가 훼손되는 문제를 수용 전에 고쳐야 한다.

61. **내부 초기 이관과 새 요청 접수 준비를 구분하고 실제 참조 검증을 먼저 완료한다.** 기존 target는 `openIngress`를 먼저 호출해야 초기 자료를 설치할 수 있지만 새 공지는 실제 `members` 검증에서 멤버 없음으로 거부됐다. 계획의 UID를 실재하는 멤버로 간주하지 않는다. 승인·격리된 target의 `prepared` 상태에서 기존의 좁은 baseline permit으로 비공개 초기 자료를 접수·설치하고, 전체 원래 baseline의 staging·materialization·실제 readback receipt와 승인한 target 멤버의 존재·기존 유효성 검증을 완료한 뒤 native ingress readiness를 발행·갱신한다. 다른 카탈로그 참조도 실제 설치하므로 기능마다 임시 검증 우회를 만들지 않는다. 내부 receiving과 원래 파일 inventory header는 source ACK·native 준비·최종 파일/쓰기 권한을 증명하지 않는다. source 쓰기는 준비 중 계속되며, native 접수는 준비 발행 뒤 source ACK·fence·최종 tail/checkpoint/file proof 설치 동안 계속 영속화한다. 실행은 최종 소유권 증거 뒤에 한다. 빈 target를 접수 준비 완료로 취급한 이전 검증은 과거의 불완전 증거로 남기고 정상 새 migration·호출자·검증으로 대체한다. 틀리면 준비 완료 뒤 정상 요청 거부·참조 권한 우회·공개 전 노출·접수 중단을 수용 전에 고쳐야 한다.

62. **비공개 초기 이관을 실제 읽기 경계에서 보호하고 접수 가능한 편집 동선은 유지한다.** 초기 materialization은 normal 행을 넣었지만 일반 조회에 target 준비 상태 검사가 없음을 확인했다. 실제 target의 최종 소유권 전에는 비인증 공개 콘텐츠·SEO·내보내기·파일·읽기 cache에서 staged 자료를 노출하지 않는다. 앱·로그인·설정 진입은 유지하며 자기 사이트의 검증된 관리자는 기존 권한으로 준비 자료를 검토한다. 실제 native 준비 뒤 자기 target 로그인 사용자는 기존 public/member/admin 제한을 유지한 정상 편집·조회 동선으로 접수할 수 있어야 한다. 로그인은 쓰기 소유권이나 추가 비공개 열람 권한을 주지 않는다. OTW token·사용자 header·Host로 target 접근을 허용하지 않고 cache 읽기 전에 검사·비공개 응답 분리를 유지한다. 최종 소유권 뒤 기존 공개 규칙을 적용하며 초기 파일 receiving을 최종 파일 증거로 사용하지 않는다. 틀리면 공개 전 자료 노출·다른 사이트 인증 우회·편집 동선 없는 명목 접수를 수용 전에 고쳐야 한다.

63. **일반 독립 배포와 임시 전환 연결을 구분한다.** [Cloudflare 배포 문서](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/#deployment)는 없는 Worker를 Service Binding 대상으로 선언하면 최초 배포가 실패한다고 명시한다. 현재 양쪽 기본 설정의 무조건 상호 연결은 아직 생성하지 않은 LuvDia 때문에 OTW 독립 배포까지 막을 수 있다. 일반 site 설정에서 임시 peer를 제거하고 named relay·선택적 binding·실제 전환 시 누락 거부는 유지한다. 실제 로컬 두 Worker 검증은 명시적 상대·entrypoint binding을 사용한다. Task5에서 검증된 전환 전용 설정과 lifecycle gate를 정비한다. 양쪽의 독립 Worker·entrypoint를 먼저 준비한 뒤 연결하고 readiness·fence를 진행하며, 정상 master 배포도 이전 접수 건의 유한 drain 동안 연결을 잃지 않아야 한다. 완료 증거 뒤에만 임시 연결을 제거한다. 공개 우회·새 secret·누락 연결의 성공 처리는 없으며 지금 운영 생성·배포는 하지 않는다. 틀리면 최초 배포 실패·독립 운영 차단·이전 요청 인계 중단을 수용 전에 고쳐야 한다. 준비·연결 순서는 플랫폼 제약에 대한 프로젝트 구현 판단이다.

64. **target의 새 D-day는 해당 사이트의 native 생성으로 접수한다.** 기존 D-day는 title/date/type만 있고 멤버 UID가 없으며 source 선택은 기존 행 ID의 명시적 분류다. 새 target 행에는 이전 source ID·분류가 없으므로 실제 선택 target 자원·서버가 확인한 단일 승인 전환·미래 세대·자기 Clerk와 기존 D-day 권한/payload 검증을 사용한 좁은 `ddays.create` envelope로 접수한다. 결정61의 준비 뒤 영속 접수하고 최종 소유권 뒤 원래 자동 ID·business/audit/capture/terminal 결과를 같은 owning batch로 저장한다. 재시도는 같은 최소 target 결과를 돌려준다. 임의 ID 예약·사용자가 고른 전환·전역 소유권 bool·일반 table 쓰기·source actor 매핑은 없다. source 기존 선택 행의 수정/삭제는 원래 분류·receipt를 유지하며 새 미분류 source 행은 기존 분류 gate를 거친다. 새 target backlog는 이전 frozen drain에 포함하지 않는다. 틀리면 정상 기능 접수 누락·이중 생성·전역 권한 우회·source 분류 손실을 수용 전에 고쳐야 한다.

65. **실제 receiver 코드의 계약을 준비 증거에 결합한다.** 현재 준비 CAS는 실제 baseline·멤버를 확인하지만 반환 receipt는 이전 identity/receiptId/expiresAt 형식이며 peer는 설치된 SQLite schema를 fingerprint한다. 새 schema가 설치된 DB를 오래된 Worker가 읽으면 같은 schema hash와 이전 준비 응답을 보낼 수 있으므로 설치 schema만으로 새 수신 코드의 의미를 증명하지 않는다. prepared baseline·비공개 조회 의미와 실제 등록 receiver/executor capability를 묶은 compiled contract fingerprint를 peer 설명과 저장 readiness에 포함하고 source ACK 및 같은 fence 조건에서 검증한다. 이전·누락·불일치 형식은 거부하며 과거 seal·소유권을 임의 변환하거나 사용자 version flag로 통과시키지 않는다. 같은 schema와 이전 receipt를 사용하는 결정적 검증은 실제 오래된 artifact 실행 증거와 구분한다. 틀리면 오래된 코드의 거짓 준비 응답으로 원본 권한이 전환되거나 접수 작업이 막히는 문제를 수용 전에 고쳐야 한다.

66. **target의 변경 추적을 실제 최종 이관 상태로 초기화한다.** 초기 baseline과 replay로 들어온 행은 target capture의 before-image/membership에 자동 등록되지 않아 첫 pending 삭제의 변경 전 상태가 빠지는 실패를 확인했다. 기존 fence·tail·checkpoint·최종 파일 설치·transfer 증거를 모두 검증한 activation의 같은 transaction에서 실제 최종 설치된 selected/shared scope를 기존 좁은 seed/capture port로 초기화하고, phase CAS·commit seal과 함께 확정한다. source membership을 복사하거나 오래된 baseline 상태를 다시 사용하지 않는다. 실패하면 activation과 capture 모두 rollback하고 native receipt는 접수 상태로 유지한다. owned/complete 이후 재시도는 기존 일치 증거를 돌려주며 이후 native 변경의 image·history를 덮어쓰거나 다시 seed하지 않는다. source seal·소유권 변경이나 전역 쓰기 허용은 없다. 가져온 pending의 첫 삭제 before-image, 값만 바꾸는 첫 편집, activation 실패·경합, 이후 native 변경 및 완료 후 재시도, source 불변을 실제 owning 경로로 검증한다. 틀리면 이후 수정·삭제의 변경 기록 누락과 재시도에 의한 최신 상태 손실을 수용 전에 고쳐야 한다.

67. **저장하지 못한 CHZZK 읽기 응답의 불확실성은 제한 재조회로 복구한다.** 실제 read-only CHZZK GET이 응답한 뒤 영속 저장 전에 Worker가 종료되면 원래 응답을 조회할 provider 기능이 없다. 원래 접수 operation·논리 request identity·정확한 허용 요청/page/cursor 아래 기존 재시도 상한·backoff·provider 예산 guard로 다시 조회할 수 있다. 이전 불확실한 attempt와 새 attempt를 구분하고 처음 성공적으로 영속 확정한 응답·control 결과를 불변으로 사용한다. 이미 확정한 페이지의 처리 재개나 peer/Queue ACK 유실은 저장 결과를 읽으며 재조회하지 않는다. [RFC9110 §9.2.1–2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)는 읽기·멱등 요청의 재시도에서도 응답이 달라질 수 있음을 설명한다. 이는 이 프로젝트의 좁은 불확실성 복구 판단이며 provider의 과거 응답 조회나 정확히 한 번 HTTP 실행 증거가 아니다. 재조회 응답·사용량은 달라질 수 있고 유실된 일시적 응답은 복원 보장하지 않는다. 불변 page/result journal은 원래 접수·허용 request/page/hash/control에 결합하며 source의 private·혼합 raw 증거를 보존하고 승인 범위의 projection·control만 기존 private peer로 전달한다. secret·actor token·범위 밖 자료·일반 proxy·임의 결과 payload는 허용하지 않는다. 불확실한 POST/Gemini/X 게시/R2 변경이나 다른 외부 effect에는 적용하지 않는다. 응답 저장 전 crash의 재조회와 달라진 실제 응답, 저장 후 crash·ACK 유실의 추가 조회 없음, 동시 응답 CAS, 잘못된 op/request/page/peer 거부, 기존 예산·backoff를 검증한다. 틀리면 일시적 자료 손실을 숨기거나 API 한도 초과·중복 외부 변경·범위 밖 자료 노출을 일으키므로 수용 전에 고쳐야 한다.

68. **이전 접수 조회의 응답 확정은 원래 source control의 단일 CAS를 따른다.** 결정67의 첫 영속 응답을 두 DB에서 독립적으로 선택하면 늦은 source 응답과 target 복구가 서로 다른 결과를 확정할 수 있다. 이전에 접수된 source scan의 허용 요청·attempt·불변 결과 journal은 유한 이전 작업의 drain 동안 source control에 단일 권위를 둔다. target 복구는 기존 private binding에서 실제 role·site/resource·세대·승인 plan·compiled contract·원래 operation/request identity를 검증한 좁은 claim/read/complete로 그 이전 책임을 이어받고 승인 projection/control만 가져온다. 새 source scan·임의 URL·일반 proxy·전역 control 권한을 만들지 않는다. native target scan은 자기 DB의 journal을 사용한다. 늦은 attempt와 불확실성 증거를 보존하면서 실제 단일 CAS로 한 응답만 영속 확정하고 잘못된·오래된·중복 claim을 거부한다. 업무·관측값 저장은 최종 소유자의 owning batch에서만 수행한다. 상대 연결이 없으면 관련 이전 요청만 복구 대기하며 다른 native 작업은 계속한다. frozen 이전 operation의 outstanding attempt·결과·ACK를 실제 drain/retention 종료 조건에 포함하고 완료 증거 뒤에만 임시 의존성을 해제한다. native backlog나 queue-empty를 종료 조건으로 사용하지 않는다. source 늦은 응답 대 target 재시도 경합, 중복 확정·잘못된 요청 거부, fence 뒤 source 업무 쓰기 없음, 실제 유한 완료·연결 해제 조건을 검증한다. 틀리면 두 응답·checkpoint 불일치와 조기 증거 삭제·이전 작업 유실을 일으키므로 수용 전에 고쳐야 한다. 이는 원래 이전 작업의 일시적 제어 권위를 구체화한 구현 판단이다.

69. **복구한 읽기의 불확실한 이전 시도는 명시적으로 대체 완료를 기록한다.** 저장 전 사라진 GET attempt는 성공 ACK를 영원히 보내지 못하므로 결정68의 유한 drain에 불가능한 ACK를 요구하지 않는다. 결정67의 확인된 read-only GET에 한해 단일 확정 응답·control의 영속 소비, 필요한 원래 continuation·혼합 결과의 정합, 원래 operation의 실제 terminal outcome ACK를 확인한 뒤 이전 attempt identity·uncertain_at을 보존하고 해당 확정 응답을 가리키는 명시적 superseded disposition을 기록한다. 이전 시도를 succeeded나 정확히 한 번 HTTP 실행으로 바꾸지 않는다. 이처럼 해결된 읽기 불확실성은 이전 유한 drain·peer 해제를 막지 않으며 기존 lease·retry 규칙 외의 새 시간 제한이나 source ACK를 만들지 않는다. control이 남아 있을 때 늦은 응답은 자기 hash·증거만 보존할 수 있고, 이미 소비한 불변 응답·terminal은 교체와 반복 업무·cursor 변경을 거부한다. 회수된 control을 찾지 못한 늦은 callback도 쓰기 권한을 얻지 않는다. disposition과 불확실성 증거는 승인 복구·보존 종료 조건에 따라 유지하며 완료 판정을 위해 삭제하지 않는다. 불확실한 외부 변경·비멱등 effect는 원래 정합 계약을 따르고 이 해제 경로를 사용하지 않는다. 영원히 사라진 읽기→대체 응답 소비·terminal ACK→native backlog와 무관한 실제 유한 완료, 이후 늦은 callback의 업무·checkpoint 불변, 불확실한 외부 변경의 우회 거부를 검증한다. 틀리면 완료할 수 없는 drain이나 불확실한 변경의 거짓 성공·조기 증거 손실을 일으키므로 수용 전에 고쳐야 한다.

70. **원래 수집의 후속 매칭·집계도 접수 책임에 포함한다.** 실제 ScheduledJobCoordinator.advanceRun(scan)은 source-local scan item 종료 뒤 source D1의 readAutoUpdateMatchTargets로 match/finalize item을 만든다. 선택 관측값이 target에 저장된 뒤 source만 읽어 매칭하거나 scan 종료 ACK만으로 drain을 끝내면 원래 후속 작업·집계가 빠진다. 원래 scheduled run/item/coordinator/finalizer와 manual history identity는 source-local로 유지한다. 실제 최종 소유자가 원래 scan의 확정 결과·control과 정확한 원래 input/window/scope/readback에서 승인된 typed match continuation을 만들고, 검증된 UID mapping/provenance·원래 run/item·안정된 child intent identity로 좁은 frozen-parent control에 영속 전달·복구한다. runnable job 복사·새 source scan/run·frozen 최상위 접수 집합 변경이나 나중 native backlog·target 전체 현재 자료에서 무한한 후속 작업을 만들지 않는다. source의 혼합·무관 item은 계속 처리하고 원래 집계·finalizer는 실제 후속 결과를 따른다. 실제 scan 단계의 결과와 후속 인계가 영속 확정되면 해당 단계 종료를 기록해 기존 coordinator가 원래 match item을 생성·실행할 수 있다. 이 단계 표시는 전체 접수 책임의 terminal delivery/drain ACK와 구분하며 후자는 필요한 원래 후속 작업·집계 정합을 확인한 뒤에만 확정한다. 후속 작업을 만드는 coordinator의 진행을 그 후속 완료로 막는 순환 조건을 만들지 않는다. 이전 전체 작업 종료를 target 소유권·새 native 저장의 선행 조건으로 사용하지 않는다. manual scan→match→history도 원래 전체 결과를 보존한다. candidate/holiday의 실제 GLOBAL affected set과 늦은 결과의 optimistic conflict를 유지한다. 실제 예정/수동 진입·coordinator·소유자 readback, 응답 유실/item 재전달, 한 번의 원래 finalizer, 혼합 결과·native backlog와 독립된 유한 완료, fence 뒤 source 업무 쓰기 거부를 검증한다. 틀리면 일정 후보·집계 누락과 거짓 완료·끝나지 않는 drain을 일으키므로 수용 전에 고쳐야 한다.

71. **원래 GLOBAL 휴방 정리의 양쪽 소유 범위를 같은 child 책임으로 나눈다.** 각 원래 match item의 GLOBAL 휴방 batch는 대상 멤버 외 source 멤버도 정리한다. 이관 대상 child를 target에만 보내면 별도 무관 match item이 없을 때 source 정리가 빠진다. 하나의 원래 child identity에 source 소유의 남은 정상 eligible 범위와 target 소유의 승인 이관 범위를 명시하고 각 원래 GLOBAL batch의 완전한3-statement 순서·conditional audit/reset·실제 owner-local affected set/predicate/phantom guard와 불변 결과를 유지한다. source 범위는 보관·이관된 선택 원본을 바꾸지 않고 target 범위는 무관 source 자료를 바꾸지 않는다. 양쪽을 정확한 원래 frozen parent/child/plan/세대/provenance에 결합하며 새 최상위 source 접수·현재 전체 멤버에서 무한한 child 생성·runnable job 복사·전역 소유권 허용을 만들지 않는다. fence 전에는 원래 완전한 local transaction을 유지한다. fence 뒤 양쪽 owning DB commit은 분산 원자적 transaction이 아니며 실제 확정한 정상 변경을 되돌려 가짜 일괄 원자성을 만들지 않는다. 각 실제 범위 결과를 영속 보존·읽기 확인하고 미완료 실행·전달만 재시도한다. ACK 유실은 확정 batch를 반복하지 않는다. 원래 coordinator는 양쪽 실제 결과·건수와 candidate 결과를 모두 정합한 뒤 child/finalizer ACK를 확정하며 부분 실패·conflict를 그대로 드러낸다. 별도 무관 match item이 없어도 원래 child의 source-global 정리 책임은 남는다. 선택 대상만 있는 원래 child의 양쪽 정리, source 이관 원본 불변, 범위 사이 실패·재개·응답 유실·반복 없음, GLOBAL phantom/새 편집 conflict, 실제 부분 결과 집계·유한 완료 뒤 임시 연결 해제를 검증한다. 틀리면 무관 source 정리 누락·중복 변경·원본 보관 훼손·거짓 집계를 일으키므로 수용 전에 고쳐야 한다. 결정70의 혼합 결과 책임을 실제 GLOBAL batch에 구체화한 판단이다.

72. **수동 수집은 실제 run-now의 원래 scheduled 실행을 따른다.** 실제 /api/settings/run-now handler는 resolveService를 사용하지 않고 ScheduledRunClient.createManualRun('schedule_auto_update', actor, Idempotency-Key)를 호출해202를 반환한다. legacy D1ManualAutoUpdateAdapter/runAutoUpdateWithHistory는 이 HTTP 진입점의 caller가 아니다. 별도 private manual in-progress identity가 필요하다는 이전 보고·controller 승인은 잘못된 caller 전제였으므로 철회한다. scheduled와 실제 manual은 같은 원래 scheduled_job_runs/items/control을 사용하고 run.source=manual, actor, 원래 idempotency와 once-only finalizer/source audit를 보존한다. 새 manual identity/schema/API·legacy adapter·test 동선으로 실제 버튼 흐름을 대체하지 않는다. auto_update_runs의 terminal success/failed 이력 의미는 유지한다. 아직 필요하지 않은 새 구조는 만들지 않으며 실제 적용한 migration 이력은 이 수정의 편의를 위해 다시 쓰지 않는다. 실제 run-now→원래 run/item→단계·후속 처리→최종 history/audit/readback와 재시도·전환을 검증한다. 합친125 검사의3FAIL/6PASS는 실제 실패 증거로 유지하고 원인을 고치기 전 전체 통과로 표시하지 않는다. 틀리면 사용자 버튼과 분리된 구현·중복 실행·잘못된 수동 이력·fixture만 성공하는 결과를 일으키므로 수용 전에 고쳐야 한다. 실제 진입점이 기존 가정·계획 해석보다 우선한다.

73. **유효한 원래 match child를 채널 실패 표지만으로 업무0으로 바꾸지 않는다.** 기준 d27의 실제 ScheduledJobExecutor match는 autoUpdateSchedules(skipScan:true)를 호출한다. coverage 실패·미완료의 throw는 !skipScan 경로에 있고 실제 match는 보존된 observation을 사용한 뒤 reconcileHolidaySuggestions의 두 GLOBAL batch를 실행한다. 따라서 원래 범위에서 정당하게 도출·접수된 child라면 local과 target 모두 이 기존 매칭·GLOBAL 정리 의미를 유지한다. 실패·미완료 marker만으로 source는 업무0, target은 정리 후 failed 같은 비대칭을 만들지 않는다. 원래 bounded scope의 유효한 영속 관측값으로 매칭하며 없는 관측값·성공 coverage·휴방 근거를 꾸며내지 않는다. 기존 holidayEligibleSql은 assessment.scan_status='complete'를 요구하므로 실패·미완료 assessment로 새 부재 기반 휴방 후보를 만들지 않는다. 기존 후보의 obsolete 철회·audit/reset은 원래 GLOBAL 조건과 결정71의 양쪽 소유 범위를 따른다. 채널 실패·미완료는 원래 scan/전체 partial·history 결과에 보존하고 성공으로 바꾸지 않는다. 이는 완전히 실패해 후속 단계가 정당하게 생성·접수되지 않은 stage에 새 child나 cleanup을 만드는 허용이 아니다. 그런 작업은 실제 실패와 업무0을 기록한다. 선택 채널 실패가 독립된 정상·partial 수집의 유효한 후속 작업을 버리게 하지 않으며 전체 오류는 유지한다. 실패·미완료 child의 기존 유효 관측 매칭, obsolete 휴방 철회·새 휴방 없음, local/target 일치, 독립 정상 결과 보존, 도출 가능한 child 없는 stage의 임의 업무 없음과 실제 집계를 검증한다. 틀리면 기존 후보·정리 기능 손실, 근거 없는 휴방·비대칭 변경·거짓 성공을 일으키므로 수용 전에 고쳐야 한다. 실제 scheduled/run-now가 권위이며 사용되지 않는 legacy !skipScan adapter로 의미를 바꾸지 않는다.

74. **도출된 target 사실과 실제 child 접수를 구분해 종료한다.** scan 관측·assessment에서 먼저 저장한 stage.targets/child row는 원래 coordinator가 match item을 접수하기 전의 잠재 사실이다. 실제 권위 있는 원래 scan 단계가 기존 규칙에 따라 terminal failed/throttled이고 정확한 parent identity와 실제 match 접수 부재를 증명할 때만 명시적 no-admission control disposition으로 닫는다. 단순 Queue·peer 전달 실패, 임시 재시도 상태, 전달3회 소진은 유효한 succeeded/partial 소유자 stage가 있는 접수 책임을 버릴 증거가 아니다. 그런 책임은 기존 영속 복구로 이어간다. 실제 terminal 결과·접수 부재·disposition을 source control의 같은 transaction에서 검증·확정하고 coordinator의 child 접수도 같은 guard를 따라 접수 대 종료 경합의 한쪽만 확정되게 한다. 원래 target identity·증거·실패 원인을 보존하고 genuinely 미접수된 실패 target의 업무는0이며 finalizer에 별도 계상한다. 독립 succeeded/partial shard는 계속 처리하고 정당한 partial child는 결정73의 기존 매칭·GLOBAL 정리를 수행한다. 실제 실패 미접수 종료, 성공 stage의 전달 실패가 잘못 종료되지 않음, 접수/disposition 경합, 자료·identity 삭제 없음, 독립 정상·혼합 finalizer의 실제 집계를 검증한다. 틀리면 유효한 접수 작업 유실·이중 종료/실행·거짓 drain 완료를 일으키므로 수용 전에 고쳐야 한다. 이는 실패 상태를 성공 ACK로 바꾸는 일반 정규화가 아니다.

75. **X 삭제 처리는 원래 전체 batch와 보관 원본을 함께 지킨다.** 실제 redactStoredXPosts는 해당 게시글·facts의 내용 제거, 다른 로컬 게시글에 포함된 reply/quote/link 제거, 참조 종료와 posts cache 정리를 한 batch로 수행한다. source fence 전에는 원래 전체 변경·audit·capture·접수·종료를 같은 transaction으로 확정한다. fence 뒤 원래 실제 변경 범위가 이관된 관리자 보관 행·참조·cache와 겹치면 전체를 변경하지 않고 CONTENT_MOVED를 반환한다. 보관 참조를 몰래 제외하거나 일부 성공으로 원래 의미를 바꾸지 않는다. 실제 변경 범위가 겹치지 않는 독립 source 작업은 계속 처리한다. 읽기에서 ID를 발견했다는 사실만으로 변경 범위의 겹침을 주장하지 않되, 원래 전체 posts cache 삭제가 보관 행을 실제로 건드리면 그 겹침은 숨기지 않는다. target은 자기 DB의 현재 소유 범위와 자기 관리자 권한으로 원래 전체 작업을 수행하며 무관 source 콘텐츠를 삭제하지 않는다. source 보관 자료와 연결된 삭제는 target 편집 동선을 사용해야 한다는 제한을 정확히 표시한다. 전환 전 전체 batch·audit 원자성, fence 경합의 전부 rollback, 전환 뒤 원본 불변과 명시적 오류, 독립 source 작업, target 전체 변경·phantom/새 편집 conflict·확정 결과 재시도를 검증한다. 틀리면 보관 원본 훼손 또는 일부 성공·숨은 의미 변경을 일으키므로 수용 전에 고쳐야 한다. 결정57과 관리자 보관 불변의 구체화이며 추가 운영 작업 허용이 아니다.

76. **사용자 리뷰의 필수 수정 두 가지를 먼저 반영하고 재검토한다.** 진행 중인 전체 구현은 그대로 보존하고, 완료된 신규 수집의 큰 응답·시도 상세 정리와 일반 비고유 인덱스 추가에 대한 호환성 검사를 우선 수정한다. 기존 보존 작업·호환성 체계를 재사용한다. 정리는 실제 완료·복구·재처리가 끝난 신규 작업에만 적용하고 미완료·불확실·이관 원본 증거와 최소 중복 방지 식별자·hash·종료 결과를 남긴다. 단순 단계 완료를 전체 종료로 해석하거나 정리 뒤 provider·업무를 재실행하지 않는다. 호환성에서는 필수 컬럼·제약조건·고유 인덱스·보호 trigger·실행 계약·실제 peer 권한 검증을 유지한다. Queue 전송 중복은 같은 파일의 작은 함수로 줄일 수 있을 때만 같은 await·오류·복구 의미로 정리한다. 사용자가 중간 재검토를 명시했으므로 전체 Task4.4 완료를 기다리지 않고 이 세 수정의 정확한 변경 전후 artifact를 독립 검토한다. 이 gate는 미완료 Task4.4의 완료·운영 준비 판정이 아니며 검토가 끝난 뒤 남은 원래 범위를 재개한다. 틀리면 접수 작업·중복 방지 증거 유실 또는 보호 계약 약화가 발생하므로 수용 전에 고쳐야 한다.

77. **Play의 콘텐츠 root와 공유 사전 부모를 구분한다.** 확정 설계와 실제 기존 검사는 선택된 performance·participant 등 콘텐츠와 전용 관계의 편집을 인계하면서, 공용 song·외부 entity·alias 등 부모 사전은 다른 OTW 콘텐츠 운영에 계속 사용할 수 있게 한다. 포착 membership이나 현재 선택된 참조가 하나라는 사실만으로 공용 부모의 독점 소유권을 새로 만들지 않는다. source의 정상 공용 사전 변경은 전환 후 자기 DB에만 적용하고 target으로 재생하거나 봉인한 source image·journal·선택 root·전용 관계를 바꾸지 않는다. 실제 승인 분류가 전용 자료인 행은 보호하며 그 분류의 모호함은 해당 행에서 해결한다. 전체 원래 catalog batch·버전·revision·event·search와 target의 자기 권한·동시성 검사를 유지한다. 실제 공유/단독 참조의 사전 분류, 정상 source 편집, 선택 root 변경 거부, 봉인 자료 불변과 target 독립성을 검증한다. 틀리면 정상 OTW 사전 관리 회귀 또는 전용 보관 자료의 변경 우회를 일으키므로 수용 전에 고쳐야 한다. 별도 범용 소유권 체계를 추가하지 않는다.

78. **Play의 필수 catalog event와 별도 비필수 admin audit를 혼동하지 않는다.** 실제 executeCatalogBatch는 catalog 업무·event·projection·revision을 원자적으로 확정하며, AdminCatalogService의 bestEffortAudit는 별도 시도로 실패가 업무를 실패시키지 않는다. 필요한 업무·접수·포착·종료의 원자성은 유지하되 원래 선택적 audit를 몰래 fatal transaction으로 바꾸거나 이미 원자적이었다고 주장하지 않는다. 원래 actor·개인정보·출처와 비필수 실패 의미를 보존하고, crash·재시도에서 업무가 중복되지 않는지 확인한다. 실제로 접수된 필수 audit 책임이 있다면 그대로 정합·완료하며 이를 선택적 성공으로 숨기지 않는다. 틀리면 기존 정상 저장을 audit 장애로 중단하거나 행위 이력을 유실시킬 수 있으므로 수용 전에 고쳐야 한다.

79. **확인된 YouTube 읽기 요청의 불확실성 복구만 명시적으로 허용한다.** 실제 YouTubeOtwPlayMetadataReader 전체와 AdminCatalogService의 channel/performance/catalog/proposal 호출, reserveYouTubeQuota를 읽어 GET 이전에 원래 접수·요청 책임이 필요함을 확인했다. 설치된 reader의 channels.list·videos.list·playlists.list·playlistItems.list에 한해 원래 접수 작업·허용된 part/ID/정렬 batch/pageToken/인자를 고정하고, 영속 결과가 없는 불확실한 조회를 기존 attempt 상한·backoff·Retry-After·오류/설정/예산 규칙 아래 제한 재조회한다. 첫 영속 소비 결과는 불변이며 결과 확정·ACK 유실은 재조회하지 않는다. 원래 불확실한 attempt와 대체 attempt·실제 status/hash·응답 변경 가능성을 남기고 일시적 유실 응답의 복원이나 HTTP exactly-once를 주장하지 않는다. 각 실제 재조회는 기존 quota 예약·사용량 처리를 거치며 이전 예약을 환급·은폐하거나 새 HTTP의 무료 예약으로 재사용하지 않는다. 두 사이트의 프로젝트 합산 한도·배분은 기존 비용 정책과 Task5–6을 따르며 한도를 늘리지 않는다. 원래 source 접수는 결정68의 단일 source control CAS와 정확한 private peer·승인 projection을 유한 이전 책임 종료까지 유지하고 native target은 자기 control을 사용한다. 업무·cursor/checkpoint는 최종 소유자만 확정한다. 결정69의 명시적 unknown superseded는 실제 영속 대체 응답 소비·모든 원래 후속 책임·진짜 terminal 결과 정합·ACK 뒤에만 확정하며 이전 unknown을 성공으로 바꾸지 않는다. 늦은 callback은 결과/업무를 덮어쓰지 않고 회수된 control은 거부한다. 임의 URL·method/body·secret 직렬화, 외부 변경, OAuth 변경이나 다른 provider로 자동 확대하지 않는다. 기존 좁은 요청/attempt/result 구조를 가능한 범위에서 재사용하며 별도 provider framework를 만들지 않는다. 기존67–69·권한 증거는 재사용하고 새 실제 호출 경계의 유실/재조회·확정 후 무재조회·CAS·quota/backoff·진짜 결과/유한 drain만 검증한다. 정책 결정이며 구현 통과나 실제 API 호출의 증거가 아니다. 근거: [channels.list](https://developers.google.com/youtube/v3/docs/channels/list), [videos.list](https://developers.google.com/youtube/v3/docs/videos/list), [playlists.list](https://developers.google.com/youtube/v3/docs/playlists/list), [playlistItems.list](https://developers.google.com/youtube/v3/docs/playlistItems/list), [요청별 quota](https://developers.google.com/youtube/v3/determine_quota_cost). 틀리면 응답 유실로 이전 책임이 영구 대기하거나 반복 호출·사용량 누락·중복 업무·비밀키 유출을 일으키므로 수용 전에 고쳐야 한다. 운영·provider 호출 권한은 추가하지 않는다.

80. **관리자 메타데이터 조회 복구는 기존 호출자의 실패 의미와 Queue 상한을 따른다.** 실제 reader에는 retry loop가 없고 관리자 서비스는 조회 오류를 전파한다. 수집의 nextRetryAt와 source-health의 별도 주기를 가져오지 않는다. 양쪽 background Queue의 max_retries=3과 현재 전환 Queue의 기본30초를 근거로, 영속 결과 없이 중단된 관리자 GET에 한해 최초1회와 복구 최대3회, 논리 요청별 총4개의 영속 started-HTTP 슬롯을 둔다. 실제 GET 전 전달 실패는 슬롯을 소비하지 않으며 Cron·DLQ·재전송으로 슬롯을 초기화하지 않는다. 발행됐거나 발행 여부가 불확실한 각 시도는 실제 quota 처리를 유지한다. 알려진 메타데이터 오류는 원래 caller 결과·분류를 따르고 다른 caller의 정책은 바꾸지 않는다. 총4회에도 usable 영속 응답이 없으면, 확인된 읽기 전용 관리자 요청에만 실제 catalog 업무 미확정을 증명해 명시적인 메타데이터 읽기 실패로 종료할 수 있다. 이는 대체 응답으로 superseded된 경우나 upstream 성공·불확실한 외부 변경의 해결이 아니다. 모든 unknown 시도·상한·업무0 증거와 원래 actor/generation을 보존하고 현재 유효 claim·응답·결과·business commit이 없는 같은 control CAS에서 닫는다. 응답/commit이 먼저 이기면 실패 종료는 거부한다. 늦은 응답은 실패를 재개하거나 업무를 실행하지 않고 control이 남으면 별도 증거만 기록하며 회수 뒤에는 거부한다. 진짜 실패 결과·Queue ACK·유한 이전 책임 종료는 이 명시적 실패 disposition을 이해한다. 새 native YouTube body/attempt 상세가 기존 table에 남는 경우 결정76의 같은 pruner·전체 완료 후30일·실제 cascade budget·최소 hash/결과·미완료/unknown/source/frozen 증거 보호를 적용한다. 원래 caller의 실패를 성공으로 바꾸거나 다른 effect의 불확실성을 닫는 범용 허용이 아니다. 기존 재시도·정리 증거를 재사용하고 새로운 상한/실패 경계·codec 완료 조건만 검증한다. 구현 통과 판정이나 운영 권한 추가가 아니다.

81. **GET 전에 접수한 작업의 기존 참조도 같은 경계에서 포착한다.** 채널 저장의 entityIds가 초기 선택 closure 밖의 기존 공용 entity를 참조하는 실제 경로가 있다. 원래 승인 설계3.3은 scope entry의 변경 없는 필요 참조를 같은 source 경계에서 포착하고 나중 uncontrolled live read를 금지한다. 따라서 실제 early-admission transaction에서 원래 작업에 필요한 bounded entity/alias/credit image·참조 identity를 기존 승인 registry/projection/closure로 포착하고 원래 command·plan·generation·source boundary에 묶는다. 먼저 기존 baseline/committed-tail replay가 이를 target 소유권 활성화 전에 실제 행으로 설치하도록 연결한다. 이 경로로 가능하면 새 범용 dependency installer나 virtual catalog view를 만들지 않는다. 기존 source 공용 사전의 전환 후 독립성77을 유지하고 frozen image·tail만 보존하며 독점 부모 소유권을 만들지 않는다. 계정/actor/lease를 옮기거나 네 번째 managed member를 만들지 않고 기존 외부 역사 credit 변환·UID mapping·identity conflict를 따른다. 원래 entityIds와 실제 관계·동시성 조건을 유지한다. 이미 있는 호환된 승인 target 부모는 덮어쓰지 않으며 새 편집·collision은 기존 실제 충돌/검증으로 처리한다. 포착과 접수는 원자적이며 fake business edit나 broad permit을 사용하지 않는다. 현재 pipeline의 정확한 누락 port가 확인되면 같은 승인 capture/projected-statements 경로의 최소 bridge로 고친다. 처음 closure 밖인 참조의 실제 source 접수→fence/tail/activation→원래 owner service/Queue 결과, native 새 편집 보존을 검증하고 기존 projection/FK/역사/77 증거는 재사용한다. 기존 참조 의무의 보정이며 구현 완료나 새 product 범위가 아니다.

82. **이관된 채널 관리 이벤트는 기존 계정 없는 역사 표현을 같은 저장 배치에 남긴다.** 실제 music_catalog_events_actor_check는 admin/member의 실제 actor_user_id를 요구하고 system만 NULL을 허용한다. 이관된 source 관리자의 계정을 target 계정으로 복사하거나 system으로 바꿔 제약을 우회하지 않는다. 확인된 기존 music_catalog_events 역사 disposition·projectCapturedRecord·historicalStatements를 재사용해, 검증된 원래 채널 작업의 sourceSite·불변 event identity·종류·내용·시각을 승인 projection으로 남긴다. 이 필수 이벤트는 원래 owner의 업무·revision·projection·receipt와 같은 원자적 batch에 포함한다. 실제 채널 이벤트에는 live event 소비 경로가 없으므로 새로운 subject link나 표현 체계를 만들지 않는다. nullable actor 값만으로 이 경로를 허용하지 않으며 검증된 이관 작업 경계에 한정한다. native와 정상 source 이벤트는 실제 actor와 원래 live table 제약을 유지한다. 다른 Play 이벤트의 receipt·삭제 판정 등 실제 live 소비자가 있으면 이 결정을 자동 적용하지 않는다. 기존 source_tail 실패는 보존하고 같은 실제 인계 사례에서 역사 이벤트 읽기 확인·전체 batch rollback·재시도 불변을 검증한다. 필수 event를 비필수 audit로 대체하거나 생략하는 허용이 아니며 새 schema·운영 권한을 추가하지 않는다.

83. **회원 저장 재시도도 현재 보관 권한을 먼저 따른다.** 확정 설계3.1.7은 public/member/own-proposal DTO에 관리자 보관 자료를 담지 않도록 요구하고, 실제 readMine·readByIdempotency도 보관 원본을 회원에게 숨긴다. 따라서 정확한 원 회원·요청 키·내용을 검증한 과거 저장 재시도라도 source의 해당 콘텐츠 소유권/접근이 이관된 뒤에는 기존 CONTENT_MOVED를 반환하고 보관된 원래 DTO·상세를 다시 노출하지 않는다. 원래 source private receipt·불변 결과·완료 증거는 그대로 보존하며 새 접수·업무 재실행을 만들지 않는다. 이 경계 전 정상 같은 회원의 재시도와 무관 OTW 제보는 기존 결과·권한을 유지한다. 다른 회원/키는 receipt 정보를 얻지 못하고 일반 readMine/list의 개인정보 경계도 유지한다. 새 LuvDia 로그인에 원 제보자의 소유권을 연결하거나 imported proposal 편집 권한을 암시하지 않는다. 이는 결정58의 원래 권한 검사와 확정 관리자 보관 정책을 실제 회원 응답에도 집행하는 보정이다. 원래 proposal.updated 필수 live event의 changedFields는 실제 고정 이름 submissionKind·broadcast·youtubeUrl·title·suggestedSongId·tags·originalArtists·participants·note만 기존 catalog_event parser/allowlist에 추가한다. source projection과 projected decode 모두 다른 이름·비문자열·actor/계정 자료를 거부하며 별도 ingestion_event 형식은 바꾸지 않는다. 작은 기존 검증을 재사용하고 임의 JSON/새 범용 표현 체계를 만들지 않는다. 실제 보관 후 같은 회원의 재시도·정상/native 재시도·잘못된 changedFields 거부를 현재 새 검사에 포함한다. 권한 우회나 원래 접수 책임 폐기 허용이 아니다.

84. **source의 전역 카탈로그 조건을 owner별 고정 경계로 인계한다.** createCatalogEntry·approveProposal의 expectedCatalogRevision은 원래 source DB의 전역 동시성 조건이며, 별도로 재구축하는 target 숫자와 직접 비교·복사하지 않는다. 이 조건이 필요한 검증된 미완료 source 작업만 원래 입력을 성공한 source fence와 같은 transaction의 불변 revision 증거에 묶는다. fence 전 무관한 카탈로그 변경도 원래 전역 조건을 stale하게 만들며, fence 후 독립 OTW 변경은 이미 넘긴 조건을 바꾸지 않는다. target은 최종 tail·projection 설치 뒤 최초 activation의 같은 transaction에서 자기 revision 기준을 한 번 고정하고 원래 전역 CAS로 실행한다. 실행 시 최신 값으로 재설정하거나 재시도·이미 소유한 activation에서 다시 고정하지 않는다. 새 target 카탈로그 변경이 이기면 이전 작업은 명시적 conflict가 되며 확정 결과 재조회는 업무를 반복하지 않는다. native 입력은 원래 자기 사이트의 client revision을 그대로 검사한다. 실제 target 카탈로그를 바꾸는 baseline/tail은 기존 재구축 계약에 따라 같은 원자적·멱등 적용에서 자기 revision도 무효화하며 같은 수신 기록 재생은 다시 증가시키지 않는다. 기존 operation/fence/activation 상태를 최소 보정하고 source 전역 revision 복제·범용 epoch/소유권 체계·정상 OTW 변경을 막는 meta 포착을 만들지 않는다. stale 조건이 미완료 조회 증거를 폐기하지 않으며 원래 metadata 오류 순서·unknown 복구·종료 책임을 유지한다. source 숫자가 다른 정상 인계, fence 전 source 변경, activation 뒤 target 새 편집, native 조건과 반복 activation/replay를 실제 현재 경로에서 검증한다.

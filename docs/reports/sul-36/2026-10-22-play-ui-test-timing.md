# 병렬 Play UI 테스트 타이밍 복구 — 2026-10-22

## 범위와 요구사항

- 기준 소스: `f46384f4dabe29872cabba6f69c45d8d834d6170` (일정 복구 PR #185 병합).
- 환경: Windows, Node 24.20.0, pnpm 11.7.0, Vitest 4.1.11, 기본 worker 2개.
- 남은 실패: 채널 소유자 보존, 노래방 다음 구간 등록, 회원 제안의 가창 역할 전송.
- 테스트 코드, 기본 5초 테스트 제한·1초 비동기 조회 제한, assertion, 병렬 수,
  실제 검색 debounce와 화면 애니메이션을 유지한다.
- 운영 기능·DB·권한을 바꾸지 않는다. 기존 실패 테스트가 회귀 검증을 담당한다.

## 재현과 원인

원본 두 테스트 파일의 전체 99건을 기본 병렬 설정으로 실행하면 98건 성공,
노래방 다음 구간 등록 1건이 5초 제한에서 실패했다(5,057ms). 전체 실행은 107.32초였다.
3건만 선택한 실행은 통과하므로 단독 재시도 성공은 해결 근거로 삼지 않았다.

실제 `getComputedStyle` 호출을 그대로 위임하는 임시 계측에서 다음 비용을 확인했다.
쿼리는 역할·접근 가능한 이름·가시성을 계산하므로 스타일 계산 비용이 반복된다.
스타일 계산이 동기 실행을 점유하면 검색 debounce·Promise·화면 전환을 처리할 여유가
줄어들고, 병렬 실행 부하에서 기존 제한을 넘는다. 실제 동시 실행의 스케줄링 영향은
이 수치와 전체 실행 실패를 함께 근거로 판단했다.

| 사례 | jsdom 28.1.0 스타일 계산 | jsdom 30.1.3 스타일 계산 |
| --- | ---: | ---: |
| 채널 소유자 보존 | 583회 / 1,343ms | 569회 / 171ms |
| 노래방 다음 구간 | 1,280회 / 2,023ms | 1,280회 / 131ms |
| 회원 가창 역할 | 450회 / 1,730ms | 768회 / 168ms |

계측한 원본에서는 스타일 계산에 각 테스트 시간의 54~76%가 사용됐다.
업데이트 후 호출을 생략하거나 가시성 판정을 우회하지 않고 계산 비용이 줄었다.
비동기 실행 순서에 따라 호출 수가 달라질 수 있으므로 호출 수 감소를 성공 조건으로 두지 않았다.
각 사례 시작 시 DOM 요소와 style 태그가 비어 있어 이전 테스트의 DOM 잔류는 관측되지 않았다.

검색 범위를 검수 패널·등록창·검색 결과로 좁히는 실험은 일부 호출만 줄였고,
소유자 사례에는 개선이 없었다. 공통 병목을 해결하는 근거가 부족해 최종 변경에서 제외했다.

## 수정

개발 의존성 `jsdom`을 28.1.0에서 30.1.3으로 갱신하고 pnpm lockfile을 재생성했다.
[30.1.0 공식 변경 기록](https://github.com/jsdom/jsdom/releases/tag/v30.1.0)의
스타일·DOM·이벤트 처리 성능 개선과
[30.1.3 공식 변경 기록](https://github.com/jsdom/jsdom/releases/tag/v30.1.3)의
스타일 계산·상호작용 테스트 성능 수정을 적용한다.
프로젝트의 기존 Node 24.20.0 요구사항이 새 jsdom의 Node 24.15.0 이상 조건을 충족한다.

두 테스트 파일은 기준 소스와 동일하다. 테스트 설정·시간 제한·재시도·assertion·모션을
수정하지 않았으며 모든 임시 계측을 제거했다. 런타임 의존성과 제품 코드는 변경하지 않았다.
lockfile의 운영 의존성에서 도달하는 하위 의존성 403개도 기준 소스와 동일하다.

## 검증

임시 계측이 없는 원본 99건을 같은 기본 worker 2개로 재실행해 99건 모두 통과했다.
전체 시간은 34.60초였다. 개별 실행 시간은 기계 부하에 따라 변하며 성능 보장 수치는 아니다.

| 사례 | 업데이트 전 전체 99건 실행 | 업데이트 후 전체 99건 실행 |
| --- | ---: | ---: |
| 채널 소유자 보존 | 2,245ms | 700ms |
| 노래방 다음 구간 | 5,057ms, 제한 초과 | 673ms |
| 회원 가창 역할 | 1,785ms | 630ms |

동일한 명령:

```powershell
pnpm exec vitest run src/features/otw-play/ui/admin/catalog-manager.test.ts src/features/otw-play/ui/member/submission-page.test.tsx --reporter=default --reporter=json --outputFile.json=<진단 JSON 경로>
```

공식 `pnpm preflight`를 처음부터 끝까지 한 번 실행해 **종료 코드 0, 전체 PASS**를 확인했다.
실패 단계만 재시도한 조합 판정이 아니다.

## 별도 관측

전체 실행에서 Vitest worker 종료 지연 경고 3건이 발생했다.
`current-member-affiliation.test.ts`, `log-filter.integration.test.ts`,
`retained-content.integration.test.ts`의 종료 대기 로그다.
Vitest 4.1.11의 `runner.stop()` 대기 중 `teardownTimeout` 알림에서 발생하며,
이 로그 자체는 테스트 실패를 설정하지 않는다. 실제 테스트 결과와 preflight 종료 코드는 모두 성공이다.
수정 전 전체 실행에도 다른 파일의 worker 종료 지연 경고 3건이 있었으므로 새 jsdom만의
회귀로 판단할 근거는 없다. 이번 UI assertion 실패 3건과 구분하며, 종료 지연 자체를 해결했다고
주장하지 않는다. 별도 runner 종료 지연의 근본 원인은 미확정이며 관측된 영향은 실행 지연이다.

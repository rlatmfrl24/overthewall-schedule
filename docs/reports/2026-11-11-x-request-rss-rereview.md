# 요청 확정·회차 차단·RSS 404 재리뷰

2026-11-11. 기준은 `236fd3495c367364ef53959e3c576375c77d72e4`와 현재 미커밋 변경이다. 사용자가 요청한 요청 확정 중 동시 저장, 이전 제어 메시지·예산 거절의 회차 차단, RSS 404 재시도, ACK 실패를 포함한 혼합20건과 D1 50회 한도를 다시 검토했다.

**결론: P2 2건·P3 1건을 추가 재현했다. 이번 작업에서 제품 코드는 수정하지 않았다.** 운영 설정·원격 DB·배포·실제 Fx 요청·신규 유료 호출·Git 게시 작업도 수행하지 않았다.

## Standards

### P2 — 실행 중인 항목의 이전 전송 거절이 새 실행 전체를 제한

위치: `worker/platform/scheduled-jobs/d1-scheduled-job-repository.ts:1118–1120`, 쓰기 `:1128`, `:1136`.

claim 검사는 outbox 임대와 해당 항목의 `deliveryGeneration`을 확인한다. 그러나 수동 재시도는 실행 중인 항목의 세대를 보존한다. 실행 전체의 `controlGeneration`이 바뀌어도 그 항목의 이전 claim이 조건을 통과할 수 있다.

실제 로컬 D1 재현:

1. dispatcher가 A의 회차0 outbox를 claim하고, 이전 날 예산 5000/5000에서 실제 거절 결과를 받는다.
2. 결과 반환을 기다리는 동안 A가 실행 중 상태가 되고, 유효한 기존 제어 처리로 실행과 B가 제한 상태가 된다.
3. UTC 날짜가 바뀐 뒤 정상 수동 재시도가 실행 회차1과 B의 회차1을 만든다. A는 진행 중이므로 항목 회차0을 유지한다.
4. 현재 날짜의 예산 사용률은 0%지만, 늦게 도착한 이전 거절이 B와 실행을 다시 `throttled/daily_background_budget_exhausted`로 바꾼다.

새 회차 보존 assertion이 실패했다. 발생 가능성은 낮지만 정상 재시도를 중단시킨다. claim에 당시 실행의 제어 회차도 보관하고, 제한 처리 SQL에서 함께 확인해야 한다. 진행 중 항목의 회차를 강제로 바꾸면 기존 진행을 끊을 수 있으므로 그 방식으로 우회하지 않는다.

### P3 — 폐기된 제어 오류도 재시도 예산을 소비

위치: `worker/app/scheduled-queue.ts:45–47`.

정상 control handler에서 이전 계획 조회 대기 → 이전 DLQ → `ScheduledRunClient.retryRun`의 새 회차 전송 → 이전 조회의 오류 반환 순서를 재현했다. 오류 catch는 세대 확인 없이 `reserveQueueOperations("control")`를 실행하고 이전 메시지를 다시 전달한다.

새 메시지 전송 후 4747이던 원장이 불필요한 예약으로 4750이 되었고, 실제 새 회차는 95% 기준에 걸려 계획 전에 제한됐다. 일반적인 추가 소모는 3/5000으로 작고, 직접적인 중단 영향은 예산 경계에서 발생한다. 재시도 예약과 재전달에도 예상 제어 회차를 확인해야 한다. 상태 변경 메서드만 보호하면 이 경로가 남는다.

두 지적은 실제 실행 결과와 무결성을 요구하는 `.agent/rules/antigravity.md` 및 사용자의 회차 차단 계약에 관한 것이다. 별도의 구조·명명 휴리스틱 지적은 없다.

## Spec

### P2 — 현재 회차 RSS 실패 큐 묶음이 D1 50회 초과

위치: `worker/app/scheduled-queue.ts:98–99`. 운영 설정의 DLQ 묶음 크기10을 사용했으며 설정은 변경하지 않았다.

RSS DLQ 최적화는 모든 메시지의 `deliveryGeneration`이 0일 때만 실행된다. 수동 재시도 뒤의 유효한 회차1 메시지는 개별 처리 경로로 들어간다.

실제 로컬 D1 및 정상 `handleWorkerQueue` 재현:

1. RSS 항목10건을 정상 수동 재시도해 회차1로 만들고 완료 결과를 저장한다.
2. 미정산 후속 outbox가 전송 가능한 시각까지 진행한다.
3. 현재 회차1의 DLQ 메시지10개를 같은 invocation에 전달한다. 외부 전송은 모의 Queue다.

| 계측 조건 | D1 binding 호출 | 한도 거절 | ACK |
| --- | ---: | ---: | ---: |
| 한도 없이 필요한 전체 처리량 측정 | 54 | 0 | 10/10 |
| 실행당50회 강제 | 50 | 2 | 9/10 |

50회 이후 추가 호출이 거절돼 `d1_binding_call_limit`이 발생했다. 54회가 실제 제한 환경에서 모두 실행됐다는 의미는 아니다. 후속 전송이 없는 같은 표본은 정확히50회에서 완료했으므로, 전송 완료 기록까지 포함하는 검증이 필요하다.

현재 유효한 회차도 묶음 처리에 포함하거나, D1 잔여분 안에서 처리하고 나머지를 재전달해야 한다. 이전 회차 메시지를 거르는 검사는 유지해야 한다. 새 회차 메시지를 무시하거나 운영 묶음 크기를 임의 변경해서 해결하지 않는다.

## 정상 확인한 흐름

Node24.20.0, 실제 로컬 D1과 모의 외부 응답을 사용했다. 사용자 요청의 대표 혼합20건은 다음 결과를 유지했다.

| 사례 | 결과 |
| --- | --- |
| 원문 캐시 만료 혼합20건 | Queue16회, D1최대49회, 한도 거절0 |
| 첫 ACK 실패를 포함한 같은 혼합20건 | Queue16회, D1최대50회, 한도 거절0 |
| 마지막 ACK 실패 후 재전달 | Queue17회, D1최대49회, 한도 거절0 |
| 기존 공식 보완 ID | 4/4 복구 |
| 일시 RSS404 → 200의 전체 Queue | D1 29회, 한도 거절0 |
| 지속 RSS404의 전체 Queue | D1 12회, 오류·대기 보존, 한도 거절0 |

기존 집중 회귀는 7파일280건을 합성 검증해 통과했다. 두 묶음 실행에서 서로 다른 Worker pool 시작 시 `bad port` 오류가 각각1회 발생했지만, 시작되지 않은 두 파일을 별도로 재실행해 85/85 통과를 확인했다. 제품 코드는 모든 실행에서 동일하다. 초기 두 명령이 오류 없이 끝났다고 보고하지 않는다.

Spec 독립 검증은 기존 정책·RSS 회귀80/80과 추가 임시 프로브12/12가 통과했다. 순번 경합 → 토큰 경합 → 중단 → 추가 Fx 저장 → 재개를 유한 경계140과 무한 경계에서 모두 확인했다. 저장 ID 신규 재조회 없이 누락을 저장하고 완료 후 +12시간을 확인했다.

RSS404 재시도는 첫 응답 스트림 정리 성공·실패, 두 번째 응답의 비정상 XML·UTF8·302·429·timeout·abort·network 오류를 확인했다. 같은 URL 최대2회이며 오류를 성공으로 바꾸거나 세 번째 요청을 보내지 않았다. 이 범위의 추가 지적은 없다.

이 정상 결과는 위3건의 경합·실패 큐 한도 위반을 해소했다는 증거가 아니다.

## 범위와 남은 작업

제품 코드·기존 테스트는 변경하지 않았고 검증용 임시 테스트를 삭제했다. 전체950건 suite, 릴리스 preflight, 운영 효과 및 실제 청구액 검증은 이번에 다시 수행하지 않았다. 12시간 주기·즉시 재개·저장 글 재조회 방지와 운영 설정 변경·배포·신규 유료 호출 보류를 유지한다.

최종 집계: Standards P2 1건·P3 1건(최악P2), Spec P2 1건(최악P2). 위3건은 아직 수정하지 않은 열린 지적이다.

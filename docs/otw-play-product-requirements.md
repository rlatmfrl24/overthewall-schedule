# OTW Play 제품 요구사항

기준: 2026-09-17, 구현 기준 `58cb3f7e26146614b0af06dc4cc61ab086a35702`.
이 문서는 현재 제품 계약이다. 개발·운영 상태는 [통합 상태표](development-status.md),
화면의 세부 규칙은 [UI/UX](otw-play-ui-ux-design.md), 저장·권한 경계는
[시스템 설계](otw-play-system-design.md)를 따른다. 구현 사실과 운영 검증 완료는 구분한다.

## 제품과 접근 범위

OTW Play는 곡, 가창 기록, 참여자, 재생 소스와 채널을 분리한 음악 카탈로그다.
로그인 회원에게 공식 오리지널·공식 커버 검색, 곡 상세, YouTube 재생과 개인 비공개
플레이리스트를 제공한다. 노래 클립 탐색은 현재 관리자에게만 제공한다.

- `/api/play/config`는 익명 조회가 가능하지만 카탈로그 API는 인증이 필요하다.
- `public_read_enabled`는 일반 회원 열람 활성화, `navigation_visible`은 진입점 노출을
  제어한다. 익명 음악 서비스 또는 Play 검색 색인 허용 flag로 해석하지 않는다.
- 관리자 preview는 서버의 관리자 권한 검사 후 허용한다. UI만으로 권한을 판정하지 않는다.
- 회원 제안 `/play/submit`, `/play/submissions`는 카탈로그 공개 flag와 분리한다.
  본인 제안만 조회·수정·철회하며 관리자 검수와 게시 권한은 부여하지 않는다.
- 외부 참여자는 카탈로그 identity로 보존하며 임의 공개 프로필을 생성하지 않는다.
  전 소속 멤버는 외부 참여자로 표시하고 현재 멤버 오시마크를 붙이지 않는다.

## 탐색과 멤버 연결

현재 탐색은 발견, 곡 검색, 플레이리스트와 관리자용 노래 클립이다.
곡명·별칭·원곡 가수·참여자 검색, URL 필터와 cursor pagination을 유지한다.
검색 relevance가 우선이며 선택 정렬은 동점 해소에 사용한다. 입력 상한·enum·cursor 오류를
조용히 보정하지 않는다. 정확한 전체 건수나 facet count를 필수로 요구하지 않는다.

발견의 멤버 항목과 개인 프로필의 Play 링크는 `/play/songs`에 member UID 필터를
전달한다. 곡 수나 과거 `pageEligible` 조건으로 발견의 멤버 진입을 막지 않는다.
개인 프로필 링크 노출은 두 Play flag를 따른다. 숫자형 UID도 문자열로 직렬화한다.

기존 `/play/members/{memberCode}`는 활성 멤버의 필터 검색으로 HTTP 301 / 클라이언트
replace 이동한다. 과거 필터·cursor는 버리고 대소문자·끝 슬래시를 정규화한다.
없는 멤버·비활성 멤버는 404, 조회 장애는 재시도 가능한 오류로 구분한다.
멤버 필터 검색은 `noindex,nofollow`, canonical `/play/songs`, sitemap 제외다.
기존 개인 프로필의 index·sitemap 정책은 유지한다. 과거 멤버 API·DTO·DB는 호환용으로
남아 있으며 독립 노래책 UI를 복원하거나 schema를 제거하는 근거로 사용하지 않는다.

## 카탈로그와 재생 불변 조건

- `music_songs.is_otw_original`은 명시적 곡 속성이다. 채널이나 가창 관계에서 추정하지 않는다.
- 동일 source segment는 하나의 가창 identity에만 연결한다. metadata 수정으로 dedupe
  identity를 재생성하지 않는다. source 관계는 방향을 가지며 역방향을 자동 생성하지 않는다.
- 채널과 entity 연결은 소유·소속 관계 자체를 나타낸다. alias 종류는 선택적 metadata다.
- publication, review, health 상태는 독립적이다. 등록·Ready·draft 변환을 게시로 간주하지 않는다.
- 공식 커버는 승인·활성 공식 채널, 최신 영상·채널·재생 가능성, 관리자의 가창 credit 확인을
  거쳐 게시한다. 임의 업로더를 가창자로, 업로드일을 방송일로 추정하지 않는다.
- 목록·player·queue의 compact credit은 메인 보컬 중심이고 상세에서는 보조 credit을
  역할별로 보존한다. 역할·참여자 필터는 동일한 가창 row에서 동시에 만족해야 한다.
- 음악 태그는 곡의 다중 분류이며 가창 관계·공개 형태·참여 형태와 분리한다.
- Play-scoped 단일 YouTube iframe을 사용한다. visible host가 없으면 재생하지 않는다.
  닫기·화면 이탈 정책은 pause/stop/destroy 경계를 보존하고 숨은 재생을 만들지 않는다.
- queue는 중복 없는 performance 단위이며 versioned `sessionStorage`로 복원한다.
  복원 시 서버에서 다시 검증하고 자동 재생하지 않는다. 전체 삭제는 현재 항목도 제거하고
  재생·세션 저장을 초기화한다. 반복은 중복 row가 아니라 repeat-one/all로 표현한다.
- 노래 클립은 저장된 시작·종료 구간을 사용한다. 다운로드·음원 추출·프록시 재호스팅,
  AI 단독 곡 확정·자동 게시, 검수 없는 회원 게시와 기존 공개 데이터 직접 편집은 금지한다.

## 플레이리스트

기본 모음은 오리지널·커버·멤버별 전체 가창을 사용한다. 최근 대표 24개로 제한하지 않는다.
카드 클릭은 상세 목록 보기이며 대기열 추가는 명시적 행동이다. 전체 페이지를 읽고
동일 revision의 모든 페이지를 모아 기존 queue 순서를 보존하며 중복을 제외해 한 번에 추가한다.
상세 화면의 추가 버튼은 완료 후 목록의 첫 재생 가능한 곡을 처음부터 재생하며, 이미 queue에
있던 곡도 선택한다. 실패·취소·충돌·화면 이탈 때 부분 추가하지 않는다.
다른 가창 버전, 정상 빈 결과, 일부 재생 불가, 전체 중복과 통신 실패를 구분한다.

회원은 기본 모음의 독립 사본 또는 빈 목록을 편집하여 계정별 비공개로 저장한다.
영구 저장은 서버 재조회·재방문 복원·소유권·version 충돌 검사를 포함한다.
철회·삭제된 참조는 이용 불가로 남기고 비공개 metadata를 반환하지 않는다. 개인 응답은
no-store, 개인 페이지는 noindex이며 계정 전환 시 캐시·편집 상태를 제거한다.
대표곡 선택과 순서 변경은 독립적이고, 이용 불가 대표곡은 교체 필요 상태로 안내한다.
세션 queue와 개인 저장 목록은 별개다. 공동·공개 공유 목록, 좋아요·최근 청취·멤버 라디오는
현재 제공 범위로 확대 해석하지 않는다.

## 입력·검수·자동화

직접 등록은 오리지널·공식 커버·노래방송 입력에서 공통 곡/가창 identity를 재사용한다.
노래방송은 `singing_clip` 경로로 구간·가창자·방송일·날짜 근거·원본 출처를 검수한다.
같은 영상의 다음 곡은 영상·구간·가창자·출처 입력을 재사용하되 곡과 완곡 여부를 다시 확인한다.
승인된 clip 채널을 요구하며 채널 관리 진입은 입력을 잃지 않도록 별도 탭으로 제공한다.
구체적 분류·등록·게시 수용 기준은 [노래 클립 계약](otw-play-singing-clips-requirements-and-plan.md)을 따른다.

가져오기는 영상별 후보를 검수한다. Ready 저장에서 새 곡·원곡 가수·외부 가창자를 같은
D1 batch로 materialize하여 다음 행에서 재사용한다. performance draft 변환과 게시는 별도다.
background metadata 갱신은 관리자의 ready/ignored/converted 결정과 입력을 덮어쓰지 않는다.
동일한 review state의 version 갱신과 실제 검수 충돌을 구분하되 채널·분류 정책을 재검증한다.

회원은 공식 커버 또는 편집된 한 곡의 노래 클립을 제안한다. 전체 다시보기의 구간 신청과
오리지널 제안은 제외한다. 장르·방송일·날짜 근거·원본 URL·완곡 여부의 선택 입력과
미확인 값은 관리자 검수로 넘긴다. 제출 제한·idempotency·본인 소유·CAS를 보존한다.
pending_review 수정·철회와 관리자 승인이 충돌하면 먼저 성공한 version을 유지한다.
내부 검수 note·code는 회원 결과나 공개 event로 자동 노출하지 않는다.

승인된 활성 clip 채널은 시간당 uploads polling을 사용한다. 250개 cap, continuation,
watermark, gap, generation, lease, 예산과 명시적 최근 1~20개 backfill을 유지한다.
pause 해제는 최신 기준점을 확보하며 중지 기간을 자동 소급하지 않는다.
WebSub·recent-50 예약은 종료되었다. 과거 DB 이력은 유지한다.
운영 절차는 [polling runbook](operations/channel-upload-polling.md)을 따른다.

Gemini는 관리자 검수 입력의 보조 기능이다. 모델 결과는 명시적으로 적용하며 수동 입력을
보호한다. 자동 승인·게시로 연결하지 않는다. 사용량·실패·품질 검증은
[AI 검수 문서](otw-play-ai-review.md)에 분리한다.

## 완료 판단과 남은 범위

코드·테스트·문서는 실제 진입점 → 검수/저장/게시 → 권위 재조회 → 접근·재생을 대신하지 않는다.
테스트 성공으로 운영 flag·권리·재생 가능성·canary 완료를 추정하지 않는다.
현재 남은 운영·제품 작업과 닫힌 문서 작업은 [개발 상태](development-status.md)를 따른다.
이 문서 정리는 기존 승인 범위를 바꾸거나 새로운 구현 우선순위를 승인하지 않는다.

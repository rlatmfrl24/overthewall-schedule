# OTW Play 노래 클립 요구사항과 구현 계획

기준일: 2026-09-14

상태: 2026-09-14 사용자 정책 확정, 코드 반영 및 자동 검증 완료. 인증된 실제 등록·게시·YouTube 재생 검증은 잔여다. 로컬 마이그레이션 적용 완료. 운영 배포·공개 설정 변경은 하지 않았다. 검증 결과와 한계는 11절에 기록한다.

상위 문서: [제품 요구사항](otw-play-product-requirements.md)의 DEC-081·FR-060~064.
이 문서는 해당 요구사항의 상세안이며 독립 제품이나 병렬 카탈로그의 기준 문서가 아니다.
공통 아키텍처는 [시스템 설계](otw-play-system-design.md), 화면 규칙은
[UI/UX 설계](otw-play-ui-ux-design.md), 출시 절차는 [구현 가이드](otw-play-implementation-guide.md)를 따른다.

## 1. 목적과 권위

멤버가 방송에서 부른 노래 클립을 OTW Play에 수록하고, 사용자가 공식 발표곡과
구분하여 찾고 들을 수 있게 한다. 관리자는 기존 곡을 연결하거나 새 곡을 등록하고,
가창자·구간·출처를 검수한 다음 명시적으로 게시할 수 있어야 한다.

사용자는 7개 정책을 모두 A안으로 확정하고, 노래 클립용과 일반 방송 클립용 키리누키 채널의 관리자 화면·기능을 독립적으로 관리하도록 요청했다. 이후 아래 전체 구현 계획을 명시적으로 승인했다.

- 공통 데이터 공유 + 공식/방송 관리·탐색 분리를 유지한다.
- 2절은 구현 전 분석 당시의 기반 기록이며, 현재 변경과 검증은 11절이 우선한다.
- 8절의 정책은 모두 확정 상태다. 기존 방송 draft 전용 제한은 이번 게시·공개 경로에 한하여 대체한다.
- 운영 공개 여부와 구현·로컬 검증 결과를 분리한다.

## 2. 현재 기반과 차이

확인 기준은 로컬 HEAD `f073720` 및 2026-09-14 작업 디렉터리다. 기존 미커밋 UI 변경이
있는 상태에서 문서와 코드를 읽었다. 이번 작업에서 production 데이터·배포·공개 flag나
브라우저 동작은 확인하지 않았으며 과거 문서의 운영 snapshot을 현재 상태로 사용하지 않는다.

| 영역 | 현재 코드·문서에서 확인한 기반 | 이번 기능에 필요한 확장 |
| --- | --- | --- |
| 공통 모델 | 곡·가창·참여자·영상·가창별 소스/구간이 분리되어 있음 | 기존 identity 재사용, 방송 날짜·출처·완곡 여부 계약 |
| 분류 | 방송 가창은 `relation_type=singing_clip`, `release_type=broadcast`로 고정 (2026-09-15 정책 변경) | 사용자에게 공식 버전과 방송 가창의 차이를 명확히 표시 |
| 자동 후보 | 승인 채널의 `singing_clip` 후보를 검수해 방송 draft로 변환 | 기존 후보에서 전용 클립 작업 영역과 게시까지 자연스럽게 연결 |
| 등록·편집 | 관리자에 방송 draft와 소스 편집 기반이 있음 | 자동 후보가 없어도 URL 직접 등록 가능, 기존 가창의 대체 클립 연결 |
| 공개 | 공개 조회는 `official_mv/official_video`, 소스 선택은 공식 채널 중심 | 방송 게시·공개 조회·소스 선택을 유형별로 확장 |
| 재생 | 단일 player, 세션 큐와 구간 데이터 기반이 있음 | 클립 resolve·구간 종료·재시도·전환의 실제 사용자 흐름 검증 |
| 저장 목록 | 개인 목록은 `performanceIds`를 보존 | 세션 큐와 별도로 방송 항목의 저장·재열기 지원 범위를 결정 |

주요 근거:

- [공통 스키마](../db/schema/index.ts), [Play 계약](../contracts/otw-play.ts), [개인 목록 계약](../contracts/otw-play-playlists.ts).
- [후보 변환 서비스](../worker/features/otw-play/application/ingestion-service.ts): 승인 채널·유형 확인 후 draft 생성.
- [관리자 서비스](../worker/features/otw-play/application/admin-catalog-service.ts), [관리자 저장소](../worker/features/otw-play/infrastructure/d1-admin-catalog-repository.ts): 방송 draft 제한, 공식 소스 중심 게시·공개 상태 편집 조건.
- [공개 조회](../worker/features/otw-play/infrastructure/d1-public-catalog-reader.ts), [공개 소스 선택](../worker/features/otw-play/domain/public-source-selection.ts): 공식 범위의 조회·재생 정책.
- [현행 채널 수집 계약](operations/channel-upload-polling.md): 시간당 uploads playlist 조회를 재사용한다. 종료된 WebSub을 재도입하지 않는다.

현재 draft가 있다는 사실은 클립 공개 기능의 완료 증거가 아니다. 단순히 UI 게시 버튼이나
공개 SQL의 release 조건 하나만 풀면 저장·편집·resolve·캐시·소스 정책이 서로 어긋날 수 있다.

## 3. 범위와 관리 방식

### 3.1 선택 근거

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 데이터·화면 모두 통합 | 단일 등록·검색 흐름 | 클립 증가 시 공식 발표 버전이 묻히고 검수 기준이 섞임 | 기본 경험으로 부적절 |
| 데이터·화면 모두 분리 | 각 영역 독립 운영 | 곡·가수 중복, 정보 불일치, 공식/방송 버전 연결 비용 | 현재 범위에 과도함 |
| 공통 데이터 + 관리·탐색 분리 | 곡 재사용과 유형별 운영을 함께 지원 | 유형별 정책·조회 범위가 필요 | 구현 기준안 |

### 3.2 첫 전달 범위

- 관리자 공식 곡/노래 클립 작업 영역 분리와 클립 URL 직접 등록.
- 기존 자동 후보 검수→클립 draft 연결. 자동화 활성화나 신규 업로드 대기를 수동 등록의 전제로 두지 않음.
- 기존 곡 검색·선택 또는 새 공통 곡 생성, 실제 가창자·역할·구간·출처 검수.
- 기존 방송 draft 재사용·보완, 명시적 게시·철회, 저장·게시 결과의 서버 재조회.
- 사용자 노래 클립 목록·곡/멤버 검색·방송일 필터와 가창 상세 접근.
- 공통 곡 상세의 공식/방송 버전 구분. 공식 가창이 없는 곡도 방송 탭에서 상세 접근 가능.
- 공개 가창 resolve와 단일 player·세션 큐를 통한 선택 구간 재생.
- 승인 해제·영상 삭제/비공개·재생 불가와 draft/철회의 공개 경계 처리.

초기 재생 소스는 기존 기반과 DEC-002에 맞춰 승인된 YouTube 키리누키를 우선하는 안이다.
정확한 허용 채널·원본 요건과 부분 가창 범위는 8절에서 결정한다.

### 3.3 후속 범위

방송별 setlist·전체 방송 연속 재생, 원본 방송만으로 공개/재생하는 경로, CHZZK 직접
재생, 회원 클립 제안, 자동 가창 인식, 가창 횟수 순위·추천은 첫 전달에 자동 포함하지 않는다.
좋아요·최근 감상·공유/공동 편집도 별도 기능이다. 개인 저장 목록에 클립을 넣는 기능은
CLIP-TBD-06에서 범위를 정하고 저장·재열기까지 함께 완성한다.

다만 원본 방송 출처를 보존할 수 있는 데이터 경계는 처음부터 유지한다. 후속 setlist를
만들기 위해 곡·가창·영상의 identity나 권위를 다시 정의해야 하는 구조는 채택하지 않는다.

## 4. 화면과 주요 사용자 흐름

### 4.1 관리자

```text
OTW Play 관리
  공식 곡: 오리지널 / 공식 커버
  노래 클립: 목록 / 새 클립 등록 / 기존 후보 검수 연결
  공통 관리: 곡 정보 / 가창자 / 승인 채널 / 소스 상태
```

이는 작업 영역 구분이며 최종 메뉴의 개수·위치는 기존 관리자 레이아웃에 맞춰 정한다.
현재 후보함을 복제하지 않고 같은 후보를 전용 등록 흐름으로 연결한다.

1. `새 클립 등록`에서 URL 입력 또는 기존 후보의 `검수·등록`으로 시작한다.
2. 영상 metadata와 출처 채널을 확인한다. 채널 미승인은 원인과 기존 승인 채널 관리로
   이동하는 경로를 제공하며, 단순 등록·후보 수집을 승인으로 간주하지 않는다.
3. 곡명·별칭·원곡 가수로 기존 곡을 검색한다. 없으면 새 곡을 명시적으로 만들며,
   공식 버전 등록 여부를 요구하지 않는다. 영상 제목을 곡의 확정 제목으로 자동 사용하지 않는다.
4. 실제 가창자와 역할, 노래 클립 관계, 방송일·근거·원본 출처,
   완곡/일부 가창, 시작·종료 위치를 검수한다. 채널 운영자를 가창자로 자동 확정하지 않는다.
5. 같은 곡·멤버·방송의 기존 가창을 확인한다. 동일 실제 가창이면 해당 가창에 source를
   추가하고, 다른 방송/다른 가창이면 새 performance로 등록한다. 자동 병합하지 않는다.
6. draft 저장 후 서버 결과를 재조회한다. 다음 등록에서 같은 곡·가창자를 재사용할 수 있어야 한다.
7. 게시 조건을 충족하면 관리자가 명시적으로 게시한다. 관리자 상태와 공개 조회를 다시
   읽어 완료를 표시한다. 실패·version 충돌은 입력을 보존하고 재검수 지점을 안내한다.

직접 등록과 후보 변환은 같은 카탈로그 검증·저장 경계를 사용한다. 기존 방송 draft는
목록에서 찾아 부족한 정보를 보완한 뒤 같은 게시 흐름을 사용한다. 새로 수집한 후보만
게시할 수 있도록 제한하지 않는다.

공통 곡 편집 시 여러 공식/방송 가창에 반영된다는 영향을 표시한다. 클립 목록에서
제거하는 동작이 공통 곡 삭제가 되지 않게 하고, 게시 상태·참조 제약과 명시적 철회 경계를 유지한다.

### 4.2 사용자

```text
OTW Play → 노래 클립 → 멤버/곡/방송일 탐색 → 가창 선택 → 구간 재생 또는 큐 추가
                                 └→ 공통 곡 상세 → 공식 버전 / 방송에서 부른 버전
```

- 목록은 영상 업로드 건수가 아니라 가창을 중심으로 표시한다. 곡명, 가창자, 방송일 또는
  미확인 표시, 완곡 여부, 구간 길이, 출처를 식별할 수 있어야 한다.
- 대표 클립과 대체 클립은 같은 가창 상세에서 구분한다. 다른 클립을 선택해도 실제 가창
  identity를 바꾸지 않으며, 소스마다 다른 시작·종료 위치를 적용한다.
- 기본 정렬은 카탈로그 공개 최신순이다. 방송일 필터는 방송일이 확인된 항목에
  적용하고 미확인 항목은 별도 선택으로 찾을 수 있게 한다. 미확인 방송일을 별도로 필터링한다.
- 공식 곡 기본 목록·검색·기본 오리지널/커버/멤버 모음과 기존 SEO 집계는 공식 범위를
  유지한다. 클립 공개만으로 기존 공식 곡 수나 멤버 노출 임계값을 늘리지 않는다.
- 곡 상세의 공통 identity는 유지한다. 공식 버전 0개·방송 버전만 있는 경우에도 노래
  클립 탭에서 접근·재생 가능해야 하며, 공식 버전 영역은 빈 상태를 명확히 표시한다.
- 탭 전환·뒤로가기는 player와 현재 재생 위치를 유지한다. Play 이탈·닫기의 기존
  pause/cleanup 계약은 유지하고 별도 iframe/player를 만들지 않는다.
- 로딩·0건·오류·비공개·재생 불가를 구분하고, 모바일 필터와 키보드 조작에서도 같은 흐름을 제공한다.

## 5. 데이터와 분류 설계

### 5.1 재사용할 권위 모델

| 단위 | 책임 | 예시 |
| --- | --- | --- |
| song | 작품 identity, 곡명·원곡 가수·별칭·OTW 오리지널 여부·공통 태그 | A곡 1개 |
| performance | 특정 실제 가창, 가창자·역할·관계·공개/품질 상태 | 공식 커버, 9/1 방송 가창, 9/10 방송 가창 |
| media source | 영상 identity·채널·업로드일·가용 상태 | 키리누키 영상 또는 원본 영상 |
| performance source | 해당 가창을 담은 소스와 시작/종료 위치·대표 여부 | 클립 00:12~04:03, 원본의 대응 구간 |
| source relation | 원본/발췌 등 영상 간 출처 관계 | 클립이 어느 원본 영상에서 발췌되었는지 |

`music_songs`는 공식 버전과 클립이 공유한다. 2026-09-15 확정 정책에 따라
방송 가창의 `relation_type`은 `singing_clip`, `release_type`은 `broadcast`로 고정한다.
클립을 커버·오리지널로 검수하지 않으며, 곡 자체의 `is_otw_original`과 소스 역할은 별도로 유지한다. 공식 채널이 올린 방송 클립도
내용이 방송 가창이면 공식 발표 버전으로 자동 분류하지 않는다. 해당 채널의 수록 허용은
CLIP-TBD-04에서 결정한다.

다른 날 같은 노래를 부르면 별도 performance다. 같은 실제 가창을 편집한 두 영상은
관리자 확인 후 같은 performance에 연결한다. 곡명·가창자 일치만으로 같은 가창이라
판정하지 않고, 현재 immutable dedupe key와 `(source_id, start_seconds)` 중복 제약을 보존한다.

### 5.2 추가 정보와 저장 경계

가창의 `broadcast_metadata` JSON에 `performedOn`, `dateEvidence`, `originalUrl`, `extent`를 저장한다. 최초 카탈로그 공개 시각은 `catalog_published_at`으로 분리한다. 날짜 정밀도는 날짜 또는 미확인으로 제한하며 시간대를 추정하지 않는다. migration `0089_ambitious_titania.sql`은 두 컬럼과 공개 정렬 인덱스를 추가한다.

| 정보 | 저장 위치 | 규칙 |
| --- | --- | --- |
| 방송일, 확인 근거 | `broadcast_metadata.performedOn` / `dateEvidence` | YYYY-MM-DD 또는 null. 클립 업로드일을 대입하지 않음 |
| 완곡/일부/미확인 | `broadcast_metadata.extent` | full / partial / null. 게시 전 full 또는 partial을 확인하며 영상 길이로 추론하지 않음 |
| 원본 방송 URL | `broadcast_metadata.originalUrl` | HTTPS URL 또는 null. 원본 링크는 참고 출처이며 별도 재생 소스로 자동 추가하지 않음 |
| 영상 업로드 시각 | 기존 media source | 방송일과 독립 보존 |
| 시작/종료 초 | 기존 performance source | 소스마다 독립. 정수, 0 이상, 종료 > 시작, 확인한 영상 길이 이내 |
| 카탈로그 최초 공개 시각 | `catalog_published_at` | 방송 가창의 명시적 게시 시 저장하며 수정·대표 영상 변경 시 유지 |

방송별 집계 테이블은 첫 전달의 필수 조건이 아니다. 방송 metadata를 song이나
후보 JSON에만 저장하지 않고 가창에 종속하여 권위 있게 보존한다. 같은 가창의 원본 출처는
편집 클립을 교체하더라도 남아야 한다. 기존 공식/방송 행의 미확인 정보를 추정하여 일괄 채우지 않는다.

### 5.3 이행과 데이터 무결성

- 기존 song/performance/source ID, 공개 상태, 후보 연결, 개인 목록 참조를 보존한다.
- 기존 draft는 자동 게시하지 않는다. 부족한 방송 metadata를 노래 클립 목록에서 보완한다.
- 확장 필드는 공식 가창에 불필요한 입력을 강제하지 않는다. 새 제약은 기존 행과
  미확인 상태를 검토한 additive migration으로 적용한다.
- 생성·검수·게시·철회는 현재 CAS, 권한, 감사 event, catalog/read-model revision과
  원자 저장 경계를 유지한다. 중복 제출·재시도·동시 검수로 곡/가창을 중복 생성하지 않는다.
- 운영 schema를 바꾸기 전 실제 컬럼과 migration 적용 상태를 확인한다. 번호는 현행
  schema에서 생성하며 문서 단계에서 migration 파일이나 production 변경을 만들지 않는다.

## 6. 게시·조회·재생 계약

### 6.1 게시와 소스 정책

방송 draft의 게시 제한을 해제할 때는 유형별 정책을 명시한다. 공식 영상의 허용 소스
집합에 키리누키를 무조건 추가하지 않는다. 관리자 게시·게시 후 수정·공개 조회·resolve가
같은 승인 상태·가창 유형·소스 역할 규칙을 적용해야 한다.

게시 조건은 곡 연결, 실제 가창자, 검수된 유효 구간, 승인된 활성 채널, 허용 재생 소스와
8절에서 확정한 방송일·원본·가창 범위 요건이다. 채널 승인과 개별 게시 승인은 별개다.
기존 공개/품질/가용 상태를 유지하고 후보 검수 상태와 하나로 합치지 않는다.

철회 또는 채널 승인 해제 후에는 해당 항목/소스가 목록·상세·resolve·캐시에서
계속 재생 대상으로 제공되지 않아야 한다. 다른 허용된 승인 소스가 있는 경우의
선택은 확정된 방송 정책을 따른다. 클라이언트의 기존 큐도 재검증 실패를 처리해야 한다.

### 6.2 조회와 API 영향

| 소비자 | 목표 계약 |
| --- | --- |
| 공식 목록·검색·기본 모음 | 기존 기본 범위를 유지하며 방송 가창 자동 포함 금지 |
| 노래 클립 목록 | 방송 가창만 조회, 멤버·곡·방송일 조건과 결정적 정렬·cursor 제공 |
| 공통 곡 상세 | 같은 song의 공식/방송 가창을 구분하고 각각 공개 조건을 적용 |
| 가창 resolve/player | 명시적 performance ID를 공개 정책으로 재검증하고 해당 소스 구간 반환 |
| 관리자 목록 | 공식/방송별 작업 범위, draft·게시·철회와 보완 필요 정보 구분 |
| 개인 저장 목록 | CLIP-TBD-06 결정에 따라 write 검증과 resolve·재열기를 함께 지원하거나 UI에서 미지원 표시 |
| SEO·멤버 집계 | 기존 공식 범위 유지. 클립 신규 색인/집계는 CLIP-TBD-07에서 별도 결정 |

구현 때 기존 query의 명시적 범위 필드와 전용 조회 경로 중 최소 변경안을 고른다.
어느 쪽이든 목록·상세·resolve와 프런트 API/Query를 함께 연결하며 DTO만 추가하지 않는다.
캐시와 Query key에는 조회 범위·필터·revision을 포함하고 게시·철회·승인 변경이 관련
공개 조회를 갱신하도록 한다. 관리자 preview가 공개 제한을 우회해 성공한 것을 익명 공개의
성공으로 기록하지 않는다.

### 6.3 재생과 대기열

- 기존 단일 player와 큐를 확장한다. 큐의 identity는 performance 기준으로 유지한다.
  같은 곡의 다른 방송 가창은 독립 항목이고 같은 가창의 대체 소스는 새 큐 항목이 아니다.
- 저장된 구간 시작에서 재생하고 종료 시 기존 반복/다음 항목 정책을 적용한다.
  seek·일시정지/재개·반복·소스 전환 후에도 구간 경계를 지킨다.
- 재생 불가 소스는 가용 상태와 사용자 피드백을 갱신한다. 무한 자동 재시도나
  미승인 원본으로의 자동 전환을 만들지 않는다.
- 공식 기본 모음의 전체 추가에는 방송 항목을 자동으로 섞지 않는다. 사용자가
  명시적으로 선택한 공개 클립은 현재 세션 큐에 추가할 수 있다.
- 개인 저장 목록 확장을 포함하지 않는 경우 클립에 저장 성공 UI를 제공하지 않는다.
  세션 큐 추가를 영구 저장 완료로 표현하지 않는다.

## 7. 구현 순서와 영향 파일

모든 단계는 같은 song→performance→source 모델과 실제 관리자/사용자 진입점을 유지한다.
내부 단계 완료를 기능 출시로 표시하지 않는다. 게시만 열고 공개 조회·재생이 없는 상태를
중간 사용자 릴리스로 제공하지 않는다.

| 단계 | 작업 | 완료 증거 |
| --- | --- | --- |
| 0. 정책·계약 정리 | CLIP-TBD-01~04를 해결하고 05~07의 초기 포함 여부 결정. 기존 draft·제약·소비자 확인 | 확정된 결정과 초기 범위, 현행 코드/데이터에 대한 영향 목록 |
| 1. 공통 데이터·관리 흐름 | 필요한 additive schema, URL 등록, 기존 후보/draft 연결, 곡 재사용, 소스 추가, metadata 보완 | 실제 관리자 등록/후보 검수→draft 저장→서버 재조회, 다음 항목에서 ID 재사용 |
| 2. 게시·공개 수직 흐름 | 방송 게시/수정/철회 정책과 노래 클립 목록·곡 상세·resolve·캐시·player를 함께 연결 | 실제 게시→익명 또는 승인된 공개 환경의 탭 진입→가창 재생·큐 추가, 철회 후 재조회 |
| 3. 회귀·운영 전달 | 공식 범위·권한·중복·원자성·구간·모바일 검증, migration/배포 절차와 복구 기록 | 9절 수용 기준 증거, 관련 commit/artifact와 실제 운영 확인 결과 |

주요 변경 후보는 다음과 같다. 경로의 존재와 책임은 확인했지만 변경 파일 목록은
구현 직전에 다시 확정한다. 기존 미커밋 player·목록 작업은 보존하고 최종 버전에 통합한다.

- `contracts/otw-play.ts`, `contracts/otw-play-playlists.ts`: 목록·상세·resolve·관리자 metadata와 저장 목록 계약.
- `db/schema/index.ts`, `drizzle/`: 필요한 방송 metadata와 검증 제약의 additive 확장.
- `worker/features/otw-play/application/` 및 `domain/`: 관리자/후보 처리, 유형별 공개·소스 정책.
- `worker/features/otw-play/infrastructure/d1-admin-catalog-repository.ts`: 생성·수정·게시·철회와 원자 검증.
- `worker/features/otw-play/infrastructure/d1-public-catalog-reader.ts`: 방송 목록·상세·resolve, 공식 범위 보존.
- `worker/features/otw-play/http/`, `worker/app/routes.ts`: 입력 검증과 명시적 API 등록.
- `src/features/otw-play/ui/admin/workflow-catalog.tsx`와 관리자 등록 UI: 분리된 작업 영역과 동일 곡/가창 연결.
- `src/features/otw-play/ui/public/`, `src/routes/play/`: 노래 클립 진입·탐색·공통 곡 상세.
- `src/features/otw-play/queries/`, `src/features/otw-play/model/play-queue.ts`, player/provider: 조회 범위, 큐 identity, 구간 재생.

실제 구현에서는 API 변경 시 `worker-api-change`, schema 변경 시 `db-migration`,
출시 검증 시 `release-ops`의 현행 저장소 지침을 적용한다. 이번 문서화는 API/schema
변경이나 출시 실행이 아니며 테스트용 우회 endpoint나 별도 재생 harness를 계획하지 않는다.

| CLIP-AC-09 | 실패·중복 제출·동시 검수/게시 | 입력 보존, CAS 충돌 표시, 부분 저장/가짜 성공/중복 identity 없음. D1 실패 후 실제 잔여 데이터 확인 |
| CLIP-AC-10 | 모바일·키보드·0건/조회 실패 | 사용자/관리자 의도된 진입점으로 접근, 필터·구간·버튼 사용 가능. 오류와 빈 결과 구분 |
| CLIP-AC-11 | 방송일·원본·가창 범위 미확인 | 확정한 정책대로 저장/게시/표시. 영상 제목이나 업로드일이 권위 값으로 자동 승격되지 않음 |
| CLIP-AC-12 | 개인 저장 목록 포함 시 저장·재열기 | 같은 performanceIds와 순서 보존, 계정 소유권·CAS 유지, 철회 항목의 가용 상태 표시 |

테스트는 순수 분류·게시 조건, 입력/권한, D1 CAS·원자성·FK·공개 조회 격리,
UI 입력 보존·탐색·큐 연결을 지원한다. 실제 결함이 발견되면 해당 결함을 재현하는
최소 회귀 테스트를 추가하고 같은 사용자 흐름으로 다시 확인한다.

실제 흐름 검증은 기존 관리자 화면과 사용자 탭을 사용한다. D1 조회나 API 직접 호출은
그 흐름의 저장 결과를 입증하는 보조 증거이며 필수 검수·명시적 게시를 우회하지 않는다.
배포 identity, 공개 flag, 검증 환경을 기록하고 로컬 preview 성공을 production 공개 성공으로 표현하지 않는다.

구현 시 영향에 맞춰 architecture/typecheck/lint/단위·Worker 통합/build 및 저장소가
요구하는 release 검증을 실행한다. 방송 공개의 완료는 테스트뿐 아니라 실제 게시·공개
진입·구간 재생·철회 readback까지 확인한 경우에만 기록한다.

## 10. 출시와 복구

- 실제 배포 전 적용 대상 commit, migration, 공개/자동화 설정의 현재 값을 확인한다.
  문서의 과거 운영 값을 추정하여 적용하지 않는다.
- 필요한 migration과 기존 draft 보존을 확인한 뒤, 게시·조회·재생 소비자가 함께
  준비된 코드로 전달한다. 새 메뉴만 노출하거나 관리자의 강제 DB 변경으로 공개하지 않는다.
- 초기 검증은 수록 정책을 충족하는 대표 항목으로 수행하되, 그 항목이나 특정 채널을
  코드에 고정하여 일반 URL 등록·검색 능력을 대신하지 않는다.
- Play 전체 공개 flag의 의미는 유지한다. 특정 클립 철회 또는 해당 Play 채널 승인 해제·비활성화로 클립 조회와 재생 후보를 차단한다. 전체 Play 비공개는 기존 전체 공개 설정을 사용한다.
- 복구 시 검수된 곡·가창·source identity를 삭제하거나 공식 상태를 변경하지 않는다.
  노출/게시 정책의 되돌림과 additive schema 데이터 보존을 분리한다.

## 11. 구현·검증 기록

- 채널 등록 저장소를 유지하고 관리자 공식/노래 클립/방송 피드 진입점을 분리했다.
- 방송 metadata 저장, 검수 draft 보완, 게시·게시 후 수정·철회와 유형별 공개 source 정책을 연결했다.
- `/play/clips` 목록·멤버/곡/방송일 검색·미확인 필터, 공통 곡 상세, 기존 단일 플레이어·현재 대기열을 연결했다.
- 공개 기본 scope는 official이다. 방송 목록은 scope=broadcast, 공통 상세와 세션 대기열 resolve는 all을 사용한다. 개인 저장 검증은 official로 유지한다.
- 기존 performance의 dedupe identity는 편집·대표 영상 변경 때 재계산하지 않는다. 같은 가창의 다른 영상만 대체 영상으로 연결한다.
- 전체 migration 89건을 임시 D1에 적용해 검증한 뒤 기존 로컬 D1에 0089만 추가 적용했다. 로컬 D1 doctor는 blocking failure 없이 완료했다.
- 운영 DB·배포·공개/자동화 설정은 변경하지 않았다. 로컬 실제 브라우저에서 `/play/clips`의 로그인 안내 진입과 페이지 오류 없음은 확인했다. 공개 flag가 꺼져 있고 인증된 관리자 브라우저 제어를 사용할 수 없어 실제 관리자 등록·게시와 YouTube 재생까지 확인한 것으로 기록하지 않는다.
- Node 24.20.0에서 전체 단위·Worker 통합 테스트 283개 파일 / 2,104개 테스트가 통과했다. `typecheck:test`, `lint`, `build`, `architecture:check`, `sync:agent-cursor:check`도 통과했다.
- D1 통합 검증은 기존 방송 draft 보완→게시→공개 DTO 구간 조회→게시 후 대체 영상 편집→다른 방송의 동일 곡 분리→승인 해제·철회와 CAS 실패 시 기존 값 보존을 확인했다. 기본 official 목록·개인 저장 대상 resolve·사이트맵에는 클립이 포함되지 않는다.
- 동일 YouTube 채널을 방송 피드 저장소와 Play에 등록한 뒤 Play 중지·삭제와 방송 피드 수정·삭제가 서로 영향을 주지 않는 것을 실제 D1 저장소 호출과 readback으로 확인했다.
- 화면 테스트는 직접 URL 등록·새 곡 입력·수집 없이 draft 저장, 미확인 날짜/원본·일부 가창 표시, 멤버/방송일 필터, 공통 대기열 연결과 게시 상태 재확인을 검증했다. 테스트의 모의 YouTube 플레이어는 실제 YouTube 재생 성공을 증명하지 않는다.
- 전체 검증은 현재 작업 디렉터리의 미커밋 변경 기준이다. 기존 사용자 변경을 유지했으며 커밋·푸시·배포는 수행하지 않았다.

- 재생 직전 확인 응답이 늦게 도착하는 동안 사용자가 일시 정지하거나 플레이어를 숨긴 경우 자동으로 재생을 다시 시작하지 않도록 요청 의도와 표시 상태를 확인한다. 일시 정지 경계 회귀 테스트를 추가했다.

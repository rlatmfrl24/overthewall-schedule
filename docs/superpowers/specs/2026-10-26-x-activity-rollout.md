승인 출처: `북마크 링크 점검 방향 검토` 채팅 `01a16156-17b5-7e20-904d-a4509d78c9cb`.
사용자 메시지 `01a175e5-061e-7e72-8183-7fde9c928a06`의 `PLEASE IMPLEMENT THIS PLAN`과 이 채팅 계속 진행 선택을 원문으로 직접 확인했다.
기존 1명·로컬 구현 및 운영 활성화 보류는 아래 승인으로 갱신한다. 다른 북마크·수집 작업은 포함하지 않는다.

# 양 사이트 X 수집을 웹훅 중심으로 전환

## 1. 확정한 운영 방식

- OTW·LuvDia에서 현재 수집이 허용된 **전체 활성 멤버**를 웹훅 구독 대상으로 한다. 비공개·제외 멤버와 사이트 수집 중지 상태는 유지한다.
- 신규 게시물은 웹훅으로 수집하고, 기존 정기 수집은 **24시간 간격의 누락 보완 수집**으로 변경한다.
- X 비용은 **양 사이트 합산 UTC 하루 $1 목표**로 관리한다. 기존 자동충전과 공급자 주기 $30 한도는 변경하지 않는다.
- 예산 소진에 따른 중지는 다음 UTC 날짜에 자동 재개한다. 사용자 직접 중지·사이트 운영 중지는 자동 해제하지 않는다.
- 별도 멤버 시범 운영이나 사진·영상 자연 발생 대기 없이 전체 대상에 적용한다.

## 2. 구독·수신 구조

- 현재 1명 전용 상태를 다중 멤버 구조로 확장한다. 구독 상태와 사이트별 수집 대상을 분리하고, 기존 상태는 추가 마이그레이션으로 이전한다.
- **OTW Worker를 공유 구독 관리 지점**으로 사용한다. 같은 X `user_id`는 한 번만 구독하고, 양 사이트에 속한 계정의 이벤트는 허용된 사이트에 각각 전달한다. 중복 구독을 피하고 소유하지 않은 구독은 변경하지 않는다. [X 구독 규칙](https://docs.x.com/x-api/activity/introduction)
- 사이트 간 전달과 제어는 공개 HTTP 중계 대신 사이트가 고정된 비공개 Service Binding RPC로 연결한다. 각 사이트는 자신의 멤버·공개 정책을 다시 확인하고 자신의 DB·Queue에 저장한다. [Cloudflare RPC](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/)
- 서명 검증 → 내구성 수신함 → 기존 Queue → 기존 게시물 저장·피드 경로를 유지한다. 재전송과 재시도는 중복 저장·중복 비용 기록을 만들지 않는다.
- 웹훅 원본으로 처리 가능한 본문·미디어는 그대로 사용한다. 정보가 부족한 게시물 ID만 보강 조회한다. 사용자 ID가 캐시에 없는 멤버도 예산 내 조회로 등록하며, 캐시 유무를 구독의 전제조건으로 삼지 않는다.
- 멤버 추가·제외·공개 상태 변경을 기존 cron에서 구독 목록과 동기화한다. 등록 실패는 대상별로 표시하고 나머지 등록은 계속한다.

## 3. 공통 예산과 누락 보완

- 공유 예산 장부를 OTW D1에 두고, **양 사이트의 웹훅 이벤트·보강·주기 수집·수동 X 조회·참조 조회**를 합산한다. 기존 사이트별 원장은 관측용으로 보존한다.
- 유료 X 조회는 공통 게이트웨이에서 원자적으로 예산을 예약한 뒤 실행한다. 공통 장부를 사용할 수 없으면 유료 호출을 중지하며, 사이트별 직접 호출로 우회하지 않는다.
- 전환 시 양 사이트의 당일 사용액·예약액과 이미 확인된 별도 검증 비용을 반영한다. 당일 사용액을 0으로 초기화하지 않는다.
- 한도에 접근하면 유료 보강과 신규 구독 등록·갱신을 멈추고 소유한 활성 구독을 해제한다. 실패한 해제는 재시도하고, 구독 만료시간도 유지한다.
- 공급자가 전달한 이벤트 비용은 이미 발생한 비용으로 기록한다. **하루 $1은 강제 상한이 아니며 전달 중인 이벤트로 초과할 수 있다.** [공식 이벤트 요금](https://docs.x.com/x-api/activity/event-pricing)
- 예산 중지 상태만 다음 UTC 날짜에 자동 재개한다. 미처리 보강과 등록 작업도 새 예산 안에서 이어간다.
- 24시간 누락 수집은 기존 REST 완료 커서 이후를 이어 읽는다. 웹훅 도착으로 이 커서나 전체 스캔 완료시각을 전진시키지 않는다. 예산·장애로 중단되면 완료로 표시하지 않고 다음 실행에서 이어간다.

## 4. 관리자 화면과 인터페이스

- 기존 X 관리 화면에 전체 적용·중지·재개와 사이트별 대상 수, 활성 구독 수, 등록 실패, 최근 수신, 누락 수집 진행 상태를 표시한다.
- `GET /api/x/activity` 응답에 다중 구독 목록, 사이트별 진행 요약, 공통 예산, 중지 사유와 재개 예정시각을 추가한다.
- 기존 시작·중지 API를 전체 대상 제어로 확장한다. 대상은 서버의 활성 멤버 목록에서 계산하며 임의 계정·콜백 URL을 받지 않는다.
- 운영 상태는 `정상 / 등록 중 / 일부 실패 / 예산 중지 / 사용자 중지`를 구분한다. 일부 등록이나 Queue 접수만으로 전체 전환 완료를 표시하지 않는다.

## 5. 운영 반영과 완료 기준

1. 진행 중인 X 구현을 보존하면서 다중 멤버·공통 예산 변경을 한 릴리스로 통합한다. 다른 북마크·수집 작업은 포함하지 않는다.
2. 기존 Worker와 호환되는 추가 마이그레이션을 적용하고, 공유 제어 지점과 양 사이트 Worker를 배포한다. 합산 예산 준비 전에는 새 유료 수집을 활성화하지 않는다.
3. 기존 배포 경로의 빌드·자동 CI를 사용한다. 별도의 유료 검증, canary, 표본 관측이나 장시간 검증 단계는 추가하지 않는다.
4. 공통 예산을 초기화한 뒤 전체 대상 등록을 시작하고, 기존 수집 간격을 24시간으로 변경한다.
5. 배포 버전·마이그레이션 적용·대상 대비 실제 구독 수·주기 설정·공통 예산 상태만 운영 반영 결과로 확인한다. 이후 자연 게시물·미디어와 장기 수집 품질은 사용자가 관찰한다.

변경된 경계의 회귀 범위는 중복 수신·공통 예산 동시 예약·자정 자동 재개·직접 중지 보존·웹훅 누락 후 커서 복구·사이트 간 공개 정책 격리다. 추가 독립 검증 실행 대신 기존 CI에 포함한다.

등록·배포가 실패하면 실패한 범위를 명시하고 기존 커서와 데이터를 보존한다. 복구 과정에서 고빈도 수집을 자동 복원하거나 예산을 높이지 않는다.

현재는 계획만 확정했으며 코드·구독·운영 설정·배포를 변경하지 않았다.

# OTW Play 재개편 코드 리뷰

2026-10-13. 범위는 플레이리스트 작업 큐·50개 검수 화면·관련 Worker/D1 계약이다. 같은 작업 폴더의 Multiview, 일반 정책 문서, Search Console 변경은 제외했다.

## 변경의 결과

관리자는 플레이리스트 정보를 먼저 저장하고, 같은 화면에서 최대 50개씩 AI 초안을 검수한다. 저장한 검수는 묶음 종료 때 비공개 카탈로그로 등록하며 게시 여부는 카탈로그에서 결정한다. 한 개의 활성 묶음, 관리자 완료 후 다음 페이지 준비, 후보 ID·버전 고정, 비용 한도와 기존 Queue를 유지한다.

예상 부하는 1,000–2,000개 플레이리스트, 한 묶음 50개, 여러 관리자 요청과 Queue 재전달이다. 리뷰는 UI 호출자·공유 DTO·Worker 핸들러·서비스·D1·기존 AI/등록 소비자·마이그레이션을 연결해 확인했다.

## 발견하고 수정한 문제

| 우선순위 | 재현 조건과 영향 | 수정 |
|---|---|---|
| P2 | 만료 정보 갱신 중 나중에 이어하기를 선택해도 갱신 응답이 도착하면 검수 화면으로 다시 이동했다. | 시작 위치와 현재 위치가 같은 경우에만 이동한다. |
| P2 | 영상 정보 갱신 실패 시 검수 폼에 진입할 수 없어 해당 항목을 명시적으로 보류·제외하기 어려웠다. | 이번 묶음 목록의 항목 메뉴에서 기존 사유 저장을 실행한다. 만료 정보를 검수 저장하는 우회는 추가하지 않았다. |
| P2 | 다음 묶음으로 완료한 뒤 다른 완료 묶음을 열면 이전 화면의 다음 이동 의도가 새 묶음에 적용됐다. | 로컬 참조를 삭제하고 해당 묶음의 서버에 저장된 다음 이동 요청만 읽는다. |
| P2 | 수집 읽기 예산이 소진되면 준비 중이라는 표시만 남고 5초 조회가 계속됐다. | 기존 예산 조회로 대기·예상 초기화 시각을 표시하고 유효한 예산 대기 중 준비 상태의 반복 조회를 멈춘다. |
| P2 | 후보 없는 같은 목록 항목을 재확인한 뒤 과거 보류를 수정하면 현재 항목과 보류 집계가 불일치했다. 완료 처리 잠금도 과거 행으로 우회할 수 있었다. | 같은 플레이리스트 목록 항목의 최신 결정을 공유하고 등록 중인 관련 행 전체에 잠금을 적용한다. |
| P2 | 재확인·조회 재시도·보관 명령의 응답이 유실되면 같은 멱등 키 재전송이 버전 충돌로 실패했다. | 기존 카탈로그 이벤트 저장소에 원자적 명령 영수증을 남겨 같은 요청을 복구하고 다른 의도의 키 재사용은 거부한다. 새 테이블은 추가하지 않았다. |

각 문제는 수정 전 실패 테스트로 재현했다. 해결하지 않으면 반복 작업의 위치·처리 결과·복구 가능성이 손상되므로 이번 PR에서 함께 수정했다. 마지막 페이지를 50개라고 부르던 목록 이름도 이번 묶음으로 정정했다.

## 검증

- UI 소비자 3파일 97건, 실제 D1 작업 큐 17건 PASS. 새 회귀에는 지연 응답 후 중단, 정보 갱신 실패 보류, 다른 완료 묶음 진입, 예산 대기, 후보 없는 항목의 과거 결정·등록 잠금, 응답 유실 후 같은 명령 복구가 포함된다.
- 변경된 테스트·Worker 타입과 lint PASS. 실제 로그인된 관리자 화면에서 마지막 29개 묶음의 검수 위치·진행률·항목별 보류/제외 메뉴를 확인했다.
- 이전 구현 검증은 [재개편 기록](otw-play-import-review-redesign.md)에 있다. 실제 50/50/29 페이지와 검수 저장·비공개 등록·다음 페이지 준비·D1/카탈로그 재조회가 포함된다.

최종 PR의 전체 preflight, 운영 마이그레이션, 병합·배포 증거는 PR 검증 댓글에 기록한다. 이 문서는 당시 실행하지 않은 결과를 미리 성공으로 표현하지 않는다.

## 남은 한계

관리자 빌드 청크 크기 경고는 기능 회귀가 아니며 이번 변경에서 번들 구조를 재설계하지 않았다. 전체 접근성 인증, 실제 브라우저 두 관리자 세션의 동시 편집, 강제 네트워크 장애는 수행하지 않았다. 동시 요청·응답 유실·부분 등록 실패는 실제 D1 회귀 테스트가 보완한다. AI 추정 결과와 플레이리스트 수량 변경은 관리자 검수 및 화면의 확인 필요 표시를 유지한다.

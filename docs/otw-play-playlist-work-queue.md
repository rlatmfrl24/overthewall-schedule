# OTW Play 플레이리스트 작업 큐

이 문서는 초기 작업 큐 구조와 당시 검증 기록이다. 현재 진입 화면·한 곡씩 검수·회차 진행률은 [가져오기·검수 재개편](otw-play-import-review-redesign.md)을 따른다.

관리자 **OTW Play → 가져오기/검수 → 작업 큐**에서 공개·일부 공개 노래 클립 플레이리스트 URL을 줄마다 하나씩 추가한다. 등록 단계에서는 플레이리스트 정보만 확인하며 영상 전체 수집이나 AI 분석을 시작하지 않는다. 같은 URL은 기존 큐를 재사용하고 입력·접근 오류를 행별로 표시한다.

## 운영 흐름

1. `다음 50개 시작`으로 영상 한 페이지와 메타데이터를 수집하고 기존 AI Queue에 초안을 요청한다. 중복·등록·제외·보류 기록은 재사용한다. 실제 AI 대상은 최대 50개이며 빈 자리를 추가 페이지로 채우지 않는다.
2. 현재 묶음의 `검수 열기`에서 기존 검수 화면과 게시 미리보기·구간 재생을 사용한다. 저장은 사람의 검수값만 확정하며 곡·인물 identity를 카탈로그에 즉시 반영한다. 여러 곡·모호한 연결은 직접 선택한다.
3. 바로 검수할 수 없는 영상은 사유와 함께 보류한다. 제외와 보류는 별개이며 보류는 완료 수에 포함하지 않는다. 보류 목록에서 다시 검수한 뒤 별도로 비공개 등록할 수 있다.
4. AI 처리 종료 후 모든 항목을 검수 저장·등록·제외·보류하면 `완료하고 다음 50개 준비` 또는 `완료하고 쉬기`를 선택한다. 서버가 비공개 가창 등록을 확인한 뒤 묶음을 마감한다. 일부 등록 실패는 성공 항목을 보존하고 현재 묶음에서 재시도한다. 게시는 기존 카탈로그 화면의 별도 동작이다.
5. 다음 페이지가 없으면 등록 순서의 다음 대기 플레이리스트로 이동한다. 끝까지 확인한 목록은 `새 항목 확인`으로 처음부터 다시 순회한다. 이미 처리한 영상은 재분석하지 않는다.

화면을 닫아도 현재 요청은 계속 처리되며 서버에 저장한 큐·묶음·검수·보류는 다시 열 수 있다. 저장하지 않은 입력에는 기존 이탈 경고를 적용한다. 다음 묶음은 관리자의 완료 동작 없이 시작하지 않는다.

## 저장과 복구

- `0099_acoustic_rachel_grey.sql`이 큐·묶음·항목 진행 기록을 추가한다. 배포 전에 적용해야 하며 기존 후보·카탈로그를 변경하지 않는다.
- 기존 수집 및 AI Queue binding을 사용한다. 신규 Queue, 모델, 자동 게시나 예약 재수집을 추가하지 않는다.
- 한 묶음만 활성화하며 서버의 버전 검사, 요청 키, lease와 기존 maintenance recovery를 사용한다. 응답이 유실된 요청은 같은 키로 재전달한다. 명확한 버전 충돌은 최신 상태로 새 요청을 만든다.
- 수집 실패는 초안 준비 완료로 표현하지 않는다. 메타데이터 재시도 성공 후 AI 준비를 이어가고, 페이지 토큰 오류는 비어 있는 실패 묶음의 `목록 처음부터 다시 확인`으로 복구한다.
- 보류·제외 집계와 목록은 최신 결정을 표시하고 과거 행은 이력으로 보존한다. API 메타데이터는 기존 30일 보존 기준을 적용하며 만료한 영상은 검수 진입 시 갱신한다.
- 큐 등록·진행 조회는 모델을 호출하지 않는다. 진행 중에는 현재 묶음만 주기적으로 조회하며 과거 큐 집계는 화면 진입·명시적 갱신·변경 후 읽는다.

50개 분할은 한 번의 작업량을 제한한다. 모든 영상을 결국 분석하면 총비용은 영상 길이·모델 사용량·재시도에 따라 발생하며, 일일 호출 한도는 금액 상한이 아니다. 기존 AI 예산·동시 호출·캐시·재시도와 수집 읽기 예산 검사를 유지한다.

## 검증 기준

관련 UI·API 테스트와 실제 D1 통합 테스트에서 일괄 등록의 수집·AI 미실행, 한 페이지 경계와 마지막 묶음, 동시 시작, 응답 유실, 메타데이터 실패 복구, 보류 재개·최신 제외 결정, 비공개 등록의 부분 성공·재시도·중복 방지를 확인한다. 마이그레이션 체인·D1 doctor·타입·아키텍처·빌드 검증과 인증된 실제 관리자 흐름의 증거는 구현 전달 시 별도로 기록한다. 자동 테스트는 실제 Gemini 결과 품질이나 운영 배포의 증거를 대신하지 않는다.
